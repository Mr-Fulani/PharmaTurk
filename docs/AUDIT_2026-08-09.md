# Аудит проекта Mudaroba — 9 августа 2026

## Итоговый вердикт

Проект существенно усилен по сравнению с исходным состоянием: критические
ошибки доверия к payment webhook, захвата аккаунтов через social auth,
SSRF/XSS, неконтролируемых загрузок, публичности профилей, конкуренции корзины
и небезопасных production defaults исправлены в коде и покрыты целевыми
тестами.

При этом текущую ревизию нельзя выпускать в production безусловно. Статус —
**условный NO-GO до выполнения P0 release gates**:

1. удалить/переместить legacy PDF-чеков с предсказуемыми R2-ключами после
   backup и retention-решения;
2. проверить миграции поверх production-like snapshot, а не только с нуля;
3. выполнить staging E2E CoinRemitter;
4. получить зелёный remote CI, включая exact production image build;
5. исправить публичный HTTP→HTTPS redirect/reverse-proxy headers и повторить
   production TLS smoke-test.

Это операционные проверки и изменения внешнего состояния. На первичном этапе
Docker намеренно не использовался, потому что host был занят другим
приложением. 20 августа Docker-проверки продолжены в отдельном Compose project;
актуальные результаты приведены в конце отчёта.

## Критические находки, исправленные в ходе аудита

### 1. Payment webhook доверял недостоверному входу

Риск: подделанный статус или повторный webhook мог привести к неверному
статусу заказа, повторному списанию остатков либо уведомлению без достоверной
оплаты.

Исправлено:

- состояние invoice повторно запрашивается через авторизованный CoinRemitter
  `invoice/get`;
- проверяются provider identity, order binding, валюта, requested/paid amount;
- применены transaction + row locks и идемпотентная обработка paid/expired;
- paid-заказ не понижается последующим событием;
- provider outage даёт retryable `503`, malformed payload не вызывает `500`;
- checkout блокирует корзину/items/promo, а promo потребляется только после
  успешного создания invoice.

### 2. Account takeover и небезопасное social linking

Риск: регистрация/социальный вход могли связать нового провайдера с аккаунтом
по неподтверждённому email.

Исправлено:

- Google ID token проверяется по точным `aud`, `iss` и `email_verified`;
- access-token fallback для identity linking удалён;
- VK/Google не присоединяются к существующему пользователю по недоверенному
  email;
- гостевые заказы присваиваются только после подтверждённой identity;
- Telegram bind/sync подписан HMAC, ограничен 15 минутами и защищён от replay;
- Telegram webhook требует secret-token header;
- публичные профили теперь private by default, добавлена data migration.

### 3. SSRF, unbounded downloads и медиа-DoS

Риск: сервер мог обращаться к private/link-local адресам, следовать опасным
redirect, загружать чрезмерные файлы либо декодировать image bombs.

Исправлено:

- добавлен общий safe image fetcher с DNS/IP validation, DNS pinning, ручными
  redirect, byte/pixel limits и sniffing реального формата;
- публичный image proxy использует allowlist хостов и rate limits;
- proxy media ограничен публичными namespaces, поддерживает корректный Range/
  `416` и не раскрывает receipts/temp;
- AI, medicine enrichment, testimonial и review images получили bounded
  validation/normalization;
- `verify=False` удалён из базовых Zara/Inditex parser paths; для TLS inspection
  предусмотрен явный CA bundle.

### 4. Stored/reflected XSS и небезопасный receipt print

Исправлено:

- CMS/imported/AI rich HTML проходит DOMPurify;
- JSON-LD экранирует закрытие `<script>`;
- receipt `document.write` экранирует динамические значения и получает CSP;
- analytics IDs принимаются только в ожидаемых форматах;
- WeasyPrint запрещено загружать внешние ресурсы.

### 5. Избыточно публичные API и отсутствие throttling

Исправлено:

- DRF default установлен в `IsAuthenticated`, публичность задаётся явно;
- AI/VAPI доступны только staff;
- testimonial create требует пользователя, изменения — staff;
- login/token/upload/checkout/receipt/webhook/cart/cookie consent и дорогие
  catalog endpoints имеют burst/sustained throttles;
- чувствительные serializers/query limits стали строгими и bounded.

### 6. Конкуренция и бесконтрольный рост корзин

Исправлено:

- добавлены partial unique constraints для user/session carts и data migration
  с merge дублей;
- анонимный GET cart не создаёт session или DB row;
- no-op/invalid mutations не создают корзину;
- ежедневная cleanup-задача удаляет только старые anonymous carts bounded
  batches с row locking;
- raw request payload удалён из production logs.

### 7. Небезопасные production defaults и контейнеры

Исправлено:

- fail-fast отклоняет debug, wildcard hosts, dummy crypto, слабый secret,
  неполный/слабый PostgreSQL URL, Telegram без webhook secret и совпадающие
  Redis targets;
- DB/Redis connect/socket waits ограничены;
- liveness не касается зависимостей, readiness требует PostgreSQL и Redis;
- backend/worker работают non-root; build использует in-project virtualenv;
- frontend не получает весь root `.env` в build context;
- stateful services находятся во внутренней `data` network, а dev-порты
  привязаны к `127.0.0.1`;
- backend Docker build получает отдельные безопасные build-only DB/Redis URL;
- Nginx получил базовые security headers и отключённый `server_tokens`.

### 8. Документация и supply chain расходились с кодом

Исправлено:

- baseline выровнен на Python 3.12.13, Django 5.2.17, Node 22.23.2,
  Next.js 15.5.21, PostgreSQL 15.18, Redis 7.4.10, Qdrant 1.18.2;
- OpenSearch удалён из актуального stack;
- backend/frontend используют lock-based reproducible install;
- CI проверяет tests, build, migrations, dependency audits и Compose config;
- README/DEV/DEPLOY/auth/payment/notification/AI/Celery/env документы
  синхронизированы;
- устаревшие currency deployment/system guides явно помечены архивными;
- Compose project name унифицирован как `mudaroba`.

## Локальный `.env` и секреты

В ignored `.env` обнаружены непустые значения, похожие на реальные credentials
нескольких внешних провайдеров. Значения не выводились и не переносились в
отчёт.

Что подтверждено:

- `.env` покрыт `.gitignore`;
- файл не tracked;
- `git log --all -- .env` не показал коммитов этого пути;
- права исправлены с `0644` на `0600`;
- простой поиск типовых token/private-key signatures в tracked working tree не
  дал совпадений.

Дополнительная проверка Gitleaks всей доступной истории и текущего
неигнорируемого дерева не обнаружила эти значения. Поэтому массовая ротация не
является доказанным release gate: конкретный ключ нужно отзывать при
подтверждённой экспозиции, подозрительной активности либо по его штатному сроку.
Provider audit logs всё равно следует проверить перед production release.

Локальный `.env` также не содержит явных `REDIS_CACHE_URL` и
`CELERY_RESULT_BACKEND_URL`. Содержимое намеренно не переписывалось: файл может
использоваться оператором. Перед следующим production-like запуском его нужно
синхронизировать с `.env.production.example`.

## Открытые риски и рекомендации

### P0 — до production release

1. Проверить provider audit logs/CI artifacts; ротировать только ключи с
   подтверждённой экспозицией, подозрительной активностью или истёкшим сроком.
2. Удалить либо переместить найденные dry-run инвентаризацией старые
   `receipts/{order.number}.pdf` в R2/CDN (125568 bytes суммарно). Код больше не
   читает legacy key и регенерирует чек в HMAC namespace, но внешние объекты
   автоматически не удаляются.
3. Применить миграции поверх production-like snapshot. Чистая PostgreSQL 15.18,
   полный suite, cart constraints и migration split уже подтверждены.
4. Staging CoinRemitter E2E, включая повтор webhook, timeout и reconciliation.
5. Исправить Cloudflare/origin маршрутизацию: 20 августа публичные apex и `www`
   отвечали `200` по HTTP вместо redirect на HTTPS, HSTS отсутствовал, а
   проектные Nginx headers не были видны. После исправления повторить TLS,
   trusted real-IP и reverse-proxy smoke. До нормализации provider IP allowlist
   должен оставаться пустым.

### P1 — ближайший спринт

1. Перевести invoice creation на pending order + idempotency/outbox. Сейчас
   внешний вызов находится внутри DB transaction; provider success + local
   rollback может создать orphan invoice.
2. Уменьшить OpenAPI baseline: схема валидна, но содержит 605 warnings
   (598 unique), преимущественно отсутствующие return types, operationId
   collisions и enum/path hints.
3. Перенести JWT из JS-readable cookies в HttpOnly Secure cookies/BFF с CSRF
   моделью. Текущие `access`/`refresh` доступны JavaScript и повышают ущерб от
   любого будущего XSS.
4. Включить nonce/hash CSP: сначала report-only, затем enforcement.
5. Проверить readiness под реальным network blackhole. Connect/socket timeouts
   теперь заданы, но нужны runtime latency/thread-exhaustion tests.
6. React Hooks warnings закрыты; постепенно заменить 44 оставшихся `<img>` на
   оптимизированный image path, начиная с LCP-элементов.
7. ESLint gate теперь запрещает рост выше 44 warnings; отдельно обновить
   deprecated ESLint 8/toolchain.
8. OpenAPI regression test запрещает рост выше 598 unique warnings; постепенно
   добавлять return types/schema hints и снижать baseline до нуля.

### P2 — системный техдолг

1. Генерировать YML feed фоново/потоково, хранить готовый объект и отдавать с
   ETag; текущий путь собирает XML в памяти и имеет N+1-риск.
2. Перевести оставшиеся privileged ingestion paths (`catalog/signals.py`,
   `parser_media_handler.py`, `vk_market_sync.py`) на общий bounded/pinned
   fetcher.
3. Валидировать container/codec testimonial video, а не только размер и
   расширение.
4. На масштабе разделить Celery broker, cache и result backend физически, а не
   только Redis logical DB.
5. Убрать последовательный resolve по множеству catalog ViewSet и продолжить
   декомпозицию крупных catalog/frontend файлов.
6. SMS endpoints либо реализовать с подтверждением/anti-abuse, либо удалить из
   публичного контракта; сейчас они честно отвечают как stubs (`501`).
7. Перевести backend image на multi-stage runtime без compiler headers и
   закрепить production images/GitHub Actions immutable digest/SHA с
   автоматизированным обновлением.

## Продолжение P0 — 20 августа 2026 года

Сначала без запуска Docker добавлены три release-safety механизма:

- blocking Gitleaks job сканирует полную доступную Git history в CI;
- `cleanup_legacy_receipts` выполняет dry-run inventory плоских legacy PDF в R2,
  скрывает ключи по умолчанию и требует bucket + quarantine prefix + `--apply`;
- `reconcile_coinremitter` только читает локальные платежи и авторизованный
  `invoice/get`, классифицируя drift без изменения статусов.

Модель платежа теперь отдельно сохраняет длинный provider `id` и короткий
`invoice_id`; это устраняет неоднозначность lookup, сохраняя совместимость со
старыми строками. Нужна миграция `payments.0002_cryptopayment_invoice_code`.

Эти инструменты не заменяют внешние операции: credentials не ротировались,
R2-объекты не удалялись, CoinRemitter API/staging не вызывался. R2 inventory
позднее был выполнен в безопасном dry-run режиме.

Проверки этого продолжения без Docker: **163 passed**, **17 deselected** и
**20 subtests passed** в непересекающихся DB-free группах; Django system check
— 0 issues; `makemigrations --check --dry-run` — no changes detected; Python
compileall, CI YAML parse, локальные Markdown-ссылки и `git diff --check`
успешны. Позднее Gitleaks был подтверждён локально через официальный container.

## Docker/PostgreSQL продолжение — 20 августа 2026 года

Docker-проверки выполнялись в отдельном project `mudaroba_audit`, без host
ports. Контейнеры и volumes другого приложения не изменялись. После проверки
тестовые PostgreSQL/Redis/Qdrant containers, network и audit volumes удалены.

Подтверждено:

- development и production Compose merge проходят `config --quiet` с
  соответствующими env templates;
- PostgreSQL 15.18 и Redis 7.4.10 успешно стартовали на internal network;
- все миграции применяются с нуля, Django check сообщает 0 issues,
  `makemigrations --check --dry-run` не видит drift;
- полный backend suite на PostgreSQL: **961 passed**, 4 deprecation warnings;
- cart dedup и partial unique indexes разделены на миграции `0008` и `0009`,
  потому что PostgreSQL не создаёт индекс при pending trigger events в той же
  transaction после удаления дублей;
- production frontend image собран из lock-файла, запускается от пользователя
  `node`, имеет размер около 269 MB и отдаёт главную страницу с HTTP 200;
- frontend unit tests: **51 passed**;
- production dependency audit непосредственно в финальном image: **0
  vulnerabilities** после обновления override `nanoid` с 3.3.17 до 3.3.18;
- оба Dockerfile проходят `docker build --check` без warnings;
- Celery app загружается с разделёнными broker/cache/result Redis URL; worker
  стал ready на очередях `celery`, `ai`, `recsys`, Beat успешно стартовал;
- backend production image собран с CPU-only PyTorch, весит около 540 MB,
  запускается non-root, проходит `pip check`, entrypoint/Gunicorn health;
- PostgreSQL, три Redis logical DB и Qdrant сохранили тестовые маркеры после
  restart; backend readiness после restart остался успешным.

Найдено и исправлено в ходе container-проверок:

- Debian Bookworm не содержит пакет `libgobject-2.0-0`; лишняя запись удалена
  из backend Dockerfile, необходимая библиотека приходит с `libglib2.0-0`;
- build-only backend settings получили валидные отдельные DB/Redis URL ранее в
  аудите и теперь проходят статическую проверку;
- npm и Poetry install steps используют BuildKit cache mounts, чтобы повторные
  сборки не скачивали dependency tree заново;
- serializer tests больше не зависят от внешнего currency API; удалены тесты
  небезопасного legacy auto-download signal, вместо них закреплено его
  отсутствие.

Первый backend build выявил нехватку диска Docker Desktop на финальной
распаковке. Для восстановления было удалено 13.97 GB только неиспользуемого
BuildKit cache; образы, контейнеры и volumes другого приложения не удалялись.
После перехода lock-файла на `torch=2.13.0+cpu` production image и весь runtime
gate завершились успешно. Повторный clean build следует закрепить в CI runner с
гарантированным запасом диска.

## Финальная безопасная проверка — 21 августа 2026 года

- release-скрипты переведены на контролируемое maintenance window: до миграций
  останавливаются Nginx, web и все Celery writers; rollout/rollback не смешивает
  разные revisions;
- автоматическая регистрация Telegram webhook отключена по умолчанию и требует
  явного `REGISTER_TELEGRAM_WEBHOOK_ON_START=1`; обычный staging restart больше
  не может перенаправить общий production bot;
- Redis production validator сравнивает host/port/DB независимо от credentials,
  а social-auth и medicine enrichment больше не логируют tokenized URLs,
  provider tokens или email;
- frontend refresh использует отдельный Axios request и единый shared promise:
  невалидный refresh token больше не способен заблокировать собственный
  interceptor;
- текущий backend-код смонтирован read-only в existing Python 3.12 test image и
  проверен на отдельном PostgreSQL/Redis/Qdrant project: **970 passed**, 4
  deprecation warnings, **30 subtests passed**;
- frontend: production audit — 0 vulnerabilities, lint — 0 errors/44 baseline
  warnings, TypeScript — passed, unit tests — **51 passed**, production build —
  passed;
- `poetry check --lock`, Django system check, migration drift, shell syntax,
  четыре Compose merge и `git diff --check` прошли.

Попытка повторного exact Docker build успешно прошла frontend image и backend
`compilemessages`/`collectstatic`, но Docker Desktop получил I/O error при
экспорте backend layer: host-диск до этого был заполнен до 151 MiB. После
удаления только пересоздаваемых host caches свободно 6.3 GiB; destructive Docker
prune/reset не выполнялся. Обычный restart потребовал завершить зависший
Docker host-backend и восстановил daemon, однако VM log содержит ext4 `error -5`
с предупреждением о potential data loss. Два ранее активных временно
именованных `saas-p1-cron-*` контейнера после восстановления отсутствуют в
metadata; их нельзя самовольно реконструировать без Compose-контекста владельца.

Поэтому новый image build на этом shared host остановлен как небезопасный.
Exact production images текущего коммита должны быть собраны blocking job в
remote CI с достаточным диском; staging/production остаются NO-GO до зелёного
job, проверенных backup/rollback artifacts и решения по ingress/R2.

Первый remote CI dependency audit обнаружил четыре новых advisory для
`sqlparse 0.5.5`; broad exception не добавлялся. Runtime constraint и lock
обновлены до `sqlparse 0.6.0`, где advisory исправлены. GitHub Actions,
использовавшие deprecated Node 20 runtime, переведены на официальные Node 24
majors (`checkout@v5`, `setup-node@v5`, `setup-python@v6`, `cache@v5`).
