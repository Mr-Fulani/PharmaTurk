# Персональные рекомендации на главной

## Статус

**Отложено: требуется завершить перед повторным включением.**

Компонент `frontend/src/components/PersonalizedRecommendations.tsx` подключён
на главной странице и запрашивает:

```text
GET /api/recommendations/personalized/
```

Сейчас API работает в двух режимах:

- `based_on: "your_history"` — персональная выдача по вектору пользователя;
- `based_on: "trending"` — свежие товары для гостя или пользователя без
  рассчитанного профиля.

Режим `trending` намеренно не отображается на фронтенде, чтобы не дублировать
стоящий рядом блок «Хиты продаж». Это сделано условием:

```tsx
if (basedOn === 'trending') return null
```

Поэтому до завершения пользовательских профилей блок на главной обычно скрыт.
Просто удалять это условие не следует: тогда на главной снова появятся две почти
одинаковые подборки.

## Что уже работает

- Qdrant и отдельный воркер `celery_recsys`;
- текстовые, визуальные и комбинированные векторы товаров;
- ночная инкрементальная индексация новых и изменённых товаров;
- похожие товары и визуальный поиск;
- модели `ProductVector`, `RecommendationEvent` и `UserEmbedding`;
- API персональной выдачи для пользователя, у которого уже заполнен
  `UserEmbedding.preference_vector`;
- клиентская карточка и сетка персональных рекомендаций.

Снимок production на 2026-07-29:

- активных векторов товаров: 10 911;
- событий рекомендаций: 16 449;
- записей `UserEmbedding`: 5;
- заполненных `preference_vector`: 0.

Эти значения приведены только как диагностический снимок и со временем могут
измениться.

## Чего не хватает

### 1. Сбор пользовательских сигналов

Нужно регистрировать как минимум:

- просмотр карточки товара;
- добавление в избранное;
- добавление в корзину;
- оформленную покупку;
- при необходимости — клик по самой рекомендации.

События должны содержать пользователя, товар, источник действия и время.
Для гостевых сессий можно собирать обезличенную аналитику, но персональный блок
на первом этапе лучше включать только авторизованным пользователям.

### 2. Расчёт профиля пользователя

`UserEmbedding.update_from_behavior()` сейчас является пустой заглушкой.
Нужно реализовать:

- получение векторов товаров, с которыми взаимодействовал пользователь;
- веса событий, например:
  `просмотр < избранное < корзина < покупка`;
- уменьшение веса старых событий со временем;
- нормализацию итогового вектора;
- сохранение `preference_vector`, `category_weights`,
  `avg_price_viewed` и `price_sensitivity`;
- минимальный порог истории, после которого профиль считается пригодным.

Конкретные веса необходимо вынести в настройки, а не фиксировать внутри view.

### 3. Обновление профиля

Нужна отдельная Celery-задача, которая будет:

- ставиться в очередь после значимого действия пользователя;
- объединять несколько быстрых событий через debounce/lock;
- периодически пересчитывать устаревшие профили;
- безопасно повторяться без создания дублей.

Тяжёлые вычисления не должны выполняться внутри HTTP-запроса.

### 4. Корректная персональная выдача

При запросе к Qdrant необходимо исключать:

- уже просмотренные товары, если их повторный показ не нужен;
- неактивные и недоступные товары;
- теневые записи вариантов;
- дубли базовой и доменной карточки;
- текущий товар, если подборка используется на его странице.

Нужно учитывать разнообразие категорий и брендов, чтобы вся сетка не состояла
из почти одинаковых товаров.

Особое внимание требуется вариативным товарам: ссылка, избранное и корзина
должны использовать канонический `base_product_id`, а выбранный вариант должен
сохраняться отдельно.

### 5. Поведение фронтенда

До готовности персонализации сохранить текущее поведение:

- «Хиты продаж» отображаются всегда при наличии товаров;
- `trending` из персонального API скрывается;
- `your_history` отображается как «Вам может понравиться»;
- ошибка персонального API не ломает остальную главную страницу.

Для безопасного запуска добавить явный feature flag. До включения флага API
может продолжать рассчитывать профили и собирать метрики, но блок не должен
показываться пользователям.

### 6. Приватность и срок хранения

Перед включением определить:

- срок хранения истории взаимодействий;
- возможность удаления истории вместе с аккаунтом;
- какие события можно хранить для гостевых сессий;
- нужно ли отражать персонализацию в политике конфиденциальности.

## Критерии готовности

Функцию можно включать, когда выполнены все условия:

1. После достаточного числа действий у пользователя появляется непустой
   `preference_vector`.
2. API возвращает `based_on: "your_history"` и валидные канонические карточки.
3. Выдача не содержит неактивные товары, теневые варианты и дубли.
4. Переход в карточку, избранное и корзина корректно работают для обычных и
   вариативных товаров.
5. Есть тесты для гостя, нового пользователя, пользователя с историей,
   недоступности Qdrant и пустой выдачи.
6. Есть метрики: число рассчитанных профилей, доля `your_history`, ошибки
   Qdrant, показы, клики, добавления в корзину и покупки.
7. Функция прошла ограниченный запуск через feature flag.
