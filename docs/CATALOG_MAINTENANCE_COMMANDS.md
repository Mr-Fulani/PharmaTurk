# Обслуживание каталога: битые медиа, бренды производителей и FLO, старые цены, цены цветов, названия LCW, смена типа

В документе девять команд. Все по умолчанию работают в режиме dry-run (только отчёт),
данные меняют только с `--apply`. Отчёт и бэкап у них разные:

- `repair_broken_media` и `assign_manufacturer_brands` пишут CSV-отчёт (`/tmp/...`,
  путь можно задать через `--report`);
- `repair_flo_brands` пишет CSV-отчёт, а с `--apply` — ещё и бэкап прежних брендов
  (`/tmp/flo_brands_backup_<время>.json`, product_id → brand_id);
- `clear_heuristic_old_prices`, `recalc_colour_prices`, `retire_stale_domain_records`,
  `move_essential_oils_from_supplements` и `ensure_demand_categories` с `--apply` требуют
  `--backup <файл.json>` со старыми значениями;
- `repair_lcw_names` печатает замены в консоль, `--report` и `--backup` у неё нет —
  сохраните вывод, прежние названия есть только в нём.

На проде изменения выполняются только после просмотра dry-run и `pg_dump`.
Остальные management-команды — в [`MANAGEMENT_COMMANDS.md`](MANAGEMENT_COMMANDS.md).

## `repair_broken_media`

Ищет ссылки из БД каталога на файлы, которых нет в R2 или у которых нулевой размер.
Список файлов берётся одним листингом бакета, без запросов к CDN (кэш Cloudflare
может отдавать уже удалённые файлы).

| action | когда | что делает `--apply` |
|---|---|---|
| `repoint` | одна половина пары (`image_file`/`image_url`, `main_image_file`/`main_image`, …) жива | перенаправляет битую половину на живую |
| `redownload` | у записи есть внешний URL источника | скачивает файл заново (`_auto_download_impl`) |
| `rescrape` | у товара есть `external_url` и включённый парсер для этого домена | перескрейп одного товара с `target_category` товара |
| `delete` | источника нет, или перекачка/перескрейп не вернули файл | удаляет строку галереи, у товара/категории очищает поле |

Предохранители: остановка, если в листинге меньше 1000 объектов или нет `products/`,
а также если битых больше 20 % проверенных ссылок (сбой листинга или чужое хранилище).
Файлы без ссылок из БД команда не ищет и не удаляет — это `cleanup_orphaned_media`.

```bash
manage.py repair_broken_media                    # отчёт
manage.py repair_broken_media --apply --no-rescrape   # быстрые исправления без парсеров
manage.py repair_broken_media --apply            # всё, включая перескрейп
```

С 2026-10-20 перескрейп больше не пишет прежнюю цену в `old_price`
(см. `clear_heuristic_old_prices` ниже).

## `assign_manufacturer_brands`

Бренд медикамента и БАДа = производитель (`MedicineProduct.manufacturer`,
у БАДов — `external_data.attributes.manufacturer`). Варианты написания одной фирмы
склеиваются (`apps/catalog/utils/manufacturer_brands.py`): турецкий регистр
и буквы (İ/ı/ş/ü…), юридические хвосты (`San. ve Tic. A.Ş.`, `Tic.Ltd.Şti`),
родовые слова (`İlaç`, `Sağlık Ürünleri`), дефисы (`Farma-Tek` = `Farmatek`).
Фирма = самый короткий набор слов, с которого начинаются остальные написания
(`Sanofi` ← `Sanofi Pasteur Aşı`, `TEB` ← `Teb Yurt Dışından İlaç Temini Birimi`).
Разные фирмы с общим первым словом (MSD / Merck İlaç, Fresenius Kabi / Medikal,
Biogen / Bio-Gen) перечислены в `_NO_PREFIX_ROOTS`. По началу названия сопоставляются
только фарм-бренды (категории medicines/supplements/medical-equipment).

- Существующий бренд фирмы переиспользуется, ему добавляются категории
  `medicines`/`supplements`; иначе создаётся бренд с самым частым написанием
  (`external_data.source = manufacturer`).
- Фарм-бренды-дубли одной фирмы сливаются: их медикаменты и БАДы переносятся на
  основной бренд, дубль без логотипа/описания/сайта и без других товаров удаляется.
- Бренд проставляется только товарам без бренда или с заглушкой «Другое» (`slug=other`),
  вместе с теневым `Product`; ручные бренды не меняются.
- Новые товары получают бренд при парсинге: `ScraperIntegrationService._assign_manufacturer_brand`.

```bash
manage.py assign_manufacturer_brands             # отчёт со склейками
manage.py assign_manufacturer_brands --apply
```

## `repair_flo_brands`

До правила «мультибрендовый магазин» (25.10.2026) новый бренд со страницы FLO не
создавался, и товары получали заглушку «Другое» (на проде ≈1 520 из 1 665).
Повторный парсинг теперь сам заменяет «Другое», но команда исправляет всё сразу
и почти без запросов к FLO:

- ссылка карточки FLO начинается со slug бренда (`/urun/lumberjack-...-102265597`);
- фильтр «Marka» на листинге отдаёт пары slug → название (`manufacturer__9__Nike__1__nike`);
- команда загружает 4 корневых листинга (`/ayakkabi`, `/giyim`, `/canta`, `/aksesuar` —
  ≈1 000 брендов, ≈6 МБ) через прокси из настроек парсера FLO, карточки не обходит;
- бренд товара — самый длинный slug из фильтра, с которого начинается его ссылка
  (`polaris-5-nokta` раньше `polaris`). Не найденные остаются «Другое» и попадают в отчёт;
- бренд проставляется только товарам с «Другое» или без бренда, вместе с доменной
  записью (ShoeProduct и т. п.); ручные бренды не меняются. Новый бренд создаётся
  с разделом товара, как при парсинге.

Запросы к FLO идут через платный прокси — запускать только с согласия владельца.
Без сети можно передать сохранённые листинги: `--listing-html файл.html` (несколько раз).

```bash
manage.py repair_flo_brands                       # 4 запроса к FLO, отчёт без записи
manage.py repair_flo_brands --apply               # проставить бренды (+ бэкап JSON)
manage.py repair_flo_brands --listing-url /ayakkabi --listing-url /giyim
```

## `clear_heuristic_old_prices`

До 2026-10-20 `old_price` заполнялся прежней ценой при любой смене цены или валюты
(парсеры, рыночные проверки лекарств/БАДов, IKEA) — снижение цены давало бессрочную
ложную скидку. Теперь `old_price` — только зачёркнутая цена источника. Команда разово
очищает накопленные значения у товаров из парсеров (кроме Instagram), их доменных
карточек и вариантов мебели; настоящая зачёркнутая цена вернётся со следующим парсингом.
Отчёт на проде 20.10: 4317 товаров, «скидка» на витрине у 920 (813 лекарств, 98 LCW).

```bash
manage.py clear_heuristic_old_prices                                     # отчёт по источникам
manage.py clear_heuristic_old_prices --apply --backup /backups/old_price.json
```

## `recalc_colour_prices`

До 04.11.2026 цену товара с цветами (одежда, обувь, головные уборы, бельё) задавал первый
цвет с ценой, даже распроданный, а зачёркнутую — главный цвет парсера: у Nautica
K35052T 749,70 при зачёркнутой 1 249,50, витрина показывала одну цену, сортировка и
фильтр шли по другой. Теперь везде одно правило `default_fashion_variant`
(`apps/catalog/utils/default_variant.py`): первый по порядку сайта цвет в наличии,
зачёркнутая — того же цвета. Команда приводит к нему `Product` и доменную карточку по
сохранённым цветам: цену, зачёркнутую, валюту, наличие и остаток (как импорт: 1000 при
цвете в наличии). Только товары парсеров FLO, SuperStep, Zara, Bershka, Pull&Bear,
Massimo Dutti и LCW; у LCW зачёркнутой по цветам нет — проверяется только, что она выше
новой цены. Instagram не трогается: цену ведут вручную. Наличие команда только снимает
или оставляет: товар, снятый с продажи (`mark_products_gone`, 404 ссылки товара), сохраняет
цвета «в наличии», и поднять его по ним значило бы вернуть в продажу и в фид ВК то, чего у
источника нет. В сеть не ходит, пишет `update()` без сигналов, пачками (`--batch-size`, 500),
и у каждого изменённого товара пересчитывает цены в валютах с наценкой
(`update_currency_prices`: `ProductPrice` и `final_price_*` — по ним фильтр и сортировка).

**Шаг после релиза PR #306** — иначе цены сойдутся с витриной только после следующего
прохода парсера:

```bash
manage.py recalc_colour_prices                                           # сколько изменится, примеры
manage.py recalc_colour_prices --apply --backup /backups/colour_prices.json
```

Бэкап — значения «до» у товара и у доменной карточки (`product_id`, `domain_id`, цена,
зачёркнутая, валюта, наличие, остаток). Повторный запуск после `--apply` показывает «изменится: 0».

## `repair_lcw_names`

С октября 2026 og:title карточек LCW рекламный («Parfüm - Markalar - 669,90 TL»), и у
999 из 1070 товаров LCW такое название; повторный парсинг название не меняет. Команда
перечитывает страницу товара и берёт полное название из `<title>` (как парсер после
исправления), товары с применённым AI-результатом не трогает. ~3 с на товар.

```bash
manage.py repair_lcw_names --limit 20      # отчёт по 20 товарам
manage.py repair_lcw_names --apply         # заменить у всех
```

## `retire_stale_domain_records`

У товара должна быть одна доменная запись — текущего `product_type`. До 2026-10-21
смена типа (в админке или нормалайзером) создавала запись нового типа, а прежняя
оставалась активной: товар отдавался и в выдаче старого типа, а фото вариантов
одежды в новую запись не попадали. Пример — косметичка Massimo Dutti (Product 26178):
`ClothingProduct` 1027 с 5 фото в варианте «SİYAH» остался в `/api/catalog/clothing/products`,
у `AccessoryProduct` 450 галерея пустая.

Теперь это делает сигнал при каждой смене типа (`domain_sync.retire_stale_domain_records`);
команда — для товаров, сменивших тип раньше. Она переносит картинки в запись текущего
типа (галерею и фото вариантов; варианты целиком — если новый тип их поддерживает,
например одежда → обувь) и снимает прежнюю запись с публикации через `update()`:
базовый `Product` не меняется, файлы в R2 не удаляются — на них ссылаются обе записи,
поэтому `cleanup_orphaned_media` их не тронет. Повторный запуск ничего не дублирует.

```bash
manage.py retire_stale_domain_records                       # отчёт: сколько товаров с несколькими записями
manage.py retire_stale_domain_records --product 26178       # отчёт по одному товару
manage.py retire_stale_domain_records --product 26178 --apply --backup /backups/stale-domain-26178.json
manage.py retire_stale_domain_records --limit 0 --apply --backup /backups/stale-domain-all.json  # все
```

Откат по бэкапу: вернуть `is_active` прежних записей и удалить у записи текущего типа
строки галереи и варианты, которых нет в списках `gallery_pks_before`/`variant_pks_before`
(файлы при этом не удалятся: на них ссылается прежняя запись). Если у текущего типа нет
доменной записи (головные уборы, бельё и исламская одежда не создаются сигналом
`ensure_domain_product_for_base`), команда товар пропускает и пишет об этом в отчёте.

## `ensure_demand_categories`

Разделы по спросу в рунете (исследование 05.11.2026,
[reports/superstep-seo-core-2026-11-05.md](../reports/superstep-seo-core-2026-11-05.md);
«Туфли на каблуке» и «Балетки» — решение владельца 07.11.2026,
[reports/seniorah-feasibility-2026-11-07.md](../reports/seniorah-feasibility-2026-11-07.md)).
Повторный запуск создаёт только недостающее: на проде после 05.11 — эти два раздела.
Создаёт разделы, под которые у SuperStep есть товары и которые ищут, и переименовывает
разделы, названия которых так не ищут:

| Что | Раздел |
| --- | --- |
| новый | «Флиски» (`fleece`) в «Трикотаже» — турецкое «Polar» |
| новый | «Рюкзаки» (`backpacks`) в «Сумках и кошельках» — унисекс (мужские и женские рюкзаки уже есть) |
| новый | «Термосы и термокружки» (`thermoses`) в «Стаканах и бокалах» — Stanley |
| «Слайды» → «Шлёпанцы» | `slides` («шлёпанцы мужские» ищут, «слайды» — нет) |
| «Шлёпанцы» → «Сланцы и вьетнамки» | `flip-flops` (сначала, иначе два «Шлёпанца» в одном родителе) |
| «Худии» → «Толстовки и худи» | `hoodies` (опечатка; «толстовка» — самое частое слово) |
| новый | «Туфли на каблуке» (`heels`) в «Туфлях» — женская обувь Seniorah (07.11.2026) |
| новый | «Балетки» (`ballet-flats`) в «Повседневной обуви» — Seniorah (07.11.2026) |

Переименование — только если название ещё прежнее: ручную правку команда не трогает.
Название меняется в `Category.name` и RU-переводе. Описание раздела и RU-перевода, равное
старому названию (на проде 05.11.2026 у всех трёх — «Слайды», «Шлёпанцы», «Худии»),
заменяется новым, как в `constants.py`: иначе после очистки `meta_description` страница взяла
бы описание и показала «Слайды» на странице «Шлёпанцы». Title, description и ключевые слова
раздела, где стоит старое название, очищаются — страница соберёт их из нового. Тексты
посадочной страницы RU (`h1`, `meta_title`, `meta_description`, `seo_text`) со старым названием
тоже очищаются (на проде 05.11.2026 они пустые у всех трёх).
Наценки у новых разделов нет — действует наценка родителя, цены товаров не меняются.
Товары команда не переносит: новые раскладывает парсер, уже загруженные — отдельно.
Те же разделы и названия записаны в `apps/catalog/constants.py`, чтобы `seed_catalog_data`
их не откатил.

```bash
manage.py ensure_demand_categories                                          # показ
manage.py ensure_demand_categories --apply --backup /backups/demand-categories.json
manage.py ensure_demand_categories --only heels,ballet-flats --apply --backup /backups/heels.json
```

`--only` — только перечисленные slug (новые разделы и переименования), остальное не трогается:
так заводятся «Туфли на каблуке» и «Балетки», пока флиски, рюкзаки, термосы и переименования
ждут решения владельца. Незнакомый slug — ошибка со списком допустимых.

Бэкап — на томе `/backups` (как у `retire_stale_domain_records`): `/tmp` контейнера
`run --rm` пропадает вместе с ним. В бэкапе — прежние название, описание, мета и переводы
переименованных разделов и список созданных (`created`).

**Откат.** Созданные разделы (`fleece`, `backpacks`, `thermoses`), пока в них нет товаров, —
удалить в админке или `Category.objects.filter(slug__in=[...], products__isnull=True).delete()`;
с товарами — сначала вернуть товары в прежний раздел (бэкап команды переноса). Переименованные
— вернуть из бэкапа `name`, `description`, мета и RU-перевод (`name`, `description`,
`h1`, `meta_title`, `meta_description`, `seo_text`) в shell. `constants.py` откатывается
вместе с PR, иначе `seed_catalog_data` вернёт новые названия.

## `move_essential_oils_from_supplements`

ilacfiyati.com держит линейку PHYTOIL (Elentra İlaç: эфирные масла, гидролаты, цветочные
воды) среди БАДов, и парсер сохранял её БАДами: в описании стояло «Биологически активная
добавка к пище», AI-тексты уходили в модерацию (`title_category_mismatch`,
`supplement_health_claim`). Команда переносит такие товары в раздел «Эфирные масла»
(`essential-oils`, тип `incense`): масло одного растения — в его подраздел («Эвкалиптовое»,
«Чайное дерево»…), другое растение или смесь — в «Одиночные масла», гидролаты и цветочные
воды — в «Эфирные масла». Правило отбора — `apps/catalog/essential_oils.py`: явный признак
эфирного масла или гидролата («uçucu yağ», «hidrolat», «çiçek suyu», «essential oil», линейка
PHYTOIL) и нет формы, которую принимают внутрь (капсулы, таблетки, саше…), и источник не называет
товар пищевой добавкой («takviye edici gıda» — VACROL, масла ZADE VITAL). Просто «yağı» — не признак:
масло чёрного тмина, рыбий жир — БАДы. RU-название карточки учитывается, только если турецкого нет.
Показ на проде 02.11.2026 — ровно 206 товаров PHYTOIL ([reports/essential-oils-move-2026-11-02.md](../reports/essential-oils-move-2026-11-02.md)).

Что меняется (одна транзакция на товар): создаётся `IncenseProduct` — копия общих полей
`SupplementProduct` (цена, наличие, главное фото, EN SEO) и его переводов; в `Product` тип и
категория меняются через `update()` (`save()` затёр бы RU SEO пустыми полями новой записи);
галерея копируется, запись БАДа снимается с публикации (`retire_stale_domain_records`, не
удаляется); из описаний убирается абзац-оговорка БАДа, из ключевых слов (`keywords`,
`meta_keywords` товара, переводов и новой записи) — «БАД …» / «food supplement …» (вещество в
списке есть отдельным словом); «Хит продаж» снимается; бренду добавляется тип `incense`. Slug и адрес карточки (`/product/<slug>`) не меняются, предложения
источника, цены в валютах, корзины и заказы не трогаются. Название и SEO остаются прежними —
их обновляет повторная AI-обработка. Повторный запуск ничего не находит (товары уже не БАДы).
Нет активного раздела эфирных масел типа `incense` — команда останавливается с ошибкой.

**Наценка = цена на сайте.** Наценка считается от раздела ([CATEGORY_MARKUP_INHERITANCE.md](CATEGORY_MARKUP_INHERITANCE.md)):
у БАДов — 50 % корня «БАДы», у «Благовоний» и «Эфирных масел» своей нет (02.11.2026), сработала
бы общая 25 % — цена на сайте упала бы ≈ на 17 %. Показ печатает цену источника и цену с
наценкой до → после. `--apply` отказывает, если наценка у кого-то меняется, пока не выбран
вариант (решает владелец): `--section-markup 50` — записать разделу `essential-oils` наценку
50 % (цена прежняя; прежнее значение — в бэкапе) или `--allow-markup-change` — перенести с
общей наценкой.

```bash
manage.py move_essential_oils_from_supplements                      # показ: id, название, раздел → раздел, наличие, цена
manage.py move_essential_oils_from_supplements --product 23956      # показ по товару (можно несколько --product)
manage.py move_essential_oils_from_supplements --section-markup 50      # показ: цена не меняется?
manage.py move_essential_oils_from_supplements --section-markup 50 --apply --backup /backups/essential-oils.json
```

Откат по бэкапу: `IncenseProduct.objects.filter(base_product_id__in=…).delete()` — через
queryset, не `instance.delete()` (тот удалит и `Product`; файлы не удалятся — на них ссылается
запись БАДа), затем вернуть в `Product` `product_type`, `category_id`, `is_featured`,
`description`, `keywords`, `meta_keywords`, описания и `meta_keywords` `ProductTranslation`,
`is_active`/`is_featured` записи БАДа, `category_slugs`/`primary_category_slug` бренда и
`margin_percent` раздела `essential-oils` (`section_margin_percent`).

Новые товары парсер ilacfiyati тем же правилом сразу кладёт в «Эфирные масла»
(`scrapers/medicine_categories.py`), а категория задачи другого типа у существующего товара
не меняется (`scrapers/services.py`, `_category_changes_domain`) — перенесённое масло не вернётся
в БАДы при повторном парсинге.


## Пустые разделы мебели не показываются

Дерево «Мебели» повторяет разделы IKEA, а товары есть не во всех (27.10.2026 — в 20 из 73).
Решение владельца: раздел без активных товаров во всём своём поддереве не попадает в списки
`/api/catalog/categories` (дерево страницы категории, подразделы, `all=true`, `children`), поэтому
его нет ни в меню, ни на странице «Мебели». Раздел появляется сам, как только в нём или в его
подразделе есть товар, — список пересчитывается раз в 5 минут (`_empty_furniture_category_ids`,
`apps/catalog/views.py`). Раздел, запрошенный по slug, открывается всегда; в sitemap пустые
разделы и раньше не попадали (`_nonempty_category_ids`). Выключать категории в админке не нужно.
Ловушка: смена типа товара через `Product.save()` не создаёт доменную запись нижнего белья,
головных уборов и исламской одежды (их нет в `domain_sync._get_domain_map`) — у таких типов
запись создаёт парсер (`ScraperIntegrationService._get_*_product`), а прежняя снимается
`retire_stale_domain_records` (27.10.2026 так переносились боксеры Zara).

## `replace_delivery_terms`

Сроки доставки в уже записанных SEO-описаниях лекарств и БАДов (решение владельца 09.11.2026: у
лекарств и БАДов «авиа 3–7, наземная 7–14, морем 20–45 дней», как на `/delivery`). Генераторы SEO
уже пишут «Заявка менеджеру, доставка 3–14 дней.»; команда меняет прежние «… 7–21 рабочий день.»
(лекарства), «… 7–14 дней.» (БАДы) и другие формулировки срока на «3–14 дней» (правила —
`apps/catalog/services/delivery_terms.py`). Поля `seo_description`, `meta_description`,
`og_description` у `Product` (medicines/supplements), `ProductTranslation`, `MedicineProduct`,
`SupplementProduct` и их переводов. Одежду, обувь и прочее не трогает, логи AI — тоже.

```bash
manage.py replace_delivery_terms                     # показ: товаров и записей к изменению, примеры
manage.py replace_delivery_terms --apply --backup /backups/delivery-terms-YYYYMMDD.jsonl
manage.py replace_delivery_terms --restore /backups/delivery-terms-YYYYMMDD.jsonl
```

Запись — пачками по 500 под блокировкой строк, только изменённые поля через `update()`. `--restore`
возвращает поле, только если его не меняли после записи. Тексты разделов, подборок и `/drugs`
меняет миграция `catalog/0239`.

На проде 10.11.2026 (релиз 745bba62): `--apply` записал 14 090 товаров (лекарства 6 808, БАДы 7 282),
116 256 полей; бэкап — `~/backups/ai-pilot/delivery-terms-20261110.jsonl.gz`; повторный показ — 0.
