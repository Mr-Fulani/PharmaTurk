# Поиск товаров на сайте

Как устроен поиск в шапке и на странице `/search`, а также поиск внутри разделов
(`/api/catalog/<раздел>/products?search=`). Первая очередь исправлений после аудита
05.11.2026 (`reports/search-audit-2026-11-05.md`, пункты P0 1–4). Код —
`backend/apps/catalog/product_search.py`, модель — `models_search.py`, страница —
`frontend/src/pages/search.tsx` + `src/lib/searchResults.js`.

## Коротко

- У каждого товара есть строка `ProductSearchIndex` (таблица `catalog_productsearchindex`)
  с подготовленным текстом: всё, по чему его можно найти.
- Запрос приводится к тому же виду и делится на слова. Товар находится, если в его тексте
  есть **каждое** слово (как часть слова: «магни» найдёт «магний»). Числа необязательны,
  если в запросе есть другие слова: «Nurofen 400» ищет по «nurofen», а 400 только поднимает
  товары с этим числом выше.
- С запросом и без явной `ordering` результаты идут по точности совпадения. С `ordering`
  (например, `price_asc`) — как попросили.
- Страница `/search` показывает 24 товара, общее число найденного и кнопку «Показать ещё».

## Что попадает в текст товара

| Откуда | Поля |
|---|---|
| `Product` | `name`, переводы `ProductTranslation.name` (ru, en), `sku`, `barcode`, `gtin`, `mpn`, `external_id` (артикул источника: `superstep-JL9188` → «superstep jl9188») |
| Бренд | `Brand.name` и переводы. Бренд-заглушка «Другое» (`slug=other`) не берётся |
| Доменная запись (лекарство, БАД, одежда…) | `name` и переводы; `manufacturer`, `active_ingredient` (турецкое МНН), `atc_code`, `barcode`, `gtin`, `mpn`, `external_id`; `active_ingredient` переводов (русское и английское МНН из памяти `medicine_inn`) |
| Варианты (цвета) | `sku`, `barcode`, `gtin` |

Отдельно хранятся `name` (все названия, по одному в строке) и `brand` — по ним считается
точность совпадения.

### Нормализация (`normalize_search_text`)

Одна функция для текста товара и для запроса:

- нижний регистр; `ё → е`;
- турецкие и другие латинские буквы с диакритикой → латиница: `İ/ı → i`, `ş → s`,
  `ç → c`, `ğ → g`, `ö → o`, `ü → u`, `â/î/û`, `é/è/ê` и т. п.;
- всё, кроме букв и цифр (дефисы, точки, скобки, запятые, `_`), — пробел:
  «Омега-3» → «омега 3», «VOGAST (лансопразол)» → «vogast лансопразол».

В текст товара дополнительно пишется склеенное написание слов с точкой или дефисом между
буквами: «U.S. Polo» → ещё и «us», «T-Shirt» → «tshirt». Поэтому находятся и «US Polo», и «U.S. Polo».

## Порядок результатов (`order_by_relevance`)

1. Одно из названий товара или бренд **совпадает** с запросом («Lacoste» → товары бренда Lacoste).
2. Название **начинается** с запроса целым словом («Парацетамол 500 мг»).
3. Название начинается с запроса как с части слова.
4. Запрос стоит в начале какого-то слова внутри названия («PAROL (парацетамол)»).
5. Остальные найденные (по переводу, веществу, производителю, коду).

Внутри группы — похожесть основного названия на запрос (`pg_trgm similarity`: короткое
«PAROL 500 мг» выше комбинации «GRIPORT COLD … парацетамол + …»), затем «в наличии»,
затем новизна и `id` (устойчивые страницы).

## Скорость

GIN-триграммный индекс `catalog_psi_text_trgm` по `text` (расширение `pg_trgm` из миграции
0207) — условие `text LIKE '%слово%'` идёт по индексу для слов от 3 букв. Короткие слова
(«d3», «с») проверяются перебором таблицы индекса — она маленькая (≈ 16 МБ на 30 тыс.
товаров вместе с индексом). Таблица отдельная от `catalog_product`: пересчёт не переписывает
строку товара с тяжёлым `external_data`.

Замер 05.11.2026 на модельном каталоге 30 тыс. товаров (локально, Postgres 15, ответ API
целиком, медиана из 5): на 61 запросе аудита, которые находили и старый, и новый поиск, —
24 карточки 168 → 172 мс, подсказка из 6 карточек 113 → 67 мс; худший ответ 1,5 → 0,96 с.
Сам SQL поиска — доли миллисекунды (`Bitmap Index Scan on catalog_psi_text_trgm`), почти
всё время — сборка карточек. Широкий запрос дороже на сортировку: «плёночной оболочкой»
(8,8 тыс. найденных) — 0,2 → 0,5 с.

## Когда текст пересчитывается

- После сохранения `Product`, `ProductTranslation`, доменной записи и её перевода
  (`post_save`, выполняется после коммита транзакции: `transaction.on_commit`). Парсеры и
  админка сохраняют товары через `save()`, поэтому текст обновляется сам.
- **Не** пересчитывается при `QuerySet.update()` / `bulk_create` / `bulk_update` — сигналы
  они обходят. Это переименование бренда, `assign_manufacturer_brands`, разнос правки МНН
  (`propagate_inn_translations`), `move_essential_oils_from_supplements`. После таких массовых
  правок — `rebuild_product_search_index --apply`. Товар, у которого строки индекса нет
  совсем (создан `bulk_create`), в поиск не попадает до пересчёта.

## Команда `rebuild_product_search_index`

```bash
manage.py rebuild_product_search_index                  # показ: сколько строк новых/изменится, примеры
manage.py rebuild_product_search_index --apply          # записать
manage.py rebuild_product_search_index --ids 12,345 --apply
manage.py rebuild_product_search_index --clear --apply  # откат: очистить, поиск снова по названию
```

Сеть, R2 и OpenAI не нужны. Первое заполнение (таблица пуста) — одной транзакцией: новый
поиск включается сразу для всех товаров. Повторные прогоны — пачками по `--batch-size` (500).

## Выкатка и откат

Пока таблица пуста, поиск и сигналы работают **по-старому** (`name__icontains`, сначала новые):
`search_index_ready()` — один запрос `EXISTS`. Поэтому порядок такой:

1. Обычный релиз: миграция `0237_product_search_index` только создаёт пустую таблицу и индекс
   (без данных, мгновенно).
2. Сразу после релиза на проде:
   ```bash
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index --apply
   ```
   (как запускать команды на проде — [MANAGEMENT_COMMANDS.md](MANAGEMENT_COMMANDS.md)).
   Таблица индекса — производные данные, `pg_dump` перед `--apply` не нужен.
   На модельном каталоге 30 тыс. товаров первый шаг — ≈ 11 с, `--apply` — ≈ 15 с, процесс ≈ 300 МБ памяти.
3. Смоук: `https://mudaroba.com/search?query=Abdi%20Ibrahim`, `…?query=омега 3`,
   `…/en/search?query=paracetamol` — товары есть; повторить аудит (`probe.py` из заметок
   аудита, 1 запрос в секунду).

Откат без релиза: `rebuild_product_search_index --clear --apply` — таблица пустеет, поиск
сразу возвращается к поиску по названию. Бэкап не нужен: таблица целиком собирается из
товаров и в `REQUIRED_TABLES` бэкапа базы не входит.
