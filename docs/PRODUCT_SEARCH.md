# Поиск товаров на сайте

Как устроен поиск в шапке и на странице `/search`, а также поиск внутри разделов
(`/api/catalog/<раздел>/products?search=`). Первая очередь исправлений после аудита
05.11.2026 (`reports/search-audit-2026-11-05.md`, пункты P0 1–4). Код —
`backend/apps/catalog/product_search.py`, модель — `models_search.py`, страница —
`frontend/src/pages/search.tsx` + `src/lib/searchResults.js`.

## Коротко

- У каждого товара есть строка `ProductSearchIndex` (таблица `catalog_productsearchindex`)
  с подготовленным текстом: всё, по чему его можно найти.
- Запрос приводится к тому же виду и делится на слова. Товар находится, если в его тексте
  есть **каждое** слово (как часть слова: «магни» найдёт «магний»). Числа необязательны,
  если в запросе есть другие слова: «Nurofen 400» ищет по «nurofen», а 400 только поднимает
  товары с этим числом выше.
- С запросом и без явной `ordering` результаты идут по точности совпадения. С `ordering`
  (например, `price_asc`) — как попросили.
- Страница `/search` показывает 24 товара, общее число найденного и кнопку «Показать ещё».

## Что попадает в текст товара

| Откуда | Поля |
|---|---|
| `Product` | `name`, переводы `ProductTranslation.name` (ru, en), `sku`, `barcode`, `gtin`, `mpn`, `external_id` (артикул источника: `superstep-JL9188` → «superstep jl9188») |
| Бренд | `Brand.name` и переводы. Бренд-заглушка «Другое» (`slug=other`) не берётся |
| Доменная запись (лекарство, БАД, одежда…) | `name` и переводы; `manufacturer`, `active_ingredient` (турецкое МНН), `atc_code`, `barcode`, `gtin`, `mpn`, `external_id`; `active_ingredient` переводов (русское и английское МНН из памяти `medicine_inn`) |
| Варианты (цвета) | `sku`, `barcode`, `gtin` |

Отдельно хранятся `name` (все названия, по одному в строке) и `brand` — по ним считается
точность совпадения.

### Нормализация (`normalize_search_text`)

Одна функция для текста товара и для запроса:

- нижний регистр; `ё → е`;
- турецкие и другие латинские буквы с диакритикой → латиница: `İ/ı → i`, `ş → s`,
  `ç → c`, `ğ → g`, `ö → o`, `ü → u`, `â/î/û`, `é/è/ê` и т. п.;
- всё, кроме букв и цифр (дефисы, точки, скобки, запятые, `_`), — пробел:
  «Омега-3» → «омега 3», «VOGAST (лансопразол)» → «vogast лансопразол».

В текст товара дополнительно пишется склеенное написание слов с точкой или дефисом между
буквами: «U.S. Polo» → ещё и «us», «T-Shirt» → «tshirt». Поэтому находятся и «US Polo», и «U.S. Polo».

## Порядок результатов (`order_by_relevance`)

Только в общем поиске `/api/catalog/products` (шапка и `/search`), при запросе от 3 символов:

1. Одно из названий товара или бренд **совпадает** с запросом («Lacoste» → товары бренда Lacoste).
2. Одно из названий **начинается** с запроса («Парацетамол 500 мг»).
3. Запрос стоит в начале какого-то слова внутри названия («PAROL (парацетамол)»).
4. Остальные найденные (по переводу, веществу, производителю, коду).

Внутри группы — короче название товара (короткое «PAROL 500 мг» выше комбинации
«GRIPORT COLD … парацетамол + …»), затем «в наличии», затем новизна и `id`.

Ключи сортировки считаются для **всех** совпадений, поэтому только дешёвые: `LIKE` по
строкам `search_index.name`/`brand` и длина названия. Регулярные выражения и `pg_trgm
similarity` (PR #321) на 8,8 тыс. совпадений стоили ≈ 0,8 с SQL.

Без сортировки по точности, сначала новые:
- запрос без слова от 3 символов («кр», «ма», «a», «кр ма») — он находит тысячи товаров;
- поиск внутри разделов (`/api/catalog/<раздел>/products?search=`): там условия на
  `external_data` доменных таблиц, и сортировка всех совпадений детоастила бы дампы парсеров.
  Сайт ищет только через `/api/catalog/products`.

## Скорость

GIN-триграммный индекс `catalog_psi_text_trgm` по `text` (расширение `pg_trgm` из миграции
0207) — условие `text LIKE '%слово%'` идёт по индексу для слов от 3 букв. Короткие слова
(«d3», «с») проверяются перебором таблицы индекса — она маленькая (≈ 16 МБ на 30 тыс.
товаров вместе с индексом). Таблица отдельная от `catalog_product`: пересчёт не переписывает
строку товара с тяжёлым `external_data`.

**Служебные строки при поиске — подзапросом.** Обычный список исключает служебные товары
(копии вариантов, заглушки лекарств) условием на `external_data`; категории так и работают —
по частичным индексам сортировки. Поиск сортирует все совпадения, и Postgres проверял это
условие по каждой строке, детоастя мегабайтные дампы парсеров. Поэтому с `search` служебные
строки исключаются `id NOT IN (…)` по частичному индексу `catalog_product_nonpublic_id_idx`
(миграция 0217, DEVELOPMENT_RULES §2.9), а основной запрос `external_data` не трогает
(тесты `test_search_excludes_service_rows_without_external_data_condition` и EXPLAIN-тест
`test_search_queryset_can_use_nonpublic_partial_index`). Так же устроен старый публичный
`/api/catalog/products/search?q=` (`CatalogService.get_products`).

**Карточки выдачи без `external_data`.** При поиске `view=card` откладывает поле (`defer`):
иначе каждая показанная строка отдавала мегабайтный дамп. Карточка читала его в двух местах —
запасная галерея копии варианта (таких строк в выдаче нет) и ISBN/страницы книги из
`attributes`; при отложенном поле первое пропускается, второе читается только у книг.

## Когда текст пересчитывается

- После сохранения `Product`, `ProductTranslation`, доменной записи, её перевода и вариантов
  (`variants`/`book_variants`: SKU, штрихкод, GTIN) — `post_save`, после коммита транзакции
  (`transaction.on_commit(..., robust=True)`: ошибка пересчёта уходит в лог и не ломает
  `save()` парсера или админки). Новая доменная запись связывается с `Product` через
  `update()`, поэтому `_sync_to_base_product` сам ставит пересчёт после связи.
- `save(update_fields=[…])` без полей, от которых зависит текст (наличие из ночной сверки,
  цена), пересчёт не запускает. Строка с тем же текстом не переписывается.
- **Не** пересчитывается при `QuerySet.update()` / `bulk_create` / `bulk_update` и при
  удалении варианта или перевода — сигналы такие правки не видят. Это переименование бренда
  (в том числе **правка названия бренда или его перевода в админке** — сохраняется бренд, а не
  товары), `assign_manufacturer_brands`, разнос правки МНН (`propagate_inn_translations`),
  `move_essential_oils_from_supplements`. После них — `rebuild_product_search_index --apply`.
  Товар, у которого строки индекса нет совсем (создан `bulk_create`), в поиск не попадает
  до пересчёта.

## Команда `rebuild_product_search_index`

```bash
manage.py rebuild_product_search_index                  # показ: сколько строк новых/изменится, примеры
manage.py rebuild_product_search_index --apply          # записать
manage.py rebuild_product_search_index --ids 12,345 --apply  # только при заполненном индексе
manage.py rebuild_product_search_index --clear --apply  # откат: очистить, поиск снова по названию
```

Сеть, R2 и OpenAI не нужны. Первое заполнение (таблица пуста) — одной транзакцией: новый
поиск включается сразу для всех товаров. Повторные прогоны — пачками по `--batch-size` (500).
`--ids` при пустом индексе запрещён: строка одного товара включила бы новый поиск для всего сайта.

## Выкатка и откат

Пока таблица пуста, поиск и сигналы работают **по-старому** (`name__icontains`, сначала новые):
`search_index_ready()` — один запрос `EXISTS`. Поэтому порядок такой:

1. Обычный релиз: миграция `0237_product_search_index` только создаёт пустую таблицу и индекс
   (без данных, мгновенно).
2. Сразу после релиза на проде:
   ```bash
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index --apply
   ```
   (как запускать команды на проде — [MANAGEMENT_COMMANDS.md](MANAGEMENT_COMMANDS.md)).
   Таблица индекса — производные данные, `pg_dump` перед `--apply` не нужен.
   На модельном каталоге 30 тыс. товаров первый шаг — ≈ 11 с, `--apply` — ≈ 15 с, процесс ≈ 300 МБ памяти.
3. **Второй прогон `--apply`** сразу после первого. Пока шло первое заполнение, сигналы видели
   пустую таблицу и ничего не писали, а заполнение читало товары до правок парсеров: второй
   прогон дописывает только изменившиеся строки (в отчёте «изменится: N», обычно единицы).
4. Смоук: `https://mudaroba.com/search?query=Abdi%20Ibrahim`, `…?query=омега 3`,
   `…/en/search?query=paracetamol` — товары есть; повторить аудит (`probe.py` из заметок
   аудита, 1 запрос в секунду).

Откат без релиза: `rebuild_product_search_index --clear --apply` — таблица пустеет, поиск
сразу возвращается к поиску по названию. Бэкап не нужен: таблица целиком собирается из
товаров и в `REQUIRED_TABLES` бэкапа базы не входит.

**Откат релиза (`rollback.sh` на предыдущий тег) — только после `--clear --apply`.** Внешний
ключ `catalog_productsearchindex.product_id` создан Django без `ON DELETE CASCADE` в базе:
каскад делает код. Старый код о таблице не знает, и при заполненной таблице удаление товара
(ночная очистка, админка) упадёт с `IntegrityError`. Пустая таблица старому коду не мешает.

Доменная запись без `base_product` в индекс не попадает (и раньше не попадала в общий поиск);
поиск внутри её раздела её тоже не найдёт. Сколько таких на проде (только чтение, локально
данных прода нет), например для лекарств — `SELECT count(*) FROM catalog_medicineproduct
WHERE base_product_id IS NULL;`, так же для остальных `catalog_*product`.
