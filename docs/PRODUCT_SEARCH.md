# Поиск товаров на сайте

Как устроен поиск в шапке и на странице `/search`, а также поиск внутри разделов
(`/api/catalog/<раздел>/products?search=`). Первая очередь исправлений после аудита
05.11.2026 (`reports/search-audit-2026-11-05.md`, пункты P0 1–4) и вторая очередь (P1 5–8:
кириллица, раскладка, опечатки, синонимы — раздел [«Язык запроса»](#язык-запроса-вторая-очередь));
третья (23.11.2026) — аптечные названия, лишнее слово в запросе, быстрые опечатки, там же. Код —
`backend/apps/catalog/product_search.py` и `search_language.py`, модель — `models_search.py`, страница —
`frontend/src/pages/search.tsx` + `src/lib/searchResults.js`.

## Коротко

- У каждого товара есть строка `ProductSearchIndex` (таблица `catalog_productsearchindex`)
  с подготовленным текстом: всё, по чему его можно найти.
- Запрос приводится к тому же виду и делится на слова. Товар находится, если в его тексте
  есть **каждое** слово (как часть слова: «магни» найдёт «магний»). Числа необязательны,
  если в запросе есть другие слова: «Nurofen 400» ищет по «nurofen», а 400 только поднимает
  товары с этим числом выше.
- С запросом и без явной `ordering` результаты идут по точности совпадения. С `ordering`
  (например, `price_asc`) — как попросили.
- Страница `/search` показывает 24 товара, общее число найденного и кнопку «Показать ещё».

## Что попадает в текст товара

| Откуда | Поля |
|---|---|
| `Product` | `name`, переводы `ProductTranslation.name` (ru, en), `sku`, `barcode`, `gtin`, `mpn`, `external_id` (артикул источника: `superstep-JL9188` → «superstep jl9188») |
| Бренд | `Brand.name` и переводы. Бренд-заглушка «Другое» (`slug=other`) не берётся |
| Доменная запись (лекарство, БАД, одежда…) | `name` и переводы; `manufacturer`, `active_ingredient` (турецкое МНН), `atc_code`, `barcode`, `gtin`, `mpn`, `external_id`; `active_ingredient` переводов (русское и английское МНН из памяти `medicine_inn`) |
| Варианты (цвета) | `sku`, `barcode`, `gtin` |
| Кириллица (вторая очередь) | бренд по-русски: словарь карточек `vocab.BRAND_RU` («nike» → «найк») и чтение латиницы («sanofi» → «санофи», «lacoste» → «лакосте»); у лекарств — торговое название из памяти `medicine_brand` («MAJEZIK» → «Мажезик», как в SEO); бренд берётся из турецкого оригинала (`medicine_source_name`: `external_data.source_name` → `name`, если он не переведён, → строка вкладки аналогов), а не только из русского названия с МНН в скобках («TYLOL (парацетамол) 500 мг…» давало бренд «TYLOL парацетамол», и «тайлол» в текст не попадал — исправлено 21.11.2026; написание по `name` тоже добавляется, если словарь его находит) и чтением латиницы («EUTHYROX» → «эутирокс»); производитель чтением латиницы |
| Тип и пол (вторая очередь) | кроме лекарств, БАДов и медтехники: тип товара и пол из названия по словарям карточек `vocab.KINDS` и `vocab.AUDIENCE` по-русски и по-английски («Kadın Spor Ayakkabı» → «женский Women's кроссовки Sneakers»); пол товара (`Product.gender`) |
| Раздел (вторая очередь) | название раздела товара и двух разделов выше с переводами («Рюкзаки», «Женская обувь») |

Отдельно хранятся `name` (все названия, по одному в строке) и `brand` — по ним считается
точность совпадения.

### Нормализация (`normalize_search_text`)

Одна функция для текста товара и для запроса:

- нижний регистр; `ё → е`;
- турецкие и другие латинские буквы с диакритикой → латиница: `İ/ı → i`, `ş → s`,
  `ç → c`, `ğ → g`, `ö → o`, `ü → u`, `â/î/û`, `é/è/ê` и т. п.;
- всё, кроме букв и цифр (дефисы, точки, скобки, запятые, `_`), — пробел:
  «Омега-3» → «омега 3», «VOGAST (лансопразол)» → «vogast лансопразол».

В текст товара дополнительно пишется склеенное написание слов с точкой или дефисом между
буквами: «U.S. Polo» → ещё и «us», «T-Shirt» → «tshirt». Поэтому находятся и «US Polo», и «U.S. Polo».

## Порядок результатов (`order_by_relevance`)

Только в общем поиске `/api/catalog/products` (шапка и `/search`), при запросе от 3 символов:

1. Одно из названий товара или бренд **совпадает** с запросом («Lacoste» → товары бренда Lacoste).
2. Одно из названий **начинается** с запроса целым словом («Парацетамол 500 мг», но не «Столик» для «стол»).
3. Запрос **целиком** стоит в названии («ибупрофен 400» → «BRAVEX (ибупрофен) 400 мг»).
4. Все слова запроса стоят в названии **целыми словами** (слово как набрано, без окончания или буква
   витамина в другом алфавите: «витамин д3» → «NONDO Витамин D3, капли»).
5. Название начинается с запроса или запрос стоит в начале слова, но слово **продолжается**
   («dress» → «Dresser», «стол» → «Столик», «PAROL (парацетамол)» для «парацет»).
6. Все слова запроса есть в названии (с синонимами, внутри слова: «кружка» → «Термокружка»).
7. Слова стоят в начале слов остального текста (вещество, производитель, раздел, код).
8. Найдено **куском внутри слова** («коран» → «никорандил»).

До 24.11.2026 целое слово от продолжения не отличалось: по «dress» первым шёл комод Dresser, по
«стол» — столики, «ибупрофен 400» начинался с геля 5 %. Ступени 2–4 считаются по названиям одной
строкой с пробелами по краям (`' ' || replace(name, '\n', ' ') || ' '`), только `LIKE`; на самых
широких запросах это +3–10 мс SQL («таблетки», 6 879 товаров: 88 → 97 мс на копии индекса прода).

Внутри группы — короче название товара (короткое «PAROL 500 мг» выше комбинации
«GRIPORT COLD … парацетамол + …»), затем «в наличии», затем новизна и `id`.

Ключи сортировки считаются для **всех** совпадений, поэтому только дешёвые: `LIKE` по
строкам `search_index.name`/`brand` и длина названия. Регулярные выражения и `pg_trgm
similarity` (PR #321) на 8,8 тыс. совпадений стоили ≈ 0,8 с SQL.

Без сортировки по точности, сначала новые:
- запрос без слова от 3 символов («кр», «ма», «a», «кр ма») — он находит тысячи товаров;
- поиск внутри разделов (`/api/catalog/<раздел>/products?search=`): там условия на
  `external_data` доменных таблиц, и сортировка всех совпадений детоастила бы дампы парсеров.
  Сайт ищет только через `/api/catalog/products`.

## Скорость

GIN-триграммный индекс `catalog_psi_text_trgm` по `text` (расширение `pg_trgm` из миграции
0207) — условие `text LIKE '%слово%'` идёт по индексу для слов от 3 букв. Короткие слова
(«d3», «с») проверяются перебором таблицы индекса — она маленькая (≈ 16 МБ на 30 тыс.
товаров вместе с индексом). Таблица отдельная от `catalog_product`: пересчёт не переписывает
строку товара с тяжёлым `external_data`.

**Служебные строки при поиске — подзапросом.** Обычный список исключает служебные товары
(копии вариантов, заглушки лекарств) условием на `external_data`; категории так и работают —
по частичным индексам сортировки. Поиск сортирует все совпадения, и Postgres проверял это
условие по каждой строке, детоастя мегабайтные дампы парсеров. Поэтому с `search` служебные
строки исключаются `id NOT IN (…)` по частичному индексу `catalog_product_nonpublic_id_idx`
(миграция 0217, DEVELOPMENT_RULES §2.9), а основной запрос `external_data` не трогает
(тесты `test_search_excludes_service_rows_without_external_data_condition` и EXPLAIN-тест
`test_search_queryset_can_use_nonpublic_partial_index`). Так же устроен старый публичный
`/api/catalog/products/search?q=` (`CatalogService.get_products`).

**Карточки выдачи без `external_data`.** При поиске `view=card` откладывает поле (`defer`):
иначе каждая показанная строка отдавала мегабайтный дамп. Карточка читала его в двух местах —
запасная галерея копии варианта (таких строк в выдаче нет) и ISBN/страницы книги из
`attributes`; при отложенном поле первое пропускается, второе читается только у книг.

## Язык запроса (вторая очередь)

Код — `search_language.py`, без LLM и без сети. Новых словарей брендов нет: бренды берутся из
`vocab.BRAND_RU` (туда добавлены написания для поиска: «икея», «он раннинг», «абди ибрагим»,
«пфайзер») и памяти `medicine_brand`.

**Слово запроса** (`word_condition`) ищется как часть слова в тексте, вместе с вариантами
(через `OR`, каждое — `LIKE` по триграммному индексу):

- основа без русского окончания (`stem`): «женские» → «женск», «магния» → «магни»,
  «футболки» → «футболк». Слова короче 5 букв, латиница и цифры не меняются;
- разговорные синонимы `QUERY_SYNONYMS` (ключ — слово запроса, сравнивается по основе):
  «толстовка» → «худи», «свитшот»; «кроссовки» ↔ «кеды»; «витамин» ↔ «vitamin»; «детей» → «детск»;
  «баланс» → «беланс» (в `vocab.BRAND_RU` — «нью беланс»); «таблетки» → «таблет» (в названиях
  «таблеток»), «уколы» → «инъекц», «ампул»; «холекальциферол» ↔ «колекальциферол». Значения — не
  короче 4 букв: «кед» находил «кедровую воду». Турецкие и английские названия типов в запрос не добавляются — они
  уже в тексте товара по `vocab.KINDS`;
- сленг `QUERY_REPLACEMENTS` ищется только заменой: «кроссы» → «кроссовк» (основа «кросс»
  нашла бы «Кроссворды»);
- аптечные названия (`_PHARMACY_NAMES`, с 23.11.2026): как лекарство называют в русской аптеке →
  действующее вещество: «анальгин» → «метамизол», «сумамед» → «азитромицин», «мидокалм» →
  «толперизон», «глюкофаж» → «метформин» (≈ 50 названий). Название ищется и само, и по веществу.
  Короткие (`_PHARMACY_SHORT_NAMES`: «найз», «омез», «лозап», «мезим», «ацц») — только по веществу:
  сами они — часть чужих слов. Из двух слов («л-тироксин», «тромбо асс») — в `PHRASE_SYNONYMS`.
  В словарь идут только названия, вещество которых есть в каталоге и соответствие однозначно;
  названий, которые в Турции продаются под тем же именем (аспирин, виагра, креон), в нём нет —
  они находятся по тексту товара. До словаря поиск «исправлял» такие названия в похожие чужие
  слова: «мидокалм» → MIDOLAM (мидазолам), «ортофен» → пробиотик «Ортоген», «диабетон» → «диабет»;
- фразы `PHRASE_SYNONYMS` — одним условием вместо своих слов: «капли в нос», «спрей для носа» →
  «назальн», «burun», «для нос»;
- назначение (`_PURPOSES`, с 23.11.2026): «от чего» → лечебная группа по международной
  классификации ATC, код которой уже есть в тексте лекарства (у 92 % лекарств прода): «от головной
  боли», «жаропонижающее» → `N02B`, `M01A`; «от кашля» → `R05`; «от давления» → `C02`, `C03`, `C07`–`C09`;
  «антибиотик» → `J01` (34 группы, 81 формулировка). Слова назначения ищутся как обычно **или**
  кодом группы с начала слова, поэтому находятся и товары, где они написаны («Сироп от кашля»
  у БАДов), и лекарства группы; остальные слова запроса сужают выдачу («жаропонижающее детское»,
  «мазь от боли в суставах»). «Лекарство», «средство», «препарат», «чем лечить» рядом с назначением
  необязательны. Группа — классификация препарата, а не совет сайта; успокоительных, снотворных и
  антидепрессантов (`N05`, `N06`) в словаре нет намеренно (тест). Порядок: сначала товары со словами
  запроса в названии, затем группы в порядке словаря — основная первой («от головной боли»: `N02B`,
  затем `M01A`; до 24.11.2026 выдача начиналась с трёх SULINDAC), внутри — короткие названия первыми. Пересборка индекса не нужна.
  Новое назначение — строка в `_PURPOSES`: формулировки и коды ATC, после проверки, сколько
  лекарств группы есть в каталоге;
- предлоги и союзы (`STOP_WORDS`: «в», «с», «и», «для», «от»…) необязательны: «чай с ромашкой»,
  «шампунь 2 в 1». Кроме буквы после «витамин»: «витамин с» ищет «C» целым словом;
- буква витамина в другом алфавите (`letter_twin`): «д3» → «d3», «с» → «c»;
- рядом с другими словами одна буква ищется целым словом, две («он», «d3») — с начала слова:
  «кроссовки он» находит бренд On, а не «Sezon». Запрос из одного короткого слова («a», «кр») —
  как раньше, частью слова; кроме буквы с цифрой («d3», «б6») — она и одна ищется с начала слова
  («d3» находил шлем «Mod3»).

**Если ничего не нашлось** (`search_plan`), по очереди, пока что-то не найдётся:

1. другая раскладка: «gfhfwtnfvjk» → «парацетамол», «ыфтщаш» → «sanofi»;
2. чтение латиницы кириллицей и обратно: «paracetamol» → «парацетамол», «нурофен» → «nurofen».
   Обе догадки принимаются, только если каждое слово стоит в начале слова текста
   (`_index_has_word_starts`): «халат» читался как «halat» и находил 289 ингаляторов (in**halat**ion);
3. опечатка: слово от 5 букв без совпадений (проверяются первые 6 таких слов одним запросом
   `SELECT EXISTS(…), EXISTS(…)`, исправляются не больше 3) заменяется словом каталога, отличным не
   больше чем на 1 букву (до 8 букв) или на 2 (длиннее; две правки в слове из 8 букв давали другое
   слово: «глюкофаж» → «глюконат», «диабетон» → «диабет»), считая перестановку соседних:
   «парацитамол» → «парацетамол», «ибупрафен» → «ибупрофен», «амоксицилин» → «амоксициллин».
   Кандидаты — одним запросом, до 300 текстов на слово по `word_similarity` (оператор `%>` того
   же GIN-индекса, порог 0,4 только в своей транзакции); из них берётся слово с меньшим числом правок, при равенстве —
   встречающееся чаще. «магнум» не превращается в «магний» (две правки в коротком слове).
   В слове до пяти букв первая буква не исправляется («халат» → «малат» — другое слово).
   Целого слова нет, а слово в запросе последнее — берётся слово с той же первой буквой, начало
   которого отличается от запроса на одну букву: подсказки в шапке шлют недописанный запрос
   («нурафе» → «нурофен»). Без условия на первую букву «пальто» (пальто в каталоге нет)
   дописывалось до «мальтодекстрин» — исправлено 23.11.2026.
   Дописывание работает только при наборе (подсказки). Страница результатов шлёт
   `search_source=page` — запрос отправлен целиком и не дописывается: «пальто» превращалось уже в
   «пальмовое» (прод 24.11.2026), честнее «ничего не нашлось». Запрос кандидатов —
   `WITH … AS MATERIALIZED (…) SELECT … LIMIT`: с `LIMIT` в одном запросе с `%>` планировщик
   перебирал всю таблицу (прод 23.11.2026: «метформн» 1,9 с вместо 45 мс по индексу).
4. лишнее слово (`_without_extra_words`, от 2 до 6 слов): в тексте должно быть каждое слово, и
   одно лишнее давало пустую страницу — «мазь диклофенак» (в каталоге гель), «нурофен детский»,
   «аспирин кардио». Сначала убираются слова, которых нет нигде, затем по одному — самое частое
   в каталоге (оно меньше всего говорит о товаре), пока что-нибудь не найдётся: «мазь диклофенак»
   → «диклофенак». Остаться должно слово, которое называет товар: самое редкое из оставшихся есть
   не больше чем в 200 товарах (`_PARTIAL_SPECIFIC`; «диклофенак» — 72, «нурофен» — 1), иначе
   страница остаётся пустой: «от головной боли» показывал бы головные уборы, «жаропонижающее
   детское» — всё детское. Слово из одной-двух букв не убирается («витамин к» без витамина K — пусто, а
   не все витамины). Опечатки к этому шагу уже исправлены («нурафен детский» → «нурофен»). Цена —
   один подсчёт слов по таблице индекса (`count(*) FILTER`) и не больше пяти `EXISTS`.

Запрос длиннее 100 символов обрезается по слову. План выбирается один раз на HTTP-запрос
(`request_search_plan`): вьюсеты разделов с фасетами вызывают `get_queryset` 3–4 раза.
Запрос из 30 выдуманных длинных слов — не больше 10 запросов поиска к базе (тест).
Каждая проверка — один `EXISTS` по таблице индекса; найденный текст ищется и сортируется как
обычный запрос, поэтому `COUNT` и страница — те же `LIKE` без `similarity` и регулярок.
Найденный по запросу как есть — одна проверка (`EXISTS`), остальные шаги не выполняются.
Ответ `/api/catalog/products` при исправлении и найденных товарах (проверки идут по всему
индексу, со скрытыми товарами, поэтому при `count = 0` поля нет) содержит
`search_info: {"mode": "layout" | "translit" | "typo" | "partial", "query": "<исправленный запрос>"}`;
страница `/search` пишет «Показаны результаты по запросу «…»» (для опечатки — «Точных
совпадений нет. Возможно, вы искали «…»», для лишнего слова — «По запросу целиком ничего не
нашлось. Показаны результаты по запросу «…»»). Поиск внутри разделов и `/products/search`
исправляют запрос так же, но без `search_info`.

Новые слова — в `QUERY_SYNONYMS` / `QUERY_REPLACEMENTS` / `PHRASE_SYNONYMS`, аптечные названия — в `_PHARMACY_NAMES`, бренды — в `vocab.BRAND_RU`, типы товаров — в `vocab.KINDS`.
После правки словарей текста товара (`BRAND_RU`, `KINDS`, `AUDIENCE`, памяти `medicine_brand`)
нужен `rebuild_product_search_index --apply`; словари запроса действуют сразу.

## Фильтры и сортировка страницы поиска

С 24.11.2026 на `/search` над выдачей стоят (компонент `SearchFilters.tsx`):

- **разделы** найденного плашками с количеством («Обувь 54», «Спорттовары 105») — параметр API `product_type`;
- **бренд** — список до 30 самых частых брендов найденного (`brand_id`);
- **«В наличии»** (`is_available=true`);
- **сортировка**: по точности (по умолчанию), сначала дешёвые/дорогие (`ordering=price_asc|price_desc`),
  сначала новые (`newest`). С явной сортировкой порядок по точности не применяется.

Состояние живёт в адресе (`/search?query=nike&type=shoes&brand=12&available=1&sort=price_asc`,
`readSearchFilters` / `searchPageQuery` в `lib/searchResults.js`): ссылкой можно поделиться, «назад»
возвращает прежний выбор. Страница остаётся `noindex`.

Списки разделов и брендов отдаёт `/api/catalog/products` в поле `search_facets`, когда в запросе
`search_facets=1` (страница шлёт его с первой страницей; подсказки в шапке — нет). Считаются по
**всему** найденному, без выбранных фильтров (`ProductViewSet._search_facets`): после выбора раздела
остальные плашки не пропадают. Это два `GROUP BY` по найденным строкам (`product_type`, `brand_id`),
`external_data` не читается.

С фильтром или сортировкой услуги в выдачу не подмешиваются (у них нет разделов и брендов), запрос в
учёт не пишется и событие `search` в аналитику повторно не уходит. Фильтра по цене нет: цены в
каталоге в разных валютах, диапазон в валюте покупателя — отдельная работа.

## Учёт запросов

С 24.11.2026 сайт записывает, что ищут на странице `/search`: таблица `catalog_searchquerystat`
(`models_search.SearchQueryStat`), одна строка на запрос и язык — сколько раз искали, сколько товаров
нашлось при последнем поиске, как запрос понят (`mode` плана и исправленный запрос), первый и
последний раз. Пользователь и адрес не пишутся — только нормализованный текст запроса (до 120 символов).

- Пишет `search_stats.record_search` из `ProductViewSet.list`, только когда в запросе
  `search_source=page`, это первая страница и нет фильтров (`product_type`, `brand_id`,
  `is_available`): параметр шлёт `searchProductParams` страницы `/search`.
  Подсказки в шапке (запрос на каждую букву) и «Показать ещё» в учёт не попадают. Поиск внутри
  разделов и услуги не считаются: «Найдено товаров» — число из `/api/catalog/products`.
- Одна-две короткие записи на поиск (`UPDATE … searches + 1`, для нового запроса — `INSERT`);
  ошибка записи уходит в лог и поиск не ломает (тест).
- Админка: «Источники и проверки» → **«Поисковые запросы»** (только чтение). По умолчанию —
  самые частые сверху; фильтр «что нашлось»: «Ничего не нашлось», «Мало (1–5)», «Запрос исправлен
  поиском»; ссылка «открыть поиск» показывает выдачу как у покупателя. По списку «Ничего не
  нашлось» пополняются словари (`_PHARMACY_NAMES`, `_PURPOSES`, `QUERY_SYNONYMS`, `vocab.BRAND_RU`).
- Кликов по товарам учёт не ведёт; таблица не чистится сама (строка на уникальный запрос).

## Когда текст пересчитывается

- После сохранения `Product` (в том числе смены раздела `category` и пола `gender`), `ProductTranslation`, доменной записи, её перевода и вариантов
  (`variants`/`book_variants`: SKU, штрихкод, GTIN) — `post_save`, после коммита транзакции
  (`transaction.on_commit(..., robust=True)`: ошибка пересчёта уходит в лог и не ломает
  `save()` парсера или админки). Новая доменная запись связывается с `Product` через
  `update()`, поэтому `_sync_to_base_product` сам ставит пересчёт после связи.
- `save(update_fields=[…])` без полей, от которых зависит текст (наличие из ночной сверки,
  цена), пересчёт не запускает. Строка с тем же текстом не переписывается.
- **Не** пересчитывается при `QuerySet.update()` / `bulk_create` / `bulk_update` и при
  удалении варианта или перевода — сигналы такие правки не видят. Это переименование бренда
  (в том числе **правка названия бренда или его перевода в админке** — сохраняется бренд, а не
  товары), `assign_manufacturer_brands`, разнос правки МНН (`propagate_inn_translations`),
  `move_essential_oils_from_supplements`, `move_supplements_to_medicines`, переименование раздела, новые слова в `vocab.BRAND_RU`,
  `vocab.KINDS` и памяти `medicine_brand`. После них — `rebuild_product_search_index --apply`.
  Товар, у которого строки индекса нет совсем (создан `bulk_create`), в поиск не попадает
  до пересчёта.

## Команда `rebuild_product_search_index`

```bash
manage.py rebuild_product_search_index                  # показ: сколько строк новых/изменится, примеры
manage.py rebuild_product_search_index --apply          # записать
manage.py rebuild_product_search_index --ids 12,345 --apply  # только при заполненном индексе
manage.py rebuild_product_search_index --clear --apply  # откат: очистить, поиск снова по названию
```

Сеть, R2 и OpenAI не нужны. Первое заполнение (таблица пуста) — одной транзакцией: новый
поиск включается сразу для всех товаров. Повторные прогоны — пачками по `--batch-size` (500).
`--ids` при пустом индексе запрещён: строка одного товара включила бы новый поиск для всего сайта.

## Выкатка и откат

Пока таблица пуста, поиск и сигналы работают **по-старому** (`name__icontains`, сначала новые):
`search_index_ready()` — один запрос `EXISTS`. Поэтому порядок такой:

1. Обычный релиз: миграция `0237_product_search_index` только создаёт пустую таблицу и индекс
   (без данных, мгновенно).
2. Сразу после релиза на проде:
   ```bash
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index
   docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index --apply
   ```
   (как запускать команды на проде — [MANAGEMENT_COMMANDS.md](MANAGEMENT_COMMANDS.md)).
   Таблица индекса — производные данные, `pg_dump` перед `--apply` не нужен.
   На модельном каталоге 30 тыс. товаров первый шаг — ≈ 11 с, `--apply` — ≈ 15 с, процесс ≈ 300 МБ памяти.
3. **Второй прогон `--apply`** сразу после первого. Пока шло первое заполнение, сигналы видели
   пустую таблицу и ничего не писали, а заполнение читало товары до правок парсеров: второй
   прогон дописывает только изменившиеся строки (в отчёте «изменится: N», обычно единицы).
4. Смоук: `https://mudaroba.com/search?query=Abdi%20Ibrahim`, `…?query=омега 3`,
   `…/en/search?query=paracetamol` — товары есть; повторить аудит (`probe.py` из заметок
   аудита, 1 запрос в секунду).

Откат без релиза: `rebuild_product_search_index --clear --apply` — таблица пустеет, поиск
сразу возвращается к поиску по названию. Бэкап не нужен: таблица целиком собирается из
товаров и в `REQUIRED_TABLES` бэкапа базы не входит.

**Откат релиза (`rollback.sh` на предыдущий тег) — только после `--clear --apply`.** Внешний
ключ `catalog_productsearchindex.product_id` создан Django без `ON DELETE CASCADE` в базе:
каскад делает код. Старый код о таблице не знает, и при заполненной таблице удаление товара
(ночная очистка, админка) упадёт с `IntegrityError`. Пустая таблица старому коду не мешает.

**Вторая очередь (язык запроса)** — без миграций. После релиза:

```bash
docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index          # показ
docker exec mudaroba-backend-1 poetry run python manage.py rebuild_product_search_index --apply  # записать
```

До `--apply` уже работают окончания, синонимы запроса, раскладка, чтение латиницы и опечатки;
бренды и лекарства кириллицей, тип, пол и раздел из текста товара — после. На модельном
каталоге 30 тыс. товаров меняется ≈ 19 тыс. строк, `--apply` — ≈ 30 с. Откат кода на #322
безопасен без очистки: лишние слова в тексте старому коду не мешают; после отката —
`rebuild_product_search_index --apply`, чтобы текст снова собрался старым кодом.

Доменная запись без `base_product` в индекс не попадает (и раньше не попадала в общий поиск);
поиск внутри её раздела её тоже не найдёт. Сколько таких на проде (только чтение, локально
данных прода нет), например для лекарств — `SELECT count(*) FROM catalog_medicineproduct
WHERE base_product_id IS NULL;`, так же для остальных `catalog_*product`.

**Третья очередь (23.11.2026: аптечные названия, лишнее слово, быстрые опечатки)** — без миграций
и без пересборки индекса: меняется только разбор запроса и порядок выдачи, текст товаров тот же.
Замер на проде до правки (210 запросов) — `reports/search-check-2026-11-23.md`.

## Что ещё не сделано

Обычное слово, совпавшее с началом названия лекарства кириллицей: «лампа» → LAMPRENE («лампрене»),
«ковер» → COVERAM («коверам») и Discovery («дискавери») — ламп и ковров в каталоге нет, а чтение
латиницы лежит в том же тексте, что и названия. Лечится отдельным полем для чтений (ищутся только
целым словом или набранным началом) — нужна миграция и пересборка индекса; решать по журналу
запросов. Названия, вещества которых в каталоге нет (но-шпа, супрастин, смекта), честно дают пустую
страницу. Назначение вне лекарств («крем для лица», «от перхоти») и не из словаря `_PURPOSES` —
тоже. Поисковый трафик такие запросы не приводят (страница `/search` — `noindex`): для него нужны
открытые страницы-подборки по назначению (`/categories/<раздел>/<подборка>`).

Умные подсказки (блоки «Бренды», «Категории», «Действующее вещество» → `/drugs/<slug>`) и
один запрос подсказок вместо двух — пункт 9 (P1) отчёта; поиск по смыслу — P2.
