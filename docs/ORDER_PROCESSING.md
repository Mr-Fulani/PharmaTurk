# Обработка заявок в админке

Состояние на 26.11.2026 (шаги обработки и причина «Не состоялась» — с 20.11; заявки «Найдём товар» в общем списке — с 22.11; кнопки под уведомлением в Telegram и готовые сообщения клиенту — с 26.11). Код — `backend/apps/orders/processing.py`, `OrderAdmin` в
`backend/apps/orders/admin.py`, модели `Order.processing_status`, `Order.processing_fail_reason`, `Order.assigned_to`,
`OrderProcessingEvent`; тесты — `backend/apps/orders/tests/test_order_processing.py`.

Оплата на сайте выключена, заказ — это заявка менеджеру. Чтобы через неделю было видно,
на какие заявки уже ответили и кто, у заказа есть отметка «Обработка» и ответственный.

## Отметка «Обработка» и «Статус для клиента» — разные вещи

| | «Обработка» | «Статус для клиента» |
| --- | --- | --- |
| Для кого | менеджеры | клиент |
| Видит клиент | нет | да, в профиле |
| Сообщение клиенту при смене | нет | да, Telegram/email (`notify_order_status_changed`) |

Значения «Обработки» — ход заявки (набор утверждён владельцем 20.11.2026, чтобы со временем
видеть, на каком шаге теряются заявки):

| Значение | В базе | Когда ставить |
| --- | --- | --- |
| Новая | `new` | заявка пришла, никто не смотрел (у каждой новой заявки) |
| В работе | `in_progress` | менеджер взял заявку и уточняет наличие, цену, доставку |
| Написали клиенту — ждём ответа | `waiting_client` | клиенту написали, ждём его ответа |
| Назвали цену — ждём решения | `price_sent` | клиент знает цену и сроки, думает |
| Клиент согласен — ждём оплату | `agreed` | договорились, ждём деньги |
| Оплачено — закупаем | `paid` | деньги получены, товар закупается |
| Отправлено | `shipped` | посылка ушла клиенту |
| Завершена | `done` | клиент получил заказ или вопрос закрыт |
| Не состоялась | `cancelled` | заявка не дошла до конца — рядом выбирается причина |

Причина «Почему не состоялась» (`Order.processing_fail_reason`) — отдельное поле, не статус:
«Клиент не ответил» (`no_reply`), «Дорого» (`expensive`), «Долго» (`slow`), «Нет в наличии»
(`out_of_stock`), «Не нашли товар» (`not_found`, с 22.11.2026 — для заявок «Найти товар»), «Не можем доставить (страна, ограничение на ввоз, рецепт)» (`cannot_deliver`),
«Передумал» (`changed_mind`), «Спам или тест» (`spam`); пусто — причина не указана. Причина
хранится только у отметки «Не состоялась»: при любой другой отметке она очищается
(`Order.save`, действия списка). Поле стоит на странице заявки рядом с «Обработкой» всегда
(скриптов в админке нет, скрывать поле нечем) — выбранная при другой отметке причина не сохранится.

Это внутренние отметки. «Ждём оплату» и «Оплачено» не значат оплату на сайте: клиент этих слов
не видит, сообщений не получает, `status` и `payment_status` заказа не меняются, в API заказа
(`OrderSerializer`) и в письма эти поля не попадают (тест
`test_processing_is_not_in_public_order_api`).

До 20.11.2026 значений было пять; `waiting_client` назывался «Ответили клиенту — ждём», `done` —
«Обработана», `cancelled` — «Отменена». Значения в базе те же, у старых заявок поменялись
только подписи, причина у них пустая («не указана»).

## Заявки «Найдём товар» — в том же списке (с 22.11.2026)

Раньше заявка из формы «Найдём товар по ссылке или фото» лежала только в разделе «🔎 Заявки на
поиск товара» со своими четырьмя статусами, и найденный товар в «Заказы» не попадал — смотреть
приходилось в двух местах. Теперь форма сразу создаёт заявку в «🛒 Заказы — Заказы»
(`create_order_for_sourcing_request`, `apps/orders/sourcing.py`): `Order.kind = sourcing`
(«🔎 Найти товар»; у заявок из Списка — `cart`, «Из Списка») и одна позиция без товара каталога.
Ссылка, фото и комментарий клиента по-прежнему хранятся в `SourcingRequest`, пара связана полем
`SourcingRequest.order`.

- **Список**: колонка «Тип» и фильтр «Тип заявки» («Из Списка» / «🔎 Найти товар»). В «Составе» —
  слова клиента (до 120 знаков), без комментария — «Товар по ссылке» / «Товар по фото».
- **Страница заявки**: блок «Что ищет клиент» — ссылка, фото, комментарий, количество. Шаги
  «Обработки», ответственный, история, метка «висит» — как у любой заявки.
- **Нашли товар**: в позиции менеджер меняет «Название товара» на настоящее и вписывает «Цену»
  (у заявок «Найти товар» она редактируется; у заявок из Списка — нет), в блоке «Amounts»
  выбирает валюту. После сохранения сумма позиции и «Итого» считаются сами
  (`OrderAdmin.save_related`). Дальше — обычные шаги: назвали цену, клиент согласен и т. д.
- **Не нашли**: «Обработка» → «Не состоялась», причина «Не нашли товар».
- **Покупатель** ничего нового не видит и не получает: таких заявок нет в его профиле
  (`OrderViewSet` и счётчики профиля берут только `kind = cart`), смена «Статуса для клиента»
  у заявки «Найти товар» сообщений не шлёт, чек не создаётся. Форма на сайте и события
  аналитики не менялись.
- **Телефон** у такой заявки может быть пустым (в форме он необязателен, если клиент оставил
  ник) — страница заявки сохраняется и без него.
- **Раздел «🔎 Заявки на поиск товара»** остался: в нём исходные данные формы и старые заявки.
  Колонка «Где ведётся» показывает ссылку «Заказы: №…» и текущую отметку обработки; у заявок,
  пришедших до 22.11.2026, пары нет — там прежний статус, и в «Заказах» (в том числе по клику
  на плитку «Найдём товар») их не видно, пока не перенесены. Перенос старых заявок — вызов
  `create_order_for_sourcing_request` для каждой (на проде только по слову владельца).
- Миграция `orders/0024` — только схема. Тесты — `tests/test_sourcing_in_orders.py`.

## Как работать (админка → «🛒 Заказы — Заказы»)

- Список сверху вниз по ходу заявки: «Новая», «В работе», «Написали клиенту…», «Назвали цену…»,
  «Клиент согласен…», «Оплачено…», «Отправлено», потом закрытые («Завершена», «Не состоялась»);
  внутри — сначала свежие. Клик по заголовку колонки меняет сортировку.
- Колонки «Обработка» (цветная метка) и «Ответственный» (по имени из профиля, иначе email).
  Клиентское поле подписано «Статус для клиента», чтобы не путать с «Обработкой».
- Фильтры справа: «обработка» (каждая отметка плюс «Не закрытые» — все шаги до «Завершена» и
  «Не состоялась», не включая их; адрес `?processing=open`), «почему не состоялась» (каждая
  причина и «Причина не указана»; `?reason=`) и «ответственный» («Мои», «Без ответственного»,
  по имени).
- **Статистика**: рядом с каждым пунктом фильтра стоит число заявок — «Назвали цену — ждём
  решения (12)», «Дорого (5)» (`show_facets`). Числа считаются с учётом остальных выбранных
  фильтров: выберите «Дата создания → Этот месяц» — и получите разбивку по отметкам и причинам
  за месяц. Отдельного экрана отчёта нет.
- Действия над отмеченными галочкой заявками: «Взять в работу (я ответственный)» и «Отметить: …»
  для каждого следующего шага — написали клиенту, назвали цену, клиент согласен, оплачено,
  отправлено, завершена. «Не состоялась» с причиной и смена ответственного — на странице
  заявки, блок «Обработка заявки».
- Если заявку двигают дальше «Новой», а ответственного нет, им становится тот, кто двигает.
  «Взять в работу» всегда делает ответственным нажавшего, даже если заявку вёл другой.
- «История обработки» на странице заявки: дата, кто менял, что было → что стало, причина
  («Назвали цену — ждём решения → Не состоялась; причина: Дорого»; смена одной причины тоже
  записывается), смена ответственного. Пишется при каждом изменении из списка и со страницы, и при
  создании заказа в админке не «Новым»; повтор того же значения не пишется.
- Страница заявки сохраняет «Обработку», причину и «Ответственного», только если их меняли на ней:
  если страница была открыта, пока коллега нажал «Взять в работу» в списке, сохранение
  комментария или клиентского статуса его отметку не откатит.
- Ответственным можно выбрать сотрудника (доступ в админку). Если у ответственного доступ
  сняли, он остаётся в списке у своих заявок, чтобы их можно было сохранить.
- Действия списком доступны только с правом на изменение заказов.

## Кнопки под уведомлением в Telegram (с 26.11.2026)

Чтобы не ходить в админку за каждой отметкой, под уведомлением о заявке в чате заявок
(`TELEGRAM_ORDERS_CHAT_ID`) стоят кнопки. Код — `backend/apps/orders/telegram_buttons.py`,
тесты — `tests/test_telegram_buttons.py`. Решения владельца (26.11.2026): кнопки — в чате
заявок, нажимать может любой его участник, «Статус для клиента» кнопками не меняется.

- **Что двигают кнопки**: только отметку «Обработка» — тем же путём, что действия списка в
  админке (`processing.change_processing`): та же история, то же правило про ответственного.
  Покупателю ничего не уходит, `Order.status` не меняется.
- **Какие кнопки**: ближайшие шаги от текущей отметки, не все девять.

  | Отметка сейчас | Кнопки шагов |
  | --- | --- |
  | Новая | Взять в работу · Написали клиенту · Назвали цену |
  | В работе | Написали клиенту · Назвали цену · Клиент согласен |
  | Написали клиенту | Назвали цену · Клиент согласен |
  | Назвали цену | Клиент согласен · Оплачено |
  | Клиент согласен | Оплачено |
  | Оплачено | Отправлено |
  | Отправлено | Завершена |
  | Завершена | только «Вернуть: Отправлено» |
  | Не состоялась | только «Вернуть в работу» |

  Кроме того: «❌ Не состоялась» (у всех, кроме закрытых) и «↩️ Вернуть: …» — на шаг назад.
- **«Не состоялась»** открывает кнопки причин (те же, что `Order.FailReason`) и «Назад».
  Отметка меняется только после выбора причины.
- **После нажатия** в сообщение дописывается строка «📌 Статус: отметка — кто нажал, дата и
  время» (при следующем нажатии строка заменяется), кнопки перестраиваются. В «Истории
  обработки» на странице заявки запись выглядит как «Имя (@ник) (из Telegram)» — поле
  `OrderProcessingEvent.actor_label` (миграция `orders/0025`, только схема).
- **Ответственный**: если нажавший привязал этот Telegram к своему аккаунту сотрудника на
  сайте, он записывается в историю как сотрудник и становится ответственным по тем же
  правилам, что в админке. Если не привязал — отметка меняется, ответственный не назначается.
- **Кнопки-ссылки**: «Открыть в админке» (эта заявка) и «Написать в Telegram / WhatsApp» —
  те же ссылки с черновиком, что в тексте уведомления; если контакт не годится для ссылки,
  кнопки нет.
- **Доступ**: участник чата заявок (`getChatMember`, ответ «да» помнится 5 минут). Остальным —
  всплывающее «Нет доступа», ничего не меняется.
- **Старые и повторные нажатия**: в кнопке записана отметка, при которой её показали. Если
  отметку уже сменили (коллега или админка), нажатие ничего не меняет: всплывает «Статус уже
  изменён», сообщение получает нынешние статус и кнопки. Telegram получает ответ на каждое
  нажатие (`answerCallbackQuery`), в том числе при сбое.
- **Где стоят кнопки**: под последним сообщением уведомления (длинное уходит несколькими).
  У текста правится текст (`editMessageText`), у чека или фото с подписью — подпись
  (`editMessageCaption`); разметка возвращается из самого сообщения. Если с новой строкой
  текст не помещается в предел Telegram, меняются только кнопки. Если Telegram не принял
  сообщение с кнопками (ответ 400), оно уходит повторно без кнопок — уведомление важнее.
- **Заявки «Найдём товар»**: те же кнопки по парной заявке в «Заказах» (причина «Не нашли
  товар» — в списке причин). У старых заявок без пары кнопок нет.
- **Уведомления, отправленные до выкатки**, остаются без кнопок.
- **Команда `/orders`** (или `/заявки`) в личном чате с ботом — чтобы не листать ленту чата
  заявок. Бот присылает сводку: по кнопке на каждую отметку, на которой есть незакрытые
  заявки, с числом — «Новая (4)», «Оплачено — закупаем (3)». Нажатие присылает заявки этой
  отметки (сначала давние, до 20; остальные — по кнопке «Эти заявки в админке»): номер,
  клиент, дата, позиции с количеством, сумма, строка «Статус» и те же кнопки шагов, что под
  уведомлением. «Оплачено — закупаем» — готовый список закупки. «К сводке» присылает
  сводку заново. Только участникам чата заявок; остальным — «Нет доступа».
- **Подсказка в меню бота**: общее меню команд видят и покупатели, поэтому `/orders` в него
  не добавлена. Участнику чата заявок бот включает личное меню (`setMyCommands` с областью
  «этот чат») — после первого нажатия кнопки под заявкой или первой команды `/orders`; общие
  команды бота в личном меню сохраняются. Обновляется не чаще раза в сутки. Если человек
  ещё ни разу не писал боту, Telegram меню не поставит — оно появится после первого сообщения.
- **Вебхук** тот же (`/api/users/telegram/webhook/`, `apps/users/telegram_auth.py`):
  нажатия с данными `o:…` (кнопки заявки) и `ol:…` (сводка) уходят в
  `telegram_buttons.handle_callback`. Перерегистрировать
  вебхук не нужно: он поставлен без `allowed_updates`, нажатия и сообщения приходят и так.
- **Что нужно от Telegram**: бот должен быть в чате заявок (в канале — администратором,
  иначе он не увидит участников). В группе нажимают все участники; в канале — подписчики.
- **Как выключить**: отдельного выключателя нет. Кнопками можно не пользоваться — админка
  работает как раньше; убрать совсем — откатить выпуск.

## Готовые сообщения клиенту по кнопке (с 26.11.2026)

Под заявкой в чате заявок и в карточках из `/orders` стоит кнопка «📝 Сообщение клиенту».
Код — `backend/apps/orders/client_messages.py` (сборка текста) и `telegram_buttons.py`
(кнопки), модель `ClientMessageTemplate`, тесты — `tests/test_client_messages.py`.

- **Бот клиенту ничего не отправляет.** Он присылает готовый текст в тот же чат, ответом на
  сообщение с заявкой; отправляет менеджер сам.
- **Меню**: «Как проходит доставка — авиа», «Как проходит доставка — наземная», «Заказ
  отправлен», «Просьба об отзыве», «Назад».
- **Что приходит**: заголовок и текст блоком — нажатие на блок копирует весь текст без
  разметки. Под ним кнопки «💬 Открыть чат в Telegram / WhatsApp» (те же правила контакта,
  что у «Написать»). Короткий текст сразу набран в чате; если ссылка с текстом длиннее 2000
  знаков (сообщения о доставке) или Telegram её не принял — открывается просто чат, текст
  вставляется вручную. Без годного контакта кнопок чата нет.
- **Быстрый путь**: при отметке «Отправлено» среди кнопок есть «✉️ Сообщение: заказ
  отправлен», при «Завершена» — «⭐ Попросить отзыв».
- **Отметку «Обработка» сообщение не меняет** и доступно даже со старого уведомления.
  Доступ — участники чата заявок.
- **Тексты** — в админке: «Заказы и корзины» → «🛒 Заказы — Готовые сообщения клиенту».
  Четыре записи, добавлять и удалять нельзя; поля «Текст по-русски» и «Текст по-английски»
  (для заявок с английской версии сайта; пусто — берётся русский). Сроки доставки — часть
  текста. Начальные тексты записывает миграция `orders/0026` (только база, без сети);
  русские утверждены владельцем 26.11.2026.
- **Подстановки** (пишутся в фигурных скобках, пробел или подчёркивание — всё равно):

  | Подстановка | Что подставится |
  | --- | --- |
  | `{имя}` | имя клиента; если его нет, «, {имя}» убирается — «Здравствуйте!» |
  | `{номер}` | номер заявки |
  | `{товары}` | блок «Ваш заказ:» и строка на товар «• название × количество» (до 20 строк); товар без цены — с пометкой «цена по запросу»; у заявки «Найти товар» блок пропускается |
  | `{сумма товаров}` | `Order.subtotal_amount` в валюте заявки; ноль — «[впишите сумму]» |
  | `{сумма доставки}` | `Order.shipping_amount`; ноль — «[впишите сумму доставки]» |
  | `{итого}` | `Order.total_amount`; с пометкой «без доставки» и/или «без позиций с ценой по запросу», когда они в сумму не вошли |
  | `{ссылка на отзывы}` | личная ссылка клиента `/testimonials?action=add&k=<ключ>` (для английских заявок — `/en/…`); ключ случайный, хранится в заявке (`Order.review_token`), заводится при первой сборке сообщения с этой подстановкой |

  Незнакомая подстановка остаётся в тексте как есть и ничего не ломает.
- **Отзывы**: по ссылке открывается форма отзыва, вход в аккаунт не нужен; отзыв получает
  отметку «Покупатель» и появляется на сайте после проверки владельцем —
  [GUEST_TESTIMONIALS.md](GUEST_TESTIMONIALS.md).
- **Как выключить**: отдельного выключателя нет; кнопкой можно не пользоваться.

## Имя, фамилия и адрес покупателя (с 25.11.2026)

Покупатель в форме заявки обязан указать имя, фамилию и телефон — на них оформляется
отправление. В заявке они стоят в поле «Имя получателя» одной строкой «Имя Фамилия». Адрес
доставки покупатель заполняет по желанию; если заполнил — он есть в поле «Адрес доставки
(текст)» и в уведомлении Telegram (раздел «📍 Адрес доставки»), если нет — в уведомлении
написано «не указан», адрес уточняет менеджер. Подробности — `notifications-and-receipts.md`.

## Удобства списка и страницы заявки

- **«Состав»** (колонка списка): до трёх позиций — миниатюра, короткое название и «×количество»,
  остальные — «+N». Позиции с товаром и фото подгружаются разом на всю страницу (их же берёт
  колонка «Ввоз»): число запросов не зависит от числа строк (тест
  `test_order_list_queries_do_not_grow_with_rows`).
- **«⏰ висит …»** под меткой «Обработка»: «Новая» дольше 24 часов с создания или шаг, на котором
  заявка ждёт, дольше 3 дней без изменений (по «Дате обновления» заказа — её сдвигает любое
  сохранение заявки): «В работе», «Написали клиенту…», «Назвали цену…», «Клиент согласен…»,
  «Оплачено — закупаем» (`STALE_WITHOUT_CHANGES`). «Отправлено» не подсвечивается: доставка
  идёт до двух недель. Пороги — `NEW_STALE_AFTER` и `IN_PROGRESS_STALE_AFTER` в `admin.py`
  (новых настроек нет, для шагов ожидания взят порог «В работе»); выбраны по умолчанию,
  владелец числа не называл. До 20.11.2026 «Написали клиенту — ждём ответа» не подсвечивалась:
  после выкатки метка появится у старых заявок, которые ждут ответа дольше 3 дней. Сразу после выкатки метка появится у многих заявок:
  миграция 0021 разметила старые «В работе», не меняя дату обновления.
- **Связь с клиентом**: в списке — колонка «Связь» (TG · WA · ☎ · ✉), на странице заявки в
  блоке «Contact» — «Связаться» (Telegram, WhatsApp, Позвонить, Email). Канал, выбранный
  клиентом, — жирным. Telegram и WhatsApp открываются в новой вкладке; звонок и email
  открывают приложение телефона/почты, поэтому без новой вкладки.
  - **Черновик сообщения** (с 20.11.2026): ссылки Telegram, WhatsApp и Email открывают чат или
    письмо с уже набранным текстом — приветствие по имени, номер заявки, первые 5 позиций
    (названия до 50 знаков, дальше «и ещё N» / «and N more»). Отправляет менеджер сам,
    автоматически ничего не уходит. Текст строит одна функция `contact_message`, ссылки —
    `contact_links` (`apps/orders/contacts.py`); те же ссылки стоят в уведомлении Telegram
    (`docs/notifications-and-receipts.md`). Те же ссылки («Связаться») есть на странице заявки
    «Найдём товар».
  - **Тексты черновика** утверждены владельцем 20.11.2026 (`MESSAGE_TEXTS`), менять только по
    его слову:
    - русский: «Здравствуйте, Иван! Это Mudaroba. Спасибо за заявку №REQ-20261120-0007:
      Парацетамол 500 мг. Пишем, чтобы уточнить детали и рассказать о стоимости, сроках и
      порядке доставки. Когда вам удобно это обсудить?» Без имени — «Здравствуйте!», без
      списка — «Спасибо за заявку №….», для «Найдём товар» — «Спасибо за заявку на поиск
      товара №….». Тема письма: «Заявка №… — Mudaroba» / «Заявка на поиск товара №… — Mudaroba»;
    - английский: «Hello Ivan! This is Mudaroba. Thank you for your request No. REQ-20261120-0007:
      Parol 500 mg. We are writing to confirm the details and tell you about the price, delivery
      time and how delivery works. When would be a good time to talk?» Без имени — «Hello!», для
      «Найдём товар» — «Thank you for your product search request No. ….». Тема: «Your request
      No. … — Mudaroba» / «Your product search request No. … — Mudaroba». Названия позиций —
      английский перевод товара (`ProductTranslation`), если он есть, иначе как в заявке
      (в уведомлении — `order_item_names`, один запрос на заявку).
  - **Язык черновика** — язык, на котором покупатель оформил заявку; английский только при
    `en`, во всех остальных случаях русский (`message_locale`). Откуда берётся:
    - заявка «Найдём товар» — поле `SourcingRequest.locale` (в Telegram и в старом разделе);
      у её пары в «Заказах» — `Order.locale`, скопированный оттуда же. Номер в черновике —
      номер заявки из «Заказов» (у старых заявок без пары — номер заявки на поиск);
    - заявка — поле `Order.locale` («Язык оформления», миграция 0022, только схема): checkout
      записывает туда тот же язык (`ru`/`en`), что передаёт задаче уведомления; поле видно в
      карточке заявки в блоке «Contact». У заявок, оформленных до этого поля, оно пустое —
      черновик русский. `User.language` для этого не используется: сайт его не обновляет;
    - уведомление Telegram о заявке — тот же язык оформления из параметра
      `notify_new_order_telegram(locale=…)`.
    В списке заявок переводы названий подгружаются одним запросом на страницу
    (`product__translations` в `OrderAdmin.get_queryset`).
  - Telegram — только если клиент выбрал Telegram: `t.me/<ник>?text=…` без @, если ник похож
    на ник; без ника (или если вместо ника вписан номер) — `t.me/+<номер>?text=…` по номеру с
    понятным кодом страны (по номеру Telegram может не подставить текст).
  - WhatsApp — `wa.me/<цифры с кодом страны>?text=…`: номер из «Юзернейма», если клиент выбрал
    WhatsApp и указал там номер, иначе из «Телефона». Правило номера (`whatsapp_number`
    в `apps/orders/contacts.py`): «+…» — как есть; 11 цифр с 7 — как есть; 10 цифр
    с 9 — российский без кода, добавляется 7; 11 цифр с 8 — 8 меняется на 7. Иначе
    (например «0532…») код страны неясен, и кнопки WhatsApp нет.
  - Позвонить — `tel:`: номер с понятным кодом в виде «+7…», иначе как ввёл клиент.
  - Email — `mailto:…?subject=…&body=…`; служебный адрес `…@mudaroba.local` не показывается.
- **«Другие заявки клиента»** на странице заявки: «У этого клиента ещё N заявок» — ссылка в
  новой вкладке на список с фильтром «клиент» (`?client_of=<id заявки>`). Совпадением считается
  тот же пользователь, или те же последние 10 цифр телефона (так «+7 912…», «8 912…» и «912…» —
  один номер), или тот же ник без регистра и @ в том же канале (Telegram с Telegram, WhatsApp
  с WhatsApp), или тот же email (без регистра). Номера-заглушки (меньше трёх разных цифр,
  например «0000000000») для совпадения не используются. Текущая заявка не считается и в
  списке не показывается.

## Позиции заказа: фото и ссылки

На странице заявки (блок «Позиции заказа») и в разделе «Позиции заказа» у каждой позиции:

- «Фото» — главное фото товара, если его нет — главное или первое из галереи; клик открывает
  фото целиком.
- «Ссылки» — кнопки одного вида с карточкой товара ([ADMIN_HOME_TILES.md](ADMIN_HOME_TILES.md)),
  все в новой вкладке:
  - «На сайте» — карточка на mudaroba.com, адрес строится как на сайте
    (`build_canonical_path`, зеркало `buildProductUrl` фронта). Для заказанной расцветки
    (теневой товар со slug «<тип>-<вариант>») — по slug варианта из `external_data`, как
    ссылка из корзины; у украшений slug теневого товара уже родительский. Скрытый товар
    откроется с 404.
  - «У продавца» — страница у донора: ссылка, сохранённая при оформлении
    (`OrderItem.source_url`), у старых позиций без неё — текущая ссылка товара
    (`Product.external_url`). Показываются только адреса http(s).
  - «Карточка в админке» — страница товара в его разделе админки: у лекарства — страница лекарства
    (там панель «Наличие и цена: проверка по источникам» с кнопкой «Проверить сейчас»,
    `docs/DRUG_CHECK.md`), у БАДа — страница БАДа, и так для всех разделов каталога.
    Если записи в разделе нет (например, заказана отдельная расцветка), открывается общая
    карточка товара. Правило одно на всю админку заказов — `product_admin_url`
    в `backend/apps/catalog/admin_links.py`.
- Если товар удалён или у него нет фото, адреса или источника — прочерк. Фото берётся только
  из общего товара: у лекарства без фото в общем товаре будет прочерк, даже если фото есть
  в записи лекарства.

Код — `OrderItemLinksMixin` в `backend/apps/orders/admin.py`; товар и фото галереи
загружаются одним запросом на все позиции, записи разделов — по одному запросу на раздел
каталога, а не на позицию (тест `test_order_item_links.py`).

## Выкатка

Миграции `orders/0020_order_processing` (поля и журнал) и `orders/0021_mark_existing_orders_processing`
(разметка) без сети: только база. Разметка вынесена в отдельную миграцию: в одной транзакции
с 0020 UPDATE заказов перед созданием индекса падал на проде («pending trigger events»).
Существующие заявки размечаются так: клиентский статус «Отменен» → «Отменена»; «Отправлен»/«Доставлен» →
«Обработана»; «Ожидает оплаты»/«Оплачен»/«В обработке» → «В работе» (без ответственного);
созданные больше 7 дней назад → «Обработана»; остальные остаются «Новая».
Истории у них нет — она начинается с первого изменения после выкатки.

Миграция `orders/0023_order_processing_stages` (20.11.2026) — только схема, без сети и без
правки строк: поле причины у заказа, поля «была/стала причина» у журнала, новые подписи и
значения в списке выбора. Значения в базе не меняются.
