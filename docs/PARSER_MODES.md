# Три режима парсеров: товар, категория, весь сайт

У каждого рабочего парсера три режима запуска. Akakce сюда не входит: это не
каталог, а проверка наличия БАДов при открытии карточки.

| Режим | Как запустить в админке | Что произойдёт |
|---|---|---|
| **1. Один товар** | «Задачи парсинга сайтов» → «Добавить». Тип «Товар или категория по ссылке», в «Ссылка» — адрес карточки товара | Спарсится и сохранится один товар (у одежды — со всеми цветами) |
| **2. Вся категория** | Тот же тип, в «Ссылка» — адрес страницы категории. «Макс. товаров» — больше, чем товаров в категории (например, 100 000) | Все страницы категории пройдут цепочкой запусков до конца или до «Макс. товаров». Пауза и «Продолжить» работают. Исключение — Bershka, Pull&Bear, Massimo Dutti: категория идёт одним запуском без чанков, не больше «Страниц за один запуск» × 12 товаров (ставить ≥ числа товаров / 12); «Продолжить» после паузы начинает её сначала, сохранённые товары идут как «пропущено». Ссылку раздела у них вставлять целиком, вместе с `?celement=…` (без него — понятная ошибка, статус парсера не меняется); раздел-витрина без своих товаров завершается с причиной «выберите подраздел» |
| **3. Весь сайт** | Тип «Весь сайт (все категории)», ссылка не нужна | Парсер сам находит категории сайта и обходит их по очереди, каждую — до конца (у Bershka, Pull&Bear, Massimo Dutti — в пределах «Страниц за один запуск» × 12). Прогресс: «Весь сайт: прогресс» в задаче |
| **Только изменения (IlacFiyati)** | Тип «Только изменения (IlacFiyati)», ссылка не нужна; «Макс. товаров» — 100 000 | Открываются только новые карточки и те, чья строка в листинге изменилась; пропавшие снимаются с продажи. Подробно — [ниже](#только-изменения-ilacfiyati) |
| **Instagram: пост** | «Задачи Instagram» → «Ссылка на пост» | Один пост |
| **Instagram: весь профиль** | «Задачи Instagram» → username, ссылку оставить пустой, «Максимум постов» не меньше числа постов профиля (до 5000) | Все посты профиля. Нужен вход: cookie `sessionid` в «Cookies» конфигурации парсера Instagram (пароль не нужен и не хранится — TD-016) |

Таблица «Как запустить» с примерами ссылок для каждого парсера есть прямо в
форме задачи (`apps/scrapers/modes.py`).

## Куда попадают товары в режиме «Весь сайт»

- Если в задаче выбрана «Целевая категория», все товары попадают туда.
  Исключение — БАДы IlacFiyati при корне «БАДы» (или «Медицина»): категорию
  сохранённого БАДа задача не меняет, новый получает раздел и подкатегорию-вещество
  («Минералы» → «Магний») по названию (`apps/catalog/supplement_taxonomy.py`),
  не распознан — раздел или корень «БАДы».
  Подкатегория, выбранная в задаче явно (например «Витамины»), применяется как раньше.
- Если не выбрана, категория ищется в «Сопоставлениях категорий»
  конфигурации: адрес категории источника → наша категория. Если
  сопоставления нет, работает автоопределение парсера: IlacFiyati — лекарства
  и БАДы, FLO — тип обуви, IKEA — по категории и функции API. Если не сработало
  и оно, товар уходит в категорию по умолчанию из конфигурации.
- Для UmmaLand (книги, праздники, игры, канцелярия…) и магазинов одежды перед
  первым полным прогоном стоит завести сопоставления категорий, иначе всё
  уйдёт в категорию по умолчанию.

## Как это устроено

- **Режим определяется по ссылке**
  (`ScraperIntegrationService._run_parser_scraping`): карточка товара — один
  товар; страница категории — обход категории. Обход сохраняет каждый товар
  сразу и продолжается чанками («Страниц за один запуск») через
  `run_scraper_task`, пока парсер сообщает `has_more_pages`. Чанки — только у
  парсеров с `SUPPORTS_PAGE_CHUNKING` и `supports_page_chunking_for_url`
  (IlacFiyati, UmmaLand, Zara, LCW, FLO, IKEA); у Inditex-наследников флага
  нет, категория — один запуск.
- **Весь сайт** (`SiteScraperTask.task_type = "site"`). В первом чанке
  вызывается `parser.parse_categories()`. Список сохраняется в
  `SiteScraperTask.site_categories`, текущая категория — в
  `site_category_index`. Каждая категория идёт тем же обходом категории.
  Когда категория закончилась, `run_scraper_task` запускает следующую со
  страницы 1. Счётчики общие. Состояние обхода (`CatalogTraversalState`:
  «уже видели», «три страницы без новых товаров») у каждой категории своё
  (`services._catalog_scope`). Если бы оно было общим, категория, первые
  страницы которой повторяют соседнюю, останавливалась бы раньше времени.
  Товар из соседней категории просто обновляется ещё раз. Категория, упавшая
  после всех повторов, пропускается с ошибкой в задаче. Пустая категория
  (лукбук без карточек, `MalformedOfferResponse`) и 404 страницы категории
  (`CategoryPageNotFoundError`) не повторяются — обход сразу идёт к
  следующей (`tasks._category_content_error`). Блокировка доступа
  (401/403) останавливает весь обход. Пустой список категорий — понятная
  ошибка, а не «успех».
- **Только изменения** (`task_type = "changes"`) идёт той же цепочкой, что
  «Весь сайт» (`tasks.SITE_TRAVERSAL_TASK_TYPES`): этапы берутся из
  `parser.parse_change_sources()`, а сервис подставляет парсеру
  `ListingChangeTracker` (`changes_only=True`).
- Тип «Товар или категория по ссылке» без ссылки форма не примет. Раньше
  такая задача запускала старый обход «всех категорий» в памяти: без чанков,
  с сохранением только в конце.

## Точечный обход: карточка открывается только при изменении

Обход категории (режимы 2 и 3) у FLO, Zara, LC Waikiki, IKEA и UmmaLand не
открывает карточку товара, если его строка в списке категории не изменилась
с прошлого обхода. Список категории проходится как раньше — новые товары
находятся в нём же.

| Парсер | Что входит в отпечаток строки списка | Что открывает карточка |
|---|---|---|
| FLO | JSON плитки `data-gtm-product`: название, цена, цена со скидкой, наличие, размеры с наличием, цвета с наличием (остаток `qty` — нет) | все цвета модели — по запросу на цвет, через платный прокси |
| Zara | компонент списка: название, цена, зачёркнутая цена, наличие, цвета с ценой и наличием | одна карточка (≥ 2,5 с между запросами, пауза 15–30 с на каждые 20), через платный прокси |
| LC Waikiki | текст плитки: бренд, название, цена со скидкой, число цветов | карточка и все цвета группы |
| IKEA | строка поиска API: название, цвет, цена, скидка, продаётся ли, статус наличия, число цветов, коды фото | `detail` артикула и каждого цвета |
| UmmaLand | строка API категории целиком (название, цена, наличие, метка, фото, рейтинг) | страница книги |

Bershka, Pull&Bear и Massimo Dutti карточек не открывают: `productsArray`
отдаёт товар целиком по 12 за запрос, экономить нечего. Akakce — не обход
каталога. Instagram — посты не меняются, отдельной карточки нет. У IlacFiyati
свой тип задачи — [«Только изменения»](#только-изменения-ilacfiyati) (своя
таблица `SourceListingRow`, ещё и снимает пропавшие товары); объединить её с
`ListingSnapshot` — отдельным шагом.

Карточка открывается, если:

- товара ещё нет в базе (нет отпечатка) или его удалили — отпечаток удаляется
  вместе с товаром;
- отпечаток строки изменился (цена, наличие, размеры…);
- карточку не открывали дольше 30 дней (у каждой строки свой срок 22–37 дней,
  чтобы такие открытия размазывались по обходам) — так обновляется то, что
  видно только в карточке: описание, состав, остатки по размерам у Zara,
  точный остаток IKEA;
- в задаче включено «Открыть все карточки» — после правок парсера или чтобы
  заново скачать все карточки (например, после потери медиа).

Пропущенные строки идут в счётчик «Пропущено», в логе чанка — строка
«карточек без изменений в списке (не открывались): N».

Ссылки на другие цвета внутри плитки FLO своей строки не имеют: если плитка не
изменилась, они тоже не открываются (наличие цвета уже входит в её отпечаток).
Цвет, загруженный вместе с группой в этом проходе, запоминается со своей
строкой без открытия — иначе следующий обход открыл бы всю группу ради него.

Устройство: `apps/scrapers/base/listing_snapshot.py` (`listing_fingerprint`,
`ListingGuard`), таблица `scrapers.ListingSnapshot` (парсер, строка, отпечаток,
товар, когда открыта карточка). Сервис создаёт `ListingGuard` для обхода
категории у парсеров с `SUPPORTS_LISTING_GUARD`, парсер спрашивает
`should_open(строка, отпечаток)` до запроса карточки и помечает товар
`attach(...)`; после успешного сохранения сервис записывает отпечаток
(`record_listing_snapshot`). Поменяли состав отпечатка — поднимите
`LISTING_FINGERPRINT_VERSION` парсера: все карточки откроются один раз заново.

Sitemap источников для этого не годится: у LC Waikiki `lastmod` у всех
товаров — дата генерации файла, у IKEA дат нет, у Zara даты только у файлов.

### Замер без открытия карточек

`manage.py measure_listing_changes <парсер>` проходит списки тем же кодом,
но карточки не открывает и в базу не пишет: строки, запросы и байты списков,
сколько карточек открыл бы точечный обход (по `ListingSnapshot` или по файлу
прошлого замера), `--sample-cards N` — цена карточки и оценка полного и
точечного обхода. Прокси — только с `--use-proxy`.

```bash
manage.py measure_listing_changes flo --url https://www.flo.com.tr/sandalet --pages 2
manage.py measure_listing_changes zara --categories 3 --baseline --sample-cards 5 --save /tmp/zara.json
manage.py measure_listing_changes zara --categories 3 --compare /tmp/zara.json
```

| FLO | фильтр «kategori» страницы `/tum-kategoriler` (полное дерево): разделы второго уровня и корни без подразделов, ~130 |

Числа — живая проверка 21.10. Список ограничен: 500 категорий, у Inditex — 800
(`BaseScraper.MAX_SITE_CATEGORIES`). Пустой список — ошибка
`SiteCategoriesError`, а не «успех».

## Весь сайт IlacFiyati: этап по sitemap

`/ilaclar` отдаёт только 1000 страниц (12 000 строк): пагинация обещает 2045, но страница 1001 — снова
первая, и обход останавливается как на конце каталога. Лекарства за 1000-й страницей полный обход раньше не
открывал (TD-037). Теперь у задачи «Весь сайт» три этапа (`parse_site_sources`):
лекарства, БАДы и sitemap. Листинги записывают показанные ссылки в `SourceListingRow` с ID прохода, а этап
по sitemap открывает только ссылки, которых листинг в этом проходе не показал. Товары с продажи полный
обход не снимает: это делает только «Только изменения». Этап занимает один запрос sitemap на чанк и по
запросу на карточку (на 31.10.2026 ≈ 460 карточек, ≈ 20 минут).

Почему sitemap, а не вторая сортировка (`?order=za`), живая проверка 31.10.2026: sitemap — один запрос и
только активные товары (12 464 лекарства); в `order=za` половина строк PASİF (6 из 12 на первой странице, а в
обычной сортировке их нет), она тоже обрезана на 1000-й странице, значит, это до 1000 лишних запросов
(≈ 47 минут) без гарантии дойти до всех. Если листинг в этом проходе упал, этап откроет всё, чего листинг не
показал: для полного обхода это ожидаемо.

Автозапуска нет, полный обход запускает владелец.

## Только изменения (IlacFiyati)

Полный обход IlacFiyati открывает каждую карточку (~20 тыс.), хотя большинство
не меняется. Режим «Только изменения» читает строки листинга — в них уже есть
название, штрихкод, цена, статус (AKTİF/PASİF) и тип рецепта — и открывает
карточку, только если строка отличается от запомненной.

**Как запустить.** «Задачи парсинга сайтов» → «Добавить»: конфигурация
IlacFiyati, тип «Только изменения (IlacFiyati)», ссылка не нужна, «Макс.
товаров» — 100 000 (считаются только открытые карточки), «Страниц за один
запуск» — 20–50. Пауза и «Продолжить» работают как у «Весь сайт». Для другого
парсера форма тип не примет.

**Три этапа** (в задаче — «Весь сайт / изменения: прогресс»):

1. **Лекарства `/ilaclar`**, все страницы листинга. Карточка открывается, если
   товара у нас нет, это заглушка аналога, товар у нас снят с продажи, а у
   источника AKTİF, или отпечаток строки (название, штрихкод, цена, статус,
   рецепт) отличается от запомненного. В первом проходе отпечатков ещё нет:
   строка сверяется с базой по названию источника (`source_name`) и цене;
   совпала — отпечаток запоминается без открытия карточки. Строка PASİF у
   товара, который у нас в продаже, — товар снимается с продажи; пассивные
   товары, которых у нас нет, не заводятся.
2. **БАДы `/takviye-edici-gida`** — так же.
3. **Sitemap `sitemap.xml.gz`** (один запрос, 34 624 адреса). Открываются
   ссылки, которых листинг в этом проходе не показал: новые товары и те, до кого
   листинг не достаёт — `/ilaclar` отдаёт только 1000 страниц (12 000 из
   ~12 465 активных лекарств), дальше снова первая страница. Наши товары в
   продаже, которых нет ни в sitemap, ни в листинге, проверяются запросом
   карточки: 404/410 или «İlaç Durumu: Pasif» — снимаются с продажи, иначе
   карточка сохраняется как обычно. Sitemap меньше 1000 карточек — ошибка, по
   нему никто не снимается. Разделы `/ilaclar/<раздел>` (106 шт., priority 0.6)
   и `/takviye-edici-gida/<раздел>` выглядят как адрес карточки — их отсеивают
   `MEDICINE_CATEGORY_SLUGS` / `SUPPLEMENT_CATEGORY_SLUGS`, а новый раздел, которого
   нет в списке, разбор карточки отклоняет как «страницу раздела» (26.10.2026 до
   этого создалось 105 «лекарств» «37 Binden Fazla İlaç…»).

**Что сохраняется.** Открытая карточка идёт обычным путём парсера: цена,
зачёркнутая цена, AI-тексты и пометка «изменился исходник»
(`ai_source_changed_at`) работают так же, как при полном обходе. Цена из строки
напрямую не пишется: карточка — один запрос (вкладки инструкции и аналоги
встроены в страницу), а единый путь сохранения важнее этой экономии.

**Снятие с продажи** ничего не удаляет: товар и доменная запись — «нет в
наличии», предложения источника — «нет в наличии» с кодом `inactive` (PASİF) или
`not_found` (404). Следующий успешный разбор карточки вернёт наличие.

**Где хранится.** Таблица `SourceListingRow` (парсер, ссылка, отпечаток, статус
у источника, ID прохода). Отпечаток открытой строки записывается только после
успешного сохранения карточки — упавшая откроется в следующем проходе. Код:
`apps/scrapers/base/listing_changes.py` (решение), `apps/scrapers/listing_changes.py`
(БД), `IlacFiyatiParser.parse_listing_rows` / `_parse_sitemap_changes`.

**Чего режим не видит.** Правку инструкции, картинок или аналогов без изменения
строки листинга. Поэтому раз в месяц — полный обход «Весь сайт» (автозапуска
нет, запускает владелец). Строки, сдвинувшиеся в листинге во время прохода,
подберёт sitemap-этап: любая активная ссылка, которую листинг не показал,
открывается.

**Только посмотреть.** `manage.py ilacfiyati_changes_probe` ничего не пишет:
проходит листинги и sitemap, печатает, сколько карточек откроется и сколько
товаров снимется с продажи, сколько это запросов и часов против полного обхода
([MANAGEMENT_COMMANDS.md](MANAGEMENT_COMMANDS.md)). `--pages 20` — быстрая проба
без sitemap.

## Описание товара

Описание не должно быть пустым. Если у источника нет текста описания, парсер
собирает его из характеристик карточки:

- **Bershka, Massimo Dutti** — `/itxrest` отдаёт пустой `description`.
  Описание собирается из атрибутов `DESCRIPTION` (их сайт показывает как
  описание), состава (`compositionDetail`) и ухода (`care`).
- **FLO** — у части обуви описания нет и на сайте, есть только блок
  «Ürün Özellikleri». Описание собирается из него: марка, модель, цвет, пол,
  материалы, подошва.

Настоящий текст источника всегда главнее. Старые товары задним числом не
перепарсиваются: описание появится при следующем проходе.

## Бренд товара

Порядок (`ScraperIntegrationService._apply_brand_mapping`):

1. **Бренд задачи** — выше всего, заменяет бренд и у уже сохранённого товара.
2. **Магазин одного бренда** (флаг «Мультибрендовый магазин» выключен) —
   «Бренд по умолчанию» из настроек парсера ставится всем товарам: LC Waikiki,
   IKEA, Zara, Bershka, Pull&Bear, Massimo Dutti. Бренд со страницы — только
   если бренда по умолчанию нет.
3. **Мультибрендовый магазин** (флаг включён: FLO, akakce) — бренд со страницы
   каждого товара (у FLO — `manufacturer` карточки). «Бренд по умолчанию» —
   только запасной, если на странице бренда нет.

Новый бренд со страницы создаётся в каталоге (уникальный slug), ему
добавляется раздел товара (`category_slugs`: shoes, clothing…) — по нему
строится фильтр брендов в категории. Пустые и служебные значения («Diğer»,
«Markasız», «Другое», цифры, ссылки) бренд не создают: товар получает «Другое»
или бренд по умолчанию.

Повторный парсинг меняет бренд, только если у товара пусто или стоит
заглушка «Другое» (`slug=other`). Выбранный вручную настоящий бренд не
перезаписывается. Книги (`BRAND_CLEAR_PRODUCT_TYPES`) бренд не получают.

То же правило действует при открытии карточки покупателем (проверка цены и
наличия у источника, [PRODUCT_CARD_SOURCE_REFRESH_PLAN.md](PRODUCT_CARD_SOURCE_REFRESH_PLAN.md)):
бренд «Другое» или пустой заменяется — у мультибрендового магазина брендом
со страницы (затем бренд по умолчанию), у магазина одного бренда только
брендом по умолчанию. Название, описание, SEO и AI-тексты не меняются.

Товары FLO, сохранённые до этого правила с «Другое», исправляет команда
`repair_flo_brands` ([CATALOG_MAINTENANCE_COMMANDS.md](CATALOG_MAINTENANCE_COMMANDS.md)).

## Проверка после деплоя

У каждого парсера: 1–2 товара по ссылке, маленькая категория до конца, начало
«Весь сайт» с маленьким лимитом. У каждого сохранённого товара проверить, что
описание не пустое. Zara, FLO и akakce идут через платный прокси — не больше
3 товаров. Instagram — один пост и начало профиля с маленьким лимитом и
паузами между запросами.

Точечный обход: маленькую категорию (не FLO/Zara) пройти дважды подряд —
во второй раз в логе чанка «карточек без изменений … : N», товаров
«Найдено» почти 0, `ListingSnapshot` с этим парсером не пуст. Первый обход
после выкладки открывает все карточки (отпечатков ещё нет).
