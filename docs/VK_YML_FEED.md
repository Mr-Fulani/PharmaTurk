# YML-фид для ВК Маркета и Яндекса

Обновлено 2026-10-31 (синхронизация каталога через API, TD-039).

## Как работает

- Ссылка: `https://mudaroba.com/api/catalog/export/yml/catalog.yml` — полный каталог;
  `?category=<slug>` — категория с подкатегориями. Ссылки всех разделов и время
  их сборки — в админке «Маппинги категорий ВК» (`/admin/catalog/vkcategorymapping/`).
- **Корневые категории и полный каталог** собирает задача Celery
  `catalog.generate_yml_feeds` каждые 6 часов (00:35, 06:35, 12:35, 18:35 МСК) в файлы
  `feeds/yml/` хранилища (на проде — R2). Какой файл актуален, хранит таблица
  `YMLFeedSnapshot` (раздел, время сборки, число офферов, размер). Эндпоинт отдаёт
  готовый файл потоком, с `ETag`/`Last-Modified` (повторный запрос с `If-None-Match` → 304).
  Лимит — 30 запросов в минуту с IP.
- **Подкатегории** (`?category=<slug подкатегории>`) собираются на лету потоком,
  лимит 2 запроса в минуту с IP.
- **Части.** Раздел больше лимита ВК (7,5 МБ с запасом к 8 МБ или 15 000 офферов)
  собирается несколькими файлами: `?category=furniture&part=2`. Каждая часть — целый
  YML с тем же деревом категорий; без `part` отдаётся часть 1, несуществующая часть — 404.
  Все части со ссылками и размерами — в админке. Подкатегории на лету не делятся.
- **Лекарства не выгружаются** (решение владельца 27.10.2026, «блокируй фид пока»):
  `?category=medicines` и любая её подкатегория — 404, в полном каталоге лекарств нет,
  товары другого типа в разделе лекарств тоже не уходят. Разрешить — убрать
  `medicines` из `BLOCKED_PRODUCT_TYPES`/`BLOCKED_ROOT_SLUGS` в `services/yml_feed.py`.
- **Книги не выгружаются** (решение владельца 01.11.2026): блокируются так же, как
  лекарства (`books` в тех же списках). Фото книг лежат на umma-land.com и часто
  недоступны. Карточки книг, уже загруженные в ВК, фид сам не убирает.
- Если готового файла ещё нет (сразу после первого деплоя), эндпоинт отвечает 503
  с `Retry-After: 600` и сам ставит сборку (не чаще раза в 10 минут). Пересобрать
  вручную — кнопка «Пересобрать фиды сейчас» в той же админке.
- Сборка: товары читаются пачками по 500, доменные записи (обувь, одежда…), фото,
  активные варианты и атрибуты подгружаются одним запросом на тип товара в пачке —
  число запросов не растёт с числом товаров. XML пишется по одному `<offer>`,
  память не растёт с размером каталога. Код — `backend/apps/catalog/services/yml_feed.py`.
- Не попадают в фид: выключенные товары, все лекарства и книги (см. выше) и всё, чего нет в
  наличии (решение владельца 30.10.2026): товар с `is_available=False`, закончившийся
  вариант и товар, который сверка поставщика считает проданным. Иначе ВК создаёт
  карточки с плашкой «Нет в наличии» (в Парфюмерии было 426 из 696). Карточки, уже
  загруженные в ВК раньше, этот фид сам не убирает (поведение ВК при повторной загрузке
  не подтверждено) — их удаляет синхронизация каталога (раздел ниже) или владелец в самом ВК.
- Цена в фиде равна цене на сайте в рублях: перевод в рубли с наценкой валютной пары
  плюс товарная наценка (бренд → категория → глобальная). До 30.10.2026 товарная наценка
  в фид не попадала, и цены в ВК были ниже сайта.
- Файлы `feeds/` защищены от `cleanup_orphaned_media`; старый файл раздела удаляет
  сама сборка после переключения на новый.

## Фото в ВК

Кнопка «Синхронизировать» в таблице разделов ставит фоновую задачу
`catalog.sync_vk_photos` (команда `sync_vk_photos`, категория с подкатегориями).
Итог приходит администратору в Telegram. Нужен `VK_USER_TOKEN` в `.env` (на проде
на 27.10 не задан — кнопка покажет ошибку и ничего не запустит). Синхронизация
меняет публичную витрину ВК — только с согласия владельца.

## Синхронизация каталога через API (TD-039)

Чтобы не загружать файлы руками: каталог ВК приводится к тем же офферам, что идут в
полный фид (только в наличии, цены с наценкой как на сайте, без лекарств, книг и «ввоз
ограничен»). Новые товары добавляются, цена, наличие, название и описание обновляются,
всё, чего нет в фиде, удаляется. Код — `services/vk_catalog_sync.py`, команда
`sync_vk_catalog`, задача `catalog.sync_vk_catalog`.

**Как запустить.** По умолчанию — только отчёт: к ВК идут одни запросы чтения, отчёт
показывает, сколько будет добавлено, обновлено и удалено, с примерами.

| Что | Как |
|---|---|
| Отчёт | `manage.py sync_vk_catalog` или кнопка «Каталог ВК: только отчёт» в «Маппингах категорий ВК» (итог в Telegram) |
| Настоящий запуск | `manage.py sync_vk_catalog --apply` или кнопка «Синхронизировать каталог ВК» — видна и работает только у суперпользователя |
| По расписанию | ежедневно 07:15, только при `VK_SYNC_ENABLED=true` (по умолчанию `false`) |

Настоящий запуск меняет публичную витрину — только с согласия владельца.

**Настройки.** `VK_USER_TOKEN`, `VK_GROUP_ID`, `VK_SYNC_ENABLED`,
`VK_SYNC_MAX_DELETE_SHARE` (0.3). Изменение `.env` — пересоздать backend, `celeryworker`
и `celerybeat`.

**Ключ — главный вопрос.** Все методы `market.*` работают только с ключом пользователя
(схема API ВК: `access_token_type: user`), `VK_YML_API` (ключ сообщества) не подходит.
Документация dev.vk.ru на 31.10.2026: право `market` «выдаётся в исключительных случаях»
по запросу в поддержку devsupport@corp.vk.com. Значит, ссылка `oauth.vk.com/authorize`
из `settings.py` может не дать нужного права: сначала пробуем получить ключ, затем
запрашиваем отчёт. Без права ВК вернёт ошибку уже на чтении, в ВК ничего не изменится.

Проверка 01.11.2026: ключ по этой ссылке выдаётся, но ВК привязывает его к адресу, где
нажали «Разрешить»: с сервера `[5] access_token was given to another ip address`. Вход в
ВК через адрес сервера не прошёл. Implicit и Authorization Code Flow для ключа
пользователя ВК отключил с 25.06.2024, ключ пользователя теперь выдаёт только VK ID и он
живёт 1 час. Рабочий порядок (FAQ id.vk.ru, «Как получить расширенные доступы»):
подтвердить профиль бизнеса приложения (резидент РФ — VK Бизнес ID: самозанятый, ИП или
ООО; нерезидент РФ — форма «Доступы → Расширенные доступы» с данными о себе или организации
и банковскими реквизитами), включить опцию «товары», написать обоснование; ручная модерация,
ответ на почту до 3 рабочих дней. Потом вход через VK ID с обновлением ключа. До этого
загрузка YML вручную остаётся единственным способом.

01.11.2026 владелец отказался от подтверждения профиля: права `market` не будет, товары в
ВК загружаются вручную, TD-038 и TD-039 отложены.

Вход «через ВК» на сайте идёт через другое приложение: «Mudaroba», ID 54532929
(`VK_APP_ID`), не «Tijara» (54475107). 01.11.2026 оно заблокировано из-за неподтверждённого
профиля: `id.vk.ru/authorize` отвечает «Сервис заблокирован». Подтвердить профиль и включить
«Товары» логично в нём: «Tijara» в кабинете id.vk.ru/about/business/go/ не значится.
`VK_USER_TOKEN` используется и во входе через ВК (`users/social_auth.py`, обогащение профиля)
раньше `VK_API_TOKEN`: нерабочий ключ в `.env` держать нельзя.

**Предохранители.**

- Сопоставление только по артикулу: `sku` в ВК = `<vendorCode>` оффера.
- Запуск останавливается и ничего не меняет, если на удаление попадает больше
  `VK_SYNC_MAX_DELETE_SHARE` каталога ВК. Разовый запуск с другим порогом, когда владелец
  посмотрел отчёт: `sync_vk_catalog --apply --max-delete-share 0.6` (порог действует и на
  проверку ниже). На первом запуске порог может сработать: в ВК лежат карточки, которых
  уже нет в наличии.
- Фид пустой или не собрался, список товаров ВК не прочитан или неполный — ничего не
  меняется.
- Товары ВК без нашего артикула (пусто или не вида `538`/`538v1`) не удаляются, они
  показаны в отчёте отдельно: решает владелец.
- Такие товары занимают больше той же доли каталога — запуск останавливается. Это не
  только чужие карточки: если ВК не отдаст `sku` товаров, загруженных через YML, весь
  каталог выглядел бы новым и получил бы дубли. Старые карточки без артикула
  (см. «Повторная загрузка») перед запуском удалить в самом ВК.
- Два товара ВК с одним артикулом из фида: обновляется первый, второй показан в отчёте и
  не удаляется. Дубль артикула, которого нет в фиде, удаляется вместе с товаром.

**Лимиты и сбои.** Пауза 0,4 с перед каждым запросом (не больше 2,5 в секунду; у ключа
пользователя лимит 3 в секунду — по сторонним SDK, официальная страница не открылась).
Ошибки 1, 6, 9, 10 и сеть — до трёх повторов с паузами 2, 10, 30 с. `market.add`
после таймаута или сбоя ВК не повторяется: товар мог создаться, и повтор дал бы дубль,
его увидит следующий запуск. Ошибка одного товара и битое фото в отчёт, запуск идёт
дальше. Запуск останавливается при ошибках ключа, прав, капчи, лимитов (5, 6, 7, 9, 14,
15, 29, 205), «слишком много товаров» (1405), выключенном магазине (1438) и 20 ошибках API
подряд. Состояния нет: следующий запуск заново сравнивает ВК с фидом, поэтому сделанное
не повторяется, а остальное продолжается. Порядок работ: удаления, цена и наличие,
новые товары, тексты.

**Время.** Задача ограничена 2,5 часа (меньше `visibility_timeout` брокера, 3 часа) и всё
это время занимает один из двух слотов `celeryworker`. За это время проходит около
22 000 правок или заметно меньше новых товаров (у каждого — скачать и загрузить фото).
Цены пересчитываются по курсу, поэтому изменённых товаров может быть много каждый день;
что не успели, сделает следующий запуск.

**Новый товар в ВК.** `market.add` требует ID категории: поле «ID категории ВК» в
маппинге (миграция `0232` заполняет его по таблице ниже, путь, изменённый в админке,
остаётся пустым). Товары без ID, фото или цены не добавляются и показаны в отчёте. Главное
фото — первый `<picture>`: `market.getProductPhotoUploadServer` → POST файла →
`market.saveProductPhoto`; не JPG/PNG/GIF переводится в JPEG, меньше 400×400 — ошибка
товара. Дополнительные фото и видео догружает `sync_vk_photos`. Название обрезается до
100 знаков (лимит API). Варианты добавляются отдельными карточками: группировку
`group_id` через API (`market.groupItems`) синхронизация не делает, цвет и размер есть в
названии.

**Проверено по официальным источникам 31.10.2026** — страницы dev.vk.ru и схема
`github.com/VKCOM/vk-api-schema` (dev.vk.com не открывается, документация переехала):
`market.add/edit/delete/get`, их параметры, `sku` в объекте товара, `availability`,
`price.amount` в сотых долях, массив `variants` при `need_variants`,
`market.getProductPhotoUploadServer`, `market.saveProductPhoto`, коды ошибок, адрес
`api.vk.ru`.

**Не подтверждено, проверить на первом отчёте и первых запусках:**

- что `market.get` с ключом отдаёт `sku` у товаров из YML, и что он равен `<vendorCode>`
  (владелец видел поле «Артикул» только в карточке). Не отдаёт — сработает остановка
  «без нашего артикула»;
- что `count` в `market.get` не включает лишнего: при `with_disabled` и `need_variants`
  поведение не описано. Не совпадёт — отчёт скажет «каталог ВК не прочитан»;
- что ВК не меняет текст при хранении: иначе тексты будут «отличаться» при каждом
  запуске (они идут последними и цены не задерживают);
- что валюта магазина в ВК — рубли: `amount` сравнивается с ценой фида;
- что `market.edit` с `deleted=0` возвращает скрытый товар (есть ещё `market.restore`);
- подходят ли ID 20000/20001/20002 для третьего уровня («Обувь», «Аксессуары»): ID этого
  уровня нет, в маппинг записан ID второго уровня;
- что ссылка в описании не вызовет ошибку 1408 «неверные ссылки»;
- дневной лимит ВК на запись: не опубликован; при флуд-контроле (9) запуск остановится;
- что версия API 5.131 (её использует руководство ВК, текущая — 5.199) отдаёт всё нужное;
- руководство `dev.vk.ru/en/api/upload/photo-in-market` ещё описывает
  `photos.getMarketUploadServer` и `photos.saveMarketPhoto`, а в схеме API этих методов
  нет. Синхронизация использует `market.*`, `sync_vk_photos` — пока прежние `photos.*`.

## Ограничения ВК (справка vk.com/faq21697)

- файл YML до **8 МБ** и до **15 000 товаров** (каждый вариант — отдельный товар) —
  поэтому части; каждую часть подключать в ВК отдельной ссылкой. Не проверено, может
  ли сообщество держать несколько YML-источников сразу и не удаляет ли импорт одной
  части товары другой — проверить на первом подключении;
- обязательны `id`, `name`, `description`, `picture`, `price`; не больше 2 `param`
  (характеристики у нас в описании).

## Варианты (цвет, размер)

Решение владельца 27.10.2026: в ВК цветовые варианты выглядели дублями (одинаковое
`<name>`, нет `group_id` и `<param>`). Теперь у каждого варианта:

- `group_id` = id товара на сайте — общий для всех его вариантов;
- в `<name>` — цвет по-русски и размер, если есть: «Кепка LC WAIKIKI, хаки»
  (цвет переводится тем же словарём, что на сайте: «Haki» → «Хаки»; если цвет уже
  есть в названии — не дублируется; длина ≤ 100 — лимит ВК, режется по слову). Цвет без перевода в словаре и
  без кириллицы («Bilinmeyen») не выводится нигде — лучше без цвета, чем турецкое
  слово. 27.10 по живым фидам из 23 непереведённых цветов переводятся 22 (`TR_COLOR_DICTIONARY`):
  «Çok renkli», «çeşitli», «Taba», «Kum», «Vizon», индиго, «Koyu Petrol» и др.;
  «SİYAH»/«LACİVERT» не находились из-за турецкой «İ» — исправлено в
  `normalize_ascii_text`. «Taş» нарочно не добавлен (короткий ключ задел бы слова
  в AI-названиях);
- `<param name="Цвет">` и `<param name="Размер">` — ВК принимает не больше двух
  свойств, поэтому остальные характеристики остаются в описании.

У товаров без вариантов ничего не меняется. Что ВК склеивает офферы с одним
`group_id` в одну карточку с выбором варианта, официальная справка не описывает;
по сторонним сервисам импорта — склеивает, свойства берёт из `<param>`, и
объединяются офферы с одинаковой ценой. В апреле 2026 `group_id` был выключен с
пометкой «ВК дописывает атрибуты к названию» — после первого импорта проверить,
нет ли в названиях двойного цвета.

## Повторная загрузка в ВК и артикул

27.10.2026 владелец дважды загрузил `?category=underwear` — число товаров выросло:
ВК создал дубли. У каждого оффера теперь `<vendorCode>` = id оффера («538»,
«538v1»), он не меняется между сборками — в карточке ВК это поле «Артикул».

- По какому тегу ВК узнаёт уже загруженный товар, официальная справка не описывает;
  проверено владельцем 27.10: с `<vendorCode>` повторная загрузка дублей не даёт.
- Сам по ссылке ВК каталог не обновляет: после изменений файл загружают заново
  (раздел «Товары» → «Импортировать из файла») либо запускают синхронизацию каталога.
- Товары, загруженные до появления артикула, ВК сопоставить не сможет — их удалить
  один раз перед новой загрузкой.

## Описание: ссылка на сайт, без кодов поставщика

- HTML из описания карточки (`<p>`, `<br>`, `<li>`…) снимается (`html_to_text`): ВК
  теги не рендерит. Абзацы — переносами строк, пункты списка — «• », сущности
  (`&nbsp;`, `&amp;`, `&reg;`) — символами; «5 < 7» в тексте не трогается.
- ВК не показывает `<url>` из фида в карточке, поэтому в конце `<description>` —
  «Подробнее и заявка: https://mudaroba.com/product/…?utm_source=vk&utm_medium=market».
  Описание ограничено 3000 знаками: при длинном тексте сокращается сам текст, затем
  характеристики, ссылка остаётся целой. `<url>` — без utm.
- Артикул поставщика (`variant.sku`) и характеристики с кодами («Артикул…», «Код…»,
  «Штрихкод», SKU, GTIN, MPN) в описание не попадают — наш артикул только `<vendorCode>`.

## Фото: что даёт фид, а что — синхронизация

- **Главное фото** приходит из фида: `<picture>` — обязательный тег импорта ВК, карточки
  без ключа `VK_USER_TOKEN` с картинкой будут.
- Сколько дополнительных `<picture>` ВК берёт из фида, в открытой справке не сказано
  (вручную в карточку ВК — до 5 фото). Видео через YML ВК не принимает.
- `sync_vk_photos` (кнопка «Синхронизировать», нужен `VK_USER_TOKEN`) загружает в уже
  импортированные товары до 5 фото — фото варианта (цвета) и галерею — и первое видео.
- **Маленькие фото.** ВК не принимает фото меньше 400×400, а у БАДов с ilacfiyati они
  368×250. Задача `catalog.prepare_feed_pictures` (ежедневно 23:50 МСК, перед сборкой
  00:35) один раз проверяет каждую ссылку фида и для маленьких кладёт в
  `feeds/pictures/` копию 800×800: фото увеличено, поля белые. Сборка фида подставляет
  копию вместо исходной ссылки; сайт копии не использует. Запись — `YMLFeedPicture`.
  Сбой скачивания повторится при следующем запуске, прерванный запуск продолжает
  следующий. Старые копии не удаляются: их мало, и `feeds/` защищена от чистки медиа.

## Категории ВК (`<market_category>`)

Пути проставлены миграцией `0229_vk_category_paths` (решение владельца 27.10.2026
«решай сам, проверь информацию в вк»), прежний путь записан в «Примечания» записи,
откат миграции возвращает четыре апрельские записи. Маппинг — по типу товара и полу:
пол берётся из товара, затем из категории (или её родителей), затем по названию
категории («Мужская…», «Женская…», «Детская…»), как фильтр «Пол» на сайте; без пола и
унисекс — запись «Любой пол».

Проверка: названия и ID второго уровня — из ответа `market.getCategories` (лог клиента
OpenIntegrations на GitHub). Разделы «Гардероб», «Дом и дача» и третий уровень
«Обувь», «Аксессуары» — из записей владельца (апрель 2026, из интерфейса ВК), для
«Женщинам»/«Детям» продублированы. Как именно ВК сопоставляет `<market_category>`,
справка не описывает — сверить на первом импорте.

## После деплоя

1. Миграции `catalog.0228`–`0229` (0229 ставит пути категорий ВК и удаляет прежние
   готовые фиды — в них были лекарства), `0232` (ID категорий ВК, без сети) и `0233` (фото
   фида, без сети); пересоздать
   backend, `celeryworker` и `celerybeat` (код задач запечён в образ).
2. После `0233` запустить `catalog.prepare_feed_pictures` и затем пересборку фидов, не
   дожидаясь расписания. Первый проход проверяет все фото каталога; если не уложится в
   50 минут, запустить ещё раз.
3. Первый запрос фида ответит 503 и сам запустит сборку; либо админка → «Маппинги
   категорий ВК» → «Пересобрать фиды сейчас». Через несколько минут в таблице — все части.
4. Смоук: `curl -sI 'https://mudaroba.com/api/catalog/export/yml/catalog.yml?category=furniture&part=2'`
   → 200, размер < 8 МБ; `?category=medicines` → 404; `<url>` в фиде начинаются с
   `https://mudaroba.com/product/` (иначе проверить `FRONTEND_SITE_URL`).
