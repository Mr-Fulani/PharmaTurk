# Технический долг Mudaroba

Актуализировано: **22 августа 2026 года**.

В этом документе фиксируются подтверждённые дефекты и хрупкие места, которые
ещё не исправлены. Приоритеты: **P0** — блокирует безопасный production-релиз;
**P1** — ближайший спринт; **P2** — системный техдолг; **P3** — улучшение.

## Открытые задачи

### TD-001 — Непрозрачное и некорректное выполнение обогащения медиа товаров

- **Приоритет:** P2
- **Статус:** открыто
- **Область:** Django Admin, Celery, каталог товаров
- **Функция:** быстрое действие «Обогатить медиа (картинки)»
- **Дата проверки:** 22 августа 2026 года

#### Подтверждённое поведение

1. Действие админки зарегистрировано для лекарств и БАДов и корректно вызывает
   Celery-задачу `catalog.enrich_medicine_media`.
2. Админка сразу показывает сообщение об успешном запуске после вызова
   `.delay()`, но не сообщает идентификатор задачи, не отслеживает её результат
   и не показывает, сколько изображений было фактически добавлено.
3. При ручном запуске все выбранные товары сначала получают статус
   `processing`. Если у товара уже есть максимальные три изображения,
   обработчик выходит раньше обновления итогового статуса, поэтому товар может
   навсегда остаться в состоянии «Обработка».
4. Если источники не нашли изображения либо все кандидаты были отклонены при
   загрузке и валидации, товар получает статус `completed`, а Celery-задача
   возвращает `success` с `images_added=0`. Для оператора это выглядит как
   успешная обработка без результата и без понятного объяснения.
5. Метод `get_media_enrichment_status` расположен в
   `ShadowProductCleanupAdminMixin`, хотя логически относится к
   `MediaEnrichmentMixin`. Сейчас колонка доступна благодаря текущей цепочке
   наследования, но при рефакторинге она может незаметно исчезнуть.

Локальная проверка 22 августа также показала, что Docker daemon и Celery-воркер
не были запущены. Это объясняет невозможность локальной обработки задач, но не
подтверждает состояние production-инфраструктуры.

#### Риски

- оператор получает ложноположительное сообщение об успехе;
- товары остаются в некорректном статусе `processing`;
- невозможно отличить остановленный воркер от результата «ничего не найдено»;
- повторные ручные запуски могут расходовать лимит внешнего поиска без видимой
  пользы;
- ошибки отдельных кандидатов скрываются и не агрегируются в понятный результат.

#### План исправления

1. При раннем пропуске товара с достаточным количеством изображений выставлять
   итоговый статус, `media_enrichment_last_at` и понятную причину пропуска.
2. Разделить результаты «добавлены изображения», «изображения не найдены»,
   «все кандидаты отклонены» и «техническая ошибка».
3. Возвращать из Celery-задачи агрегированный результат без общего `success`,
   если ни один товар не был обогащён или были ошибки.
4. Показывать в админке идентификатор поставленной задачи и ссылку либо иной
   способ просмотра её итогового результата.
5. Перенести `get_media_enrichment_status` в профильный mixin.
6. Добавить тесты переходов статусов для товара с достаточным количеством
   изображений, отсутствием кандидатов, полностью отклонёнными кандидатами,
   успешным добавлением и исключением обработчика.
7. Перед production-проверкой подтвердить доступность Redis и Celery-воркера и
   проверить соответствующие логи выполнения задачи.
