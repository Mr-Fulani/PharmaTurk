# Свод правил разработки Mudaroba

Правила учитывают специфику проекта: Next.js 15.5 на Node.js 22 (pages router,
i18n ru/en, defaultLocale=ru) + Django 5.2/DRF + Celery + Postgres + Redis +
R2/Cloudflare, мультидоменный каталог (18 типов товаров + услуги), деплой
docker-compose за nginx и Cloudflare.

---

## 1. SEO — железные правила

Это e-commerce: страницы каталога — главный источник трафика. Любая правка страниц обязана соблюдать:

1. **Роутинг локалей:** `ru` — без префикса (`/product/x`), `en` — с префиксом (`/en/product/x`). URL вида `/ru/...` Next отдаёт как 200-дубликат (склеивается 301-ом на уровне nginx). Никогда не генерировать ссылки/редиректы/canonical с `/ru`.
2. **Canonical:** всегда self-referencing с учётом локали:
   ```ts
   const localePrefix = router.locale === router.defaultLocale ? '' : `/${router.locale}`
   const canonicalUrl = `${siteUrl}${localePrefix}${path}`
   ```
   Захардкоженный canonical без префикса = EN-версия выпадает из индекса.
3. **hreflang:** на каждой индексируемой странице ровно три тега: `ru` (без префикса), `en` (`/en/...`), `x-default` (= ru). Один источник — страница; в `_document.tsx` hreflang не дублировать.
4. **Редиректы в getServerSideProps:** `destination` строить через `ctx.locale !== ctx.defaultLocale ? '/'+ctx.locale : ''`. Постоянный редирект (`permanent: true`) — только когда URL действительно навсегда сменился.
5. **Ошибки бэкенда ≠ 404.** `notFound: true` возвращать только если API явно ответил 404. Сетевые ошибки и 5xx — пробрасывать (бот получит 500 и вернётся, страница останется в индексе).
6. **noindex** — на cart, checkout (включая `checkout-success`, `checkout-crypto`), profile, auth, favorites, search и на каталожных страницах с фильтрами/сортировкой (категории и бренды, `buildCatalogSeoState`). Бренд, у которого меньше 3 товаров (`isThinBrand`, `lib/brandCatalog.js`), тоже `noindex, follow` и вне sitemap (`BRAND_SITEMAP_MIN_PRODUCTS` в `SitemapEntriesView`): в Search Console 27.10.2026 из 1 000 примеров «Просканирована, но пока не проиндексирована» 431 были страницами брендов, а в sitemap стояли все 950 брендов, 107 из них пустые. Чистая пагинация `?page=N` — self-canonical, индексируется. На noindex-страницах canonical/hreflang не нужны. Закрытые разделы в `robots.txt` перечислять для обеих локалей (`/cart` и `/en/cart`). Переходы на закрытые страницы из публичных (вход ради отзыва или вопроса на карточке) — кнопкой с `router.push`, не ссылкой: до 09.11.2026 «Войти» в отзывах была `<Link>` на `/auth?next=…`, и Search Console показывал ~3 400 таких адресов «заблокировано в robots.txt». `Clean-param` в `robots.txt` — только метки (`utm_*`, `yclid`, `ysclid` и т. п.), параметры сайта (`page`, `sort`, фильтры, `q`) туда не добавлять ([YANDEX_INDEXING.md](YANDEX_INDEXING.md)).
7. **Sitemap:** единственный источник — `frontend/src/pages/sitemap.xml.tsx` (индекс) и его секции `pages/sitemaps/[section].tsx`. Новая сущность с публичной страницей → сразу добавить в sitemap (с hreflang-альтернативами) и проверить canonical. Новая ключевая страница (раздел, гайд, посадочная) — ещё и ссылка в `frontend/public/llms.txt` (описание сайта для ИИ-поиска). Подкатегории обуви и мебели (`/categories/sneakers`, `/categories/beds`) — обычные страницы и стоят в секции `categories`: до 27.10.2026 они отдавали 307 на фильтр корня с `noindex`, и у «Кроссовок», «Кроватей» не было индексируемой страницы. Перелинковка каталога — ссылками `<Link>`, не `onClick` + `router.push`: плитки разделов и брендов на главной до 27.10.2026 были кнопками, и в HTML главной не было ни одной ссылки на раздел. Подборки категорий (`/categories/<категория>/<подборка>`) идут в секцию `categories` из `sitemap-entries?kind=collections`, пустые не попадают. Секция `brands` — только бренды от 3 товаров в наличии (снимок `get_brand_product_counts`). Страницы препаратов (`/drugs/<slug>`) — секция `drugs` из `kind=drug_groups`, статьи блога — секция `static`. Секция, собранная со сбоем API, не кэшируется (`no-store`), а пустая из-за сбоя отвечает 503 с `Retry-After`: до 22.10.2026 пустой список уходил с `s-maxage=86400`, и Cloudflare сутки отдавал пустую секцию (тест `src/lib/sitemapSection.test.mjs`). Товарная секция без товаров в индекс `/sitemap.xml` не попадает (проверка `sitemap-products?page_size=1` по каждому домену): urlset без `<url>` Google считает ошибкой «Тег XML отсутствует» — так было с electronics, medical-equipment, auto-parts до 09.11.2026. Если проверка домена не ответила, секция остаётся, а индекс отдаётся с `no-store` (тест `src/lib/sitemapIndex.test.mjs`).
8. **Метаданные двуязычны.** Title/description берутся из переводов API (`translations[locale]`), фолбэк — шаблонные строки через `t(...)`. Не хардкодить русский текст в мету. H1, title, description и SEO-текст посадочной страницы категории или подборки — поля перевода (`CategoryLandingSeoMixin`, в API категории — `seo` при `include_seo=true`); перевода на языке страницы нет — шаблон, а не текст другого языка ([MEDICINE_LANDING_PAGES.md](MEDICINE_LANDING_PAGES.md)).
9. **JSON-LD:** карточка товара — `Product` (+ `Offer`, `aggregateRating` при наличии отзывов); медикаменты — БЕЗ `Offer` (сайт их не продаёт, см. `canPublishSchemaOffer` в `lib/productAvailability.js`); `Product`/`Drug` без `Offer` и `aggregateRating` не выводится вовсе (`shouldPublishProductSchema`: иначе ошибка «Описания товара» в Search Console — 222 лекарства 25.10.2026); `image` — массив всех фото галереи, главное первым, до 10 (`buildSchemaImages`; поле Merchant Center «изображения на предложение»); в `Offer` — `shippingDetails` (`buildSchemaShippingDetails`, решение владельца 28.10.2026: 7–14 дней = сборка 1–2 + в пути 6–12, у БАДов с 09.11.2026 — 3–7 дней (авиа: сборка 1–2 + в пути 2–5), 5 $ в валюте цены по курсу сайта из `shipping_rates` в resolve, страны `SCHEMA_SHIPPING_COUNTRIES`: KZ, UZ, AZ, TR, AE, US и ЕС; у мебели, лекарств и услуг доставки в разметке нет, на карточке — строка «Доставка из Турции: 7–14 дней, от 5 $»), `hasMerchantReturnPolicy` (условия `/returns`: 14 дней, почтой, обратная доставка за счёт покупателя, кроме брака), `brand`, `sku` ≤ 50 символов (`resolveSchemaSku`); категории и бренды — `BreadcrumbList`; страница препарата `/drugs/<slug>` — `BreadcrumbList` + `FAQPage` по видимым «Вопросам и ответам» (`buildDrugGroupFaq`), без `Product`/`Drug` и `Offer`; статья блога — `Article` + `FAQPage` по видимым вопросам + `BreadcrumbList`; `og:image` категории берётся из актуальной карточки (`get_effective_og_image_url`), адрес карточки в `og_image_url` не копировать — после перезаливки карточки копия ведёт на удалённый файл; описание категории — `buildCategoryDescription` (`lib/seoText.js`); главная — `Organization` (`description` из переводов, растровый логотип `/logo-512.png`, `sameAs` только https, `email` из настроек футера; адреса нет — решение владельца 09.11.2026) + `WebSite`; `image`/`og:image` карточки — с нашего домена, если в галерее есть своя копия фото: свои первыми, чужой CDN убирается, когда своих ≥ 2 (`preferOwnDomainImages`), og:image — первая своя не-GIF (`pickOwnDomainImage`). Валидировать через Rich Results Test после изменения.
10. **Длина мета:** title ≤ 80, description ≤ 200 символов, резать только по границе слова (`lib/seoText.js`: `limitTitle`, `truncateAtWord`), не `.slice(0, N)`. Название сайта в title — через « | Mudaroba» на всех типах страниц (`SEO.tsx`, `withSiteName`); title карточки товара без названия сайта получает «… из Турции | Mudaroba» (`withProductTitleSuffix`, слова не убираются, пока влезает в 80).
11. **alt фото товара** — название на языке страницы, со второго кадра «— фото N» (`productImageAlt`, `lib/seoText.js`; в карточке каталога — название без номера). Сохранённый `alt_text` собран при загрузке из исходного турецкого названия и ни AI, ни правками не обновляется: до 05.11.2026 он стоял первым, и у новых товаров (SuperStep — все 131) alt был турецким на обеих локалях. Запасной описательный текст карточки — с названием в начале («<название> из Турции — заказ на Mudaroba»), а не «Заказать <название>»: название в именительном падеже после глагола — ошибка.
12. **Перед мержем любой правки страниц** прогнать чек: `curl -s https://site/<page> | grep -E 'canonical|hreflang|robots'` для обеих локалей.

## 2. Производительность

1. **SSR — только то, что нужно для первого экрана и меты.** Остальное (рекомендации, отзывы, похожие товары) — клиентская подгрузка. Исключение — перелинковка карточки: до 8 текстовых ссылок на товары той же категории приходят в ответе resolve (`related_links`, 2 запроса по частичному индексу, без отдельного HTTP-запроса из gSSP).
2. **Кэшируй HTML только при безопасном общем ответе:** публичная gSSP-страница
   может ставить `Cache-Control: public, s-maxage=..., stale-while-revalidate=...`
   только если её HTML не зависит от cookie, авторизации, валюты или другой
   персонализации. Ответ с пользовательскими/currency-cookie либо `Set-Cookie`
   должен использовать `private, no-store`. Персонализацию по возможности
   загружать на клиенте, не включать в общий SSR-кэш.
   Ответ-ошибка в CDN-кэш не попадает: при 500 (исключение в gSSP или в рендере)
   `pages/_error.tsx` перезаписывает заголовок на `private, no-store`, поэтому
   public-кэш можно ставить в начале gSSP и не сбрасывать перед `throw`.
   Осознанный `notFound` (только по явному 404 API, §1.5) рендерит `404.tsx`,
   он сохраняет кэш страницы. `getInitialProps` из `_error.tsx` не убирать.
3. **Параллель, не серия:** несколько независимых запросов к API в gSSP — только `Promise.all/allSettled` с таймаутами. Циклы по страницам пагинации в SSR запрещены.
4. **Запросы к БД:** новый list/detail-эндпоинт обязан иметь `select_related`/`prefetch_related` и `only()` по факту использования сериализатором. Проверка — `django-debug-toolbar`/`assertNumQueries` в тесте. Список, сериализуемый по одному объекту (`serialize_product_for_card`), получает один общий `context` на ответ — в нём батч-кэши категорий и брендов.
5. **Медиа:** изображения — через `cdn.mudaroba.com` или proxy-media с `max_width`; в `<Image>` указывать `sizes`; `priority` — только для LCP-элемента. Оптимизатор `/_next/image` работает в процессе Next и под нагрузкой ронял его по памяти: его ответы кэширует nginx (`next_image`), а `onError` у важных картинок сначала повторяет прямой URL CDN (`unoptimized`) и только потом ставит заглушку (см. [PROD_MEMORY.md](PROD_MEMORY.md)). Видео никогда не стримить через Django, если есть прямой CDN-URL.
6. **Кэш Redis:** ключи версионировать (`v2:...`), не вайпить кэш целиком при деплое. TTL обязателен.
7. **Длинные операции — в Celery**, не в request-цикле (генерация, парсинг, рассылки, конвертация).
8. **Расписание beat — `crontab`, а не длинный интервал.** Состояние beat теряется при каждом деплое, интервал «раз в сутки/неделю» может не сработать никогда (см. `CELERY_TASKS.md`). Массовое удаление — пачками с отдельной транзакцией на пачку.
9. **Условия на `external_data` (jsonb) в публичных выборках** детоастят дампы парсеров (до мегабайт на строку): планировщик не учитывает эту цену и проверяет `?` раньше индексных условий. Такое условие допустимо только вместе с частичным индексом, предикат которого текстуально совпадает с SQL ORM, и тестом на `EXPLAIN` (примеры — миграции 0194/0208/0217, `apps/catalog/querysets.py`). Редкие служебные строки исключать подзапросом `id NOT IN (…)` по такому индексу, а не условием в основном запросе. `COUNT` по такому индексу — index-only скан, он быстр, только пока VACUUM успевает за правками таблицы: таблице с частичными индексами и большим `external_data` нужны пониженные пороги autovacuum (миграция 0218, [PROD_DB_MAINTENANCE.md](PROD_DB_MAINTENANCE.md)).

## 3. Бэкенд (Django/DRF)

1. Каждый публичный эндпоинт: пагинация (`StandardPagination`), фильтры через query-параметры, `max_page_size` ≤ 1000.
2. Локализация ответа — по `Accept-Language`; новые текстовые поля моделей сразу получают перевод (механизм `translations`).
3. Списки типов товаров (`BASE_PRODUCT_TYPES`, `TYPES_NEEDING_PATH`) — единый источник правды на бэкенде; фронт не копирует, а потребляет (до рефакторинга: менять синхронно в `product_resolve.py`, `lib/product.ts`, `sitemap.xml.tsx` — все три, и обновлять тесты).
4. Слаги валидируются на входе (парсеры, админка, AI): нижний регистр, дефисы, без дублирующихся половин, уникальность по всем доменным моделям. В слаг товара из парсера `external_id` попадает только допустимыми в адресе символами (буквы, цифры, `-`, `_`): точка из кода цвета SuperStep (`superstep-13424.0195`) давала слаг, по которому страница отвечала 404 (`CatalogNormalizer.normalize_product`, тест `test_product_slug_external_id`).
5. Миграции — только через `makemigrations` локально и в коммит; на проде только `migrate`.
   Миграции данных не ходят в сеть (R2, внешние API): у контейнера миграций на проде нет выхода в интернет — релиз 27.10.2026 упал на удалении файлов фидов, сайт лежал ~4 минуты. Файлы чистит фоновая задача после деплоя.
6. Никаких секретов в коде и дефолтах настроек; прод падает при отсутствующем env, а не работает на заглушке.
7. **AI не перетирает данные каталога.** `AIResultApplier` заполняет категорию
   только у товара без категории (иначе — модерация), не меняет slug
   существующего товара и не перезаписывает описание/SEO/переводы, изменённые
   после генерации (снимок `input_data["content_snapshot"]`). Новые поля,
   которые пишет AI, подчиняются тем же правилам (см. `AI_GUIDE.md`).
   Парсеры и импорты не перезаписывают тексты товара с применённым
   AI-результатом (`apps/ai/services/ownership.py`): исходник — в
   `external_data["source_description"]`, смена — флаг `ai_source_changed_at`.
   Название источника — в `external_data["source_name"]`: AI пишет в `name`
   перевод, а код, которому нужен оригинал (шаблон названия лекарства),
   берёт его оттуда, а не из `name`.
8. Глобальный DRF default — `IsAuthenticated`. Каждый действительно публичный
   endpoint обязан явно объявлять `AllowAny`; административные и служебные
   операции — `IsAdminUser` либо более строгое объектное permission. Нельзя
   полагаться на неявный default при изменении публичности API.
9. **Варианты в доменных сериализаторах — из prefetch-кэша.** `.filter()`,
   `.order_by()` и `.exists()` на менеджере `variants`/`images` идут мимо
   prefetch: default/active вариант запрашивается до десятка раз на товар, и
   страница бренда мебели/одежды делала ~300 запросов к вариантам. Брать
   варианты и их картинки через `_prefetched_active_variants`,
   `_variant_cover_image`, `_variant_images_by_sort_order`
   (`apps/catalog/serializers.py`); без prefetch они идут в БД по-прежнему.
   Галерея самого товара (`obj.images`) — через те же два хелпера картинок.
   Название ключа атрибута (`GlobalAttributeKey.name`) берёт переводы из
   prefetch `…attribute_key__translations`, если он есть. Тесты —
   `apps/catalog/tests/test_domain_variant_queries.py`,
   `apps/catalog/tests/test_brand_card_gallery_queries.py`.
10. **Карточка лекарства — для покупателя из России.** Турецкие реалии,
   которые ему ничего не говорят (цвет бланка рецепта), в карточку не
   переносятся; формулировки нейтральные — сайт лекарства не продаёт
   («рецептурный препарат», а не «отпускается по белому рецепту»).
   Проверки AI-названий оценивают сам результат и сверяют его с турецким
   оригиналом, а не с текущим именем товара в БД: название, исправленное
   модератором, должно проходить (см. `AI_GUIDE.md`, «Лекарства: код вместо LLM»).
   Клинический раздел применяется к товару, только если его абзацы прошли те же
   правила, что и при записи в память (`medicine_paragraph_findings` в
   `SemanticValidator.validate_log`); новый путь применения AI-лога идёт через
   `apply_log_to_product`, а не в обход валидатора.
   У каждой блокировки модерации есть действие модератора, которое её снимает:
   новая проверка, отклоняющая поле, добавляет такое решение и подсказку в
   `get_unblock_actions`. Решение снимает проверку только явным действием
   человека и привязано к проверенному тексту (`moderator_title_review`,
   `moderator_description_review` у БАДов,
   решение раздела `reviewed`) — новый AI-результат проверяется заново.
11. **Парсеры не выдают «пустой успех».** Пропажа ожидаемого блока вёрстки или
   ключа API — ошибка источника, а не «каталог закончился»; одна снятая
   карточка (404/410) пропускается, а не обрывает обход. Цена 0 от источника —
   «цена не опубликована» и при создании, и при обновлении товара. Итог
   прогона пишет в `ScraperConfig` только поля статистики (`update()`), не
   `save()` объекта, загруженного в начале задачи. Снятая карточка (404/410) и
   неверная ссылка раздела (`CategoryPageNotFoundError`) не переводят
   конфигурацию в «Ошибка»: проверка цены при открытии карточки и в корзине
   берёт только `status=active`. Живые изменения вёрстки
   закрываются тестом на фрагменте настоящей страницы (см.
   [AUDIT_2026-10-20_PARSERS.md](AUDIT_2026-10-20_PARSERS.md)). Селектор
   цены и зачёркнутой цены ограничивается блоком самого товара — блоки
   рекомендаций размечены теми же классами. Поля адресов медиа, которые
   заполняет парсер, — `max_length=2000`: путь CDN с длинным slug бывает
   длиннее 200 символов. Файловые поля фото и видео товаров
   (`image_file`, `main_image_file`, `main_video_file`) — `max_length=500`: путь
   раздела со slug (`products/headwear/hw-caps/hw-baseball-caps/…`) длиннее 100
   символов по умолчанию, и до 04.11.2026 фото шапок, белья и исламской одежды
   не сохранялись («Storage can not find an available filename») и качались
   заново при каждом проходе (тест `test_domain_media_max_length`).
12. **У каждого каталожного парсера три режима:** товар по ссылке, категория
   до конца (чанки и `has_more_pages`; у Bershka, Pull&Bear и Massimo Dutti
   чанков нет — категория идёт одним запуском в пределах «Страниц за один
   запуск»), весь сайт (`parse_categories`). Новый
   парсер реализует все три, получает строку в `apps/scrapers/modes.py` и
   тест на `parse_categories`. Описание товара не пустое: если у источника
   нет текста, оно собирается из характеристик карточки (состав, материалы,
   уход). Обход категории точечный: если строка списка уже даёт цену и
   наличие, парсер считает её отпечаток и открывает карточку только при
   изменении (`ListingGuard`, `SUPPORTS_LISTING_GUARD`); состав отпечатка
   поменяли — поднять `LISTING_FINGERPRINT_VERSION`. Бренд: «Бренд по
   умолчанию» в настройках — для магазина одного бренда; у магазина разных
   брендов (FLO) включается «Мультибрендовый магазин», и парсер отдаёт бренд
   каждого товара в `ScrapedProduct.brand`. Повторный парсинг и обновление
   карточки при открытии заменяют только заглушку «Другое». См. [PARSER_MODES.md](PARSER_MODES.md).
13. **У товара одна активная доменная запись — текущего `product_type`.** Смена
   типа (админка, нормалайзер; в форме товара смена только категории на категорию
   другого типа меняет и тип) переносит картинки прежней доменной записи — галерею и
   фото вариантов, варианты целиком, если новый тип их поддерживает, — в запись
   нового типа и снимает прежнюю с публикации (`domain_sync.retire_stale_domain_records`).
   Снимать только `QuerySet.update(is_active=False)`: `save()` доменной модели
   синхронизирует её в `Product` и вернул бы товару старый тип и `is_active=False`;
   запись прежнего типа в `Product` больше не синхронизируется. Строки медиа при
   этом не удаляются — ссылки нужны, иначе файлы снесёт `cleanup_orphaned_media`.
   Парсеры Zara/Inditex отмечают сумки, кошельки, ремни, украшения и шапки
   (`attributes["inditex_category_slugs"]`), и категория задачи из ветки «Одежда»
   не делает их одеждой. Категория задачи парсера другого типа существующему товару не
   ставится (кроме лекарств): тип она не меняет, товар оказался бы чужим разделу
   (`_category_changes_domain`). Смена типа без `Product.save()` — так, как это делает
   `move_essential_oils_from_supplements`: `save()` синхронизирует из новой доменной записи
   пустые SEO. См. [CATALOG_MAINTENANCE_COMMANDS.md](CATALOG_MAINTENANCE_COMMANDS.md).
14. **Файл медиа удаляется только после проверки ссылок, закрытой при сбое.** Резервной
   копии медиа товаров нет: код, который удаляет файл из R2, проверяет ссылки через
   `apps/catalog/utils/media_references.py` (один запрос на поле, а не на файл) и при
   `MediaReferenceCheckError` ничего не удаляет; `except: continue` в проверке ссылок
   запрещён. Массовое удаление — с потолком числа файлов и отчётом админу при превышении
   (`cleanup_orphaned_media`, чистка `products/parsed/` — `CELERY_TASKS.md`).
   Оригинал парсера в `products/parsed/` удаляется в конце прогона, когда его копия в
   читаемом пути записана в БД (`collect_parsed_originals`); новый путь сохранения
   товаров парсером (задача, команда, скрипт) оборачивается в него, иначе оригиналы
   копятся и еженедельная `cleanup_orphaned_media` отменяется по лимиту (`SCRAPERS_GUIDE.md`, §11.2).
   Товары вместе с файлами удаляются только через «Неактуальные товары» в админке
   ([STALE_PRODUCTS.md](STALE_PRODUCTS.md)): файл сначала копируется в бакет бэкапов,
   сигналы удаления файлов на это время выключены (`storage_deletes_suppressed`), удаление
   файлов и `cleanup_orphaned_media` держат одну блокировку.
15. **Цвет, скрытый как дубль у другого продавца, сам на сайт не возвращается.** У FLO и
   SuperStep одинаковый товар показывается один раз — более дорогой
   ([CROSS_SOURCE_DUPLICATES.md](CROSS_SOURCE_DUPLICATES.md)); скрытый цвет —
   `is_active=False` + строка `CrossSourceDuplicate`. Код, который ставит цвету
   `is_active=True` (импорт, проверка карточки, ночная сверка, новые пути), пропускает
   цвета из `hidden_variant_ids()` и после смены цены или наличия вызывает
   `resolve_for_products()`. Тот же товар узнаётся по штрихкоду размера (`gtin`) и
   артикулу (`mpn` цвета), не по названию; скрытое возвращается на сайт только после
   проверки у продавца (`verify_hidden_duplicate`); адрес скрытой карточки — временный редирект
   (307) на показанную, не 301 и не 404.
16. **Вторая страница ilacfiyati одного препарата не становится товаром.** Страницы с одним
   штрихкодом (импорт `1111111…`: страница фирмы с ценой и страница TEB с «0,00 TL»),
   совпадающие по названию в источнике и составу, — один товар: остаётся страница с ценой,
   вторая не создаётся или скрывается (`is_active=False`, адрес — 301 на оставленную через
   `ProductSlugHistory`); сомнение (разные числа или слова названия, состав, цены) — на
   проверку человеку, не объединять. Код, который ставит лекарству `is_active=True`,
   не возвращает товары с `external_data["ilacfiyati_twin_of"]`
   ([ILACFIYATI_TWIN_PAGES.md](ILACFIYATI_TWIN_PAGES.md)) и
   `external_data["ilacfiyati_duplicate_of"]`. Страница с тем же настоящим штрихкодом,
   названием и ценой — тот же товар под новым адресом (адрес переносится, копия «…-2» не
   заводится), карточка после 301 сохраняется по конечному адресу, новая карточка «Pasif»
   товаром не становится, адрес источника сравнивается целиком, не «содержит» ([ILACFIYATI_DUPLICATES.md](ILACFIYATI_DUPLICATES.md)).
17. **Поиск товаров — только через `apps/catalog/product_search.py`** (`filter_by_search`,
   `order_by_relevance`), не `name__icontains`: до 05.11.2026 поиск смотрел только в
   `Product.name`, и производители, переводы, МНН, штрихкоды, «омега 3», «US Polo» не
   находились (44 из 115 запросов аудита). Новое поле, по которому покупатель ищет товар, —
   в `build_search_row` и тест. Массовая правка через `update()`/`bulk_*` сигналы обходит:
   после неё — `rebuild_product_search_index --apply` ([PRODUCT_SEARCH.md](PRODUCT_SEARCH.md)).
   Откат релиза на версию без таблицы индекса — только после `--clear --apply` (каскад FK — в коде).
   Сортировка по точности перебирает все совпадения: ключи только дешёвые (`LIKE`, длина), служебные
   строки — подзапросом по индексу 0217, проверка — на каталоге с тяжёлым `external_data`
   (05.11.2026 после выкатки «кр» искалось 20 с).
   Кириллица, синонимы, раскладка и опечатки — словарями (`vocab.BRAND_RU`, `vocab.KINDS`,
   память `medicine_brand`, словари запроса в `search_language.py`), не новым словарём брендов и не LLM;
   исправленный запрос ищется теми же `LIKE`, без `similarity` в `COUNT` и странице.

## 4. Фронтенд (Next.js)

1. Страница > ~400 строк — выделяй компоненты/хуки. В `pages/` — только роутинг, мета и gSSP; логика — в `components/`, `lib/`, `hooks/`.
2. Мета-теги — через единый компонент `SEO.tsx`; ручной `<Head>` с canonical в новых страницах — запрещён.
3. Переводы: каждая новая строка UI — сразу в `public/locales/ru/common.json` и `en/common.json`; `t('key', 'фолбэк')` обязателен.
4. Клиентские запросы — через `lib/api.ts` (`getClientApiBase`), SSR — `getInternalApiUrl`. Прямые URL бэкенда в компонентах запрещены.
5. Деньги: форматирование только через `lib/price.ts`. Никаких локальных `toFixed`/`toLocaleString`.
6. **Цвет из CSS-переменной — без модификатора прозрачности.** Tailwind 3 не генерирует `bg-[var(--bg)]/95`, `text-main/50`, `border-[var(--border)]/50`: класс молча пропадает, и фон становится прозрачным (так мобильная шторка фильтров категорий показывала тёмный текст на размытой картинке). В `[var(--…)]` — только переменные, объявленные в `styles/globals.css` (`--accent-hover`, `--text-muted`, `--text-main` там нет). Шторка фильтров `CategorySidebar` на мобильном: сплошной фон `--bg`, текст не ниже 4.5:1 в обеих темах, строки и кнопки от 44 px.
7. **Видео баннеров не грузится вместе со страницей.** В `BannerCarouselMedia` `<video>` рендерится с `preload="none"` без `autoPlay`; ролики играют, только пока блок не дальше полэкрана от видимой области (`IntersectionObserver` с `rootMargin`): активный слайд и видимые миниатюры (на десктопе превью — часть дизайна). Скрытые CSS-ом миниатюры (на телефоне все, `visibility: hidden`) ролик не качают, ушедший с экрана блок стоит на паузе. Исключение — карусель `main`: она в первом экране и запускает ролик без ожидания гидратации. `preload="metadata"` миниатюрам не подходит: у роликов баннеров `moov` в конце файла, и Chrome скачивает их почти целиком. До правки мобильная главная тянула ≈ 18 МБ mp4 восьми роликов `after_brands`/`before_footer`. Пока ролик грузится, виден постер — поле `BannerMedia.video_poster` (в админке рядом с видео; webp до 1400 px, 50–100 КБ), в API `poster_url`. Его ставит тот же ref-колбэк и по тому же условию, что `play()`, а не проп `poster`: постер скрытого `<video>` браузер тоже скачивает. Тест — `src/lib/bannerLoading.test.mjs`.
8. **Миниатюры баннеров на десктопе.** Видны две — 2-й и 3-й элементы `BannerCarouselMedia` (`VISIBLE_THUMBNAILS`), порядок — из админки. Обе целиком в окне: правый край ленты (`--strip-end`) в 48 px от края окна (с классической полосой прокрутки ≈ 40 px), миниатюра 2:3: 100×150 до ~960 px, 116×173 на 1024, 174×262 на 1280, 200×300 с ~1390 px; зазор — 0,1 ширины. До ~1200 px обе внутри баннера, дальше правая выступает за его край; с ~1420 px положение прежнее. Лента начинается не левее 67 % ширины баннера, место убранной миниатюры у центра (`left: 52%`) свободно с ~950 px — ради этого миниатюры мельче (решение владельца 22.10.2026: на 1024 px 116×173 вместо варианта 168×252, при котором лента заходила на место у центра); на 769–950 px миниатюры 100×150 заходят на него до 57 px — так оставлено сознательно (решение владельца 22.10.2026), уменьшать их ради свободного места не нужно. Если медиа два, единственная миниатюра стоит на прежнем месте, когда там помещается. Формула считает, что карусель стоит по центру окна (так на главной, /how-to-order-medicines, /brands и /categories); в несимметричной колонке правый край ленты нужно пересчитать. До 22.10.2026 на 769–1324 px вторая миниатюра обрезалась краем окна (на 1024 было видно 52 px из 200). На ≤ 768 px лента от 52 %, как раньше, на ≤ 640 px миниатюр нет. Миниатюра — кроп широкого баннера (до 200×300 из картинки шириной ~700 px), поэтому файл под её ширину размыт. После `load`, в `requestIdleCallback`, видимые картинки-миниатюры (≥ 769 px, блок рядом с экраном, без роликов) получают тот же полноразмерный файл, что и слайд: при переключении он уже в кэше. До этого миниатюры маленькие, ближайшая с `fetchPriority="auto"`, остальные `low` — канал у LCP не отнимается. Картинки — только через `next/image`. Тест — `src/lib/bannerLoading.test.mjs`.

## 5. E-commerce правила

1. **Цена и наличие правдивы.** JSON-LD `Offer` и видимая цена обязаны совпадать; нет цены — `price on request`, без нулей. Цена товара — цена, по которой продаёт источник (у FLO — `special_price`, а не `price`). `old_price` — только зачёркнутая цена, которую показывает сам источник, и только если она выше текущей (`apps/catalog/utils/old_price.py`); прежняя цена товара скидкой не является, у лекарств `old_price` пустой. Цена товара с цветами (одежда, обувь, головные уборы, бельё) — цена одного цвета по одному правилу `default_fashion_variant` (`apps/catalog/utils/default_variant.py`): первый по порядку сайта цвет в наличии, зачёркнутая — того же цвета. Им пользуются импорт, обновление карточки, пересчёт дублей и витрина; своё «первый с ценой» не писать — до 04.11.2026 витрина показывала цену распроданного цвета, а сортировка шла по другой.
2. **Деньги — Decimal на бэкенде**, никогда float. Округление вверх (`Math.ceil`) — только на отображении, не в расчётах заказа.
3. **Снятый с продажи товар не 404:** страница остаётся (200) с пометкой «нет в наличии» и ссылками на аналоги; 410 — только при окончательном удалении; редирект 301 — при замене на преемника.
4. **Смена slug = 301-редирект** со старого URL. Механизм: при `save()` `Product` или доменной модели старый slug пишется в `ProductSlugHistory` (сигналы в `catalog/signals.py`); resolve, не найдя живой товар, ищет slug в истории и отдаёт товар с `canonical_path` на новый URL, а gSSP карточки отвечает 301 с учётом локали. `QuerySet.update()`/`bulk_update` сигналы обходят — slug ими не менять (либо дописать `ProductSlugHistory` вручную). Slug, снова ставший живым, из истории удаляется; удаление товара удаляет его историю (старый URL → 404).
5. **Checkout-цепочка неприкосновенна:** изменения cart/checkout/payments требуют ручной проверки на стейдже (карта + крипто) и юнит-тестов на пересчёт суммы.
6. **Аналитика событий** (view_item, add_to_cart, generate_lead, contact_click…) не ломается молча: события шлются только через хелперы `lib/gtm.ts` (GA4 + цели Метрики), новое событие — сразу тест в `gtm.test.mjs` и строка в `docs/ANALYTICS_EVENTS.md`; проверка на сайте — DebugView GA4 и `?_ym_debug=1` (GTM не загружается). Заявка менеджеру — `generate_lead`, не `purchase`.
7. **Фиды (YML и т.п.)** меняются вместе с моделью товара: добавил поле/тип — проверь, что фиды и sitemap его учитывают.
8. **Сообщения клиенту по инициативе сайта** (напоминания о Списке заявки и будущие рассылки) — только вошедшим клиентам на подтверждённый email или привязанный Telegram; выключатель в админке (по умолчанию выключено), отписка в каждом сообщении (ссылка + `List-Unsubscribe`, `/stop` в боте) и в профиле; без «купить» — сайт не продаёт лекарства; ссылки с UTM. Образец — [CART_REMINDERS.md](CART_REMINDERS.md).
9. **Работа менеджеров с заявкой — отдельно от клиентского статуса.** «Обработка» (`Order.processing_status`), ответственный и журнал `OrderProcessingEvent` — только для админки: клиенту не уходят и `status` не трогают. Менять их только через `apps/orders/processing.py` (или `OrderAdmin.save_model`), чтобы в истории остались кто и когда; `QuerySet.update()` журнал обходит. Новое значение «Обработки» — в `PROCESSING_RANK` и `PROCESSING_COLORS` админки и в [ORDER_PROCESSING.md](ORDER_PROCESSING.md).
10. **Сроки доставки — одни на весь сайт** и меняются только решением владельца. Лекарства и БАДы (решение 09.11.2026): «авиа 3–7, наземная 7–14, морем 20–45 дней», в коротких местах (SEO-описания, превью, пометка карточки лекарства) — «3–14 дней»; прочие товары — «7–14 дней, от 5 $». Фразы для бэкенда — `apps/catalog/services/delivery_terms.py`, уже записанные тексты меняет команда `replace_delivery_terms` (см. [CATALOG_MAINTENANCE_COMMANDS.md](CATALOG_MAINTENANCE_COMMANDS.md)), тексты разделов и страниц в базе — миграцией данных. До 10.11.2026 на сайте одновременно стояли «7–21 рабочий день», «7–14 дней» и «авиа 3–7, наземная 7–14», и ChatGPT пересказывал сроки `/delivery`, расходившиеся с карточками ([SEO_AI_VISIBILITY.md](SEO_AI_VISIBILITY.md)).

## 6. Git

1. **main — защищённая ветка.** В main — только через PR (или merge ветки после ревью), никогда напрямую при работе над фичей. Hotfix-исключение допустимо, но фиксируется тегом.
2. **Ветки:** `feature/<краткое-имя>`, `fix/<краткое-имя>`, `seo/<...>`, `perf/<...>`. Одна ветка — одна задача.
3. **Коммиты:** на русском, формат «Префикс: что сделано» — как уже принято (`Сигнал:`, `Перформанс:`, `SEO:`, `Починить:`). Один логический шаг = один коммит. Без Co-Authored-By агентов.
4. **CI обязателен:** все обязательные jobs должны быть зелёными. Backend-тесты,
   проверки схемы, секретов и уязвимостей зависимостей сохраняются. Для diff только
   в backend/docs frontend-job проверяет область изменений и зависимости, но
   не повторяет lint/typecheck/tests/build неизменённого фронтенда. Изменения CI,
   Compose, release-инструментов и неизвестные пути требуют полного набора.
   Определение области — по Git diff, не по ручному флагу пропуска, и только
   для PR: push в main всегда проходит полный набор и публикует оба образа SHA.
5. **Теги релизов:** каждый прод-деплой — тег `vYYYY.MM.N`. Откат = деплой предыдущего тега.
6. **Не коммитить:** `.env*` (кроме `*.example`), дампы, медиа, `node_modules`, сгенерированные файлы. Новые MD-доки — в `docs/`, не в корень.
7. **PR-описание:** что изменилось, как проверено (команды/скрины), затронуты ли SEO-мета/фиды/checkout — отдельной строкой.

## 7. Тестирование и деплой

1. Багфикс начинается с теста, воспроизводящего баг.
2. Минимум для merge: все обязательные jobs действующего CI зелёные; локальные
   проверки выбираются по изменённым компонентам и риску. Не повторять уже
   валидные проверки той же логики без конкретной причины. Правки документации
   не требуют тестов приложения. Изменённая страница проверяется RU/EN.
3. SEO-правки дополнительно: проверка canonical/hreflang curl-ом на обеих локалях + одна карточка каждой затронутой категории.
4. Деплой не в пятницу вечером; после деплоя — смоук: главная, категория, карточка, поиск, корзина, /sitemap.xml.
5. После деплоя следить за Search Console (Coverage) минимум неделю при SEO-изменениях.
6. Диск прода: перед `git merge` релиз запускает `prepare-disk.sh --apply` (остановленные вспомогательные контейнеры `mudaroba-once-*`/`mudaroba-aibatch-*`/`*-run-*`, образы старше предыдущего релиза, копии сверх двух новейших) и останавливается, если места на копию + 4 ГиБ под образы нет; `create-backup.sh` проверяет то же до копии, `pull-images.sh` не скачивает образы при свободных < 4 ГиБ; полный `deploy.sh` после успеха удаляет образы релизов старше предыдущего и копии перед деплоем, кроме двух новейших (текущая защищена). Остальные бэкапы, тома и stage-данные удаляются только по явному согласию. Свободное место и память Redis проверяет `check_server_resources` с алертом в Telegram (см. [PROD_DISK_AND_REDIS.md](PROD_DISK_AND_REDIS.md)).
7. Память прода: у каждого постоянного сервиса Compose есть `mem_limit`, сумма ≤ 7 ГиБ (тест `scripts/release/test_compose_memory.py`). Новый сервис или больший лимит — за счёт других. Кэш Django только в `redis-cache` (вытесняемый), брокер Celery — `noeviction` (см. [PROD_MEMORY.md](PROD_MEMORY.md)).
8. Бэкап базы: ежедневно во внешний приватный бакет отдельным ключом (не ключом медиа), ротация 7/4/3, еженедельная проверка; восстановление с нуля — [DB_BACKUP.md](DB_BACKUP.md). Новая таблица, без которой база бесполезна, — в `REQUIRED_TABLES` (`apps/monitoring/db_backup.py`). Медиа, сделанное вручную (`marketing/`, `pages/`, `services/`), каждую ночь копируется туда же под `media/`, пропавшие файлы хранятся 30 дней; товарные фото не копируются (решение владельца 22.10.2026). Новый префикс такого медиа — в `MEDIA_BACKUP_PREFIXES`.

## 8. Сокращённый backend-релиз

1. Для совместимых изменений backend использовать `scripts/release/backend_release.py`.
   Backend и все его воркеры получают один неизменяемый SHA; текущий frontend
   сохраняет свой SHA. Версии фиксируются атомарно в `.env` без изменения других
   настроек. API-совместимость пары версий проверяется при ревью.
2. Frontend, Nginx, PostgreSQL, Redis и Qdrant не останавливаются и не пересоздаются.
   Инструмент сравнивает их конфигурации и проверяет неизменность контейнеров.
   Короткая недоступность API при замене единственного backend всё ещё возможна.
3. Проверка миграций работает только на чтение. Разрешены отсутствие миграций
   либо явно проверенные nullable UUID-поля таблицы управления парсером без
   default/index/constraint. Остальные операции требуют полного релиза.
4. При такой миграции копируются только таблица задач и журнал миграций; при
   code-only релизе — только защищённая конфигурация/запись версий. Полный дамп,
   новые копии медиа и Qdrant не запускаются автоматически. Удаление старых
   файлов, образов, контейнеров и бэкапов требует отдельного согласования целей.
5. Откат сокращённого релиза — по сохранённой записи пары версий, без обратной
   миграции и без восстановления поверх новых заказов/товаров. При неуспешном
   запуске не продолжать парсинг до проверки состояния и отката.
