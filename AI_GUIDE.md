# AI-модуль PharmaTurk

AI-модуль формирует описание и SEO, предлагает категорию, извлекает атрибуты и при необходимости анализирует изображения товара. По умолчанию результат сохраняется в журнале для проверки и **не применяется к товару автоматически**.

Актуальные источники правды в коде:

- `backend/apps/ai/views.py` и `serializers.py` — API и его входные данные;
- `backend/apps/ai/tasks.py` — постановка и выполнение Celery-задач;
- `backend/apps/ai/services/content_generator.py` — основной pipeline;
- `backend/apps/ai/signals.py` — политика автоматического запуска;
- `backend/config/settings.py` — очереди и расписание.

## 1. Как запускается обработка

Автоматического запуска после сохранения товара или завершения парсинга сейчас нет. Файл `apps/ai/signals.py` намеренно не регистрирует `post_save` receiver на товар, чтобы обычное сохранение товара не расходовало токены OpenAI. Единственный receiver в нём — на `AITranslationMemory`: правка перевода МНН сразу разносится по лекарствам с этим веществом, OpenAI не вызывается. Поля `ai_on_create_enabled` и `ai_on_update_enabled` в конфигурации скрапера сами по себе задачу не ставят.

Поддерживаются явные способы запуска:

1. action для выбранных товаров в Django Admin;
2. кнопка или action «Запустить AI» для сессии/задачи парсинга;
3. staff-only API;
4. management-команда `benchmark_ai` для синхронной диагностики;
5. страница `/admin/ai/manual-tasks/` для массовых ручных задач;
6. раздел **AI → AI-прогоны** (`/admin/ai/airun/`) — массовые прогоны, обслуживающие операции и перевод абзацев инструкций через Batch API кнопками (см. «Массовые прогоны из админки» ниже и пошаговую инструкцию [docs/AI_RUNS_ADMIN_GUIDE.md](docs/AI_RUNS_ADMIN_GUIDE.md)).

Все штатные точки запуска используют `auto_apply=False`, кроме явно названного admin action «[AI] Полная AI обработка + авто-применение», параметра `--auto-apply` у benchmark и API-запроса с `"auto_apply": true`.

## 2. Поток данных

1. `enqueue_product_ai_task()` блокирует строку товара, проверяет существующие активные/готовые логи и создаёт `AIProcessingLog` со статусом `pending`.
2. После commit в очередь `ai` отправляется `process_product_ai_task`.
3. `ContentGenerator` собирает данные товара и контекст вариантов.
4. Если изображения разрешены, до пяти изображений оптимизируются и могут быть отправлены в Vision API.
5. Qdrant, если доступен и заполнен, добавляет к prompt похожие категории и шаблоны. При ошибке Qdrant pipeline продолжает работу без RAG-контекста.
6. OpenAI возвращает структурированный результат; журнал сохраняет ответ, токены, расчётную стоимость и время обработки.
7. При `auto_apply=False` результат получает статус `completed` либо `moderation`. При `auto_apply=True` результат сразу применяется; ошибка применения переводит лог в `failed`.
8. После полной обработки синхронизируются простые названия вариантов, формируется список вариантов-кандидатов на отдельную ручную AI-обработку и откладывается переиндексация товара для рекомендаций.

Повторный обычный запуск не создаёт дубликат, если для того же товара и типа уже есть `pending`, `processing`, `completed`, `moderation` или `approved` лог. Принудительный повтор (`force=True`) используется в действиях перезапуска.

Надёжность очереди:

- `pending`/`processing`-лог, который не обновлялся дольше 60 минут (`STALE_AI_LOG_AFTER` в `apps/ai/tasks.py`), считается зависшим: при следующей постановке он переводится в `failed` и не блокирует повтор. Задача, чей лог уже не активен, пропускается и не дублирует обработку.
- `process_product_ai_task` работает с `acks_late=True` и `reject_on_worker_lost=True`: при деплое или падении `celery_ai` задача возвращается в очередь и продолжает тот же `processing`-лог.
- Автоповтор (до 3 раз) — только при временных сбоях: сетевая ошибка/таймаут, HTTP 429 и 5xx. `ValueError` (невалидный JSON, нет товара) и исчерпанная квота не повторяются. Повтор возвращает тот же лог в `pending`, новый лог не создаётся.

## 3. Данные и компоненты

### Модели

- `AIProcessingLog` — входные данные, результат, метрики, ошибки, статус обработки и отдельный `application_status`, показывающий фактическое применение к товару;
- `AIModerationQueue` — причина, приоритет, назначенный сотрудник и время разрешения;
- `AITemplate` — активные prompt/RAG-шаблоны типов `description`, `category_example`, `attribute_extraction`, `image_prompt`, `category_instruction`.

### Сервисы

- `ContentGenerator` — оркестрация pipeline и применение результата;
- `LLMClient` — OpenAI chat, Vision и embeddings;
- `R2MediaProcessor` — получение и уменьшение изображений перед Vision;
- `QdrantManager` — коллекции `categories` и `templates`, поиск RAG-контекста;
- `AIResultApplier` — перенос одобренных полей в базовый и доменный товар;
- `quality_checker` и `SemanticValidator` — решение о ручной модерации;
- `apps/ai/services/rules/` — детерминированные тексты не медицинских товаров (ниже).

### Детерминированная обработка не медицинских товаров

Для `clothing`, `shoes`, `underwear`, `headwear`, `islamic_clothing`, `accessories`, `perfumery`, `furniture` с назначенной категорией (`RULE_PRODUCT_TYPES` в `rules/facts.py`) полный промпт не строится, RAG и предложение категории не запрашиваются. Лекарства, БАДы, медтехника, книги, украшения и товары без категории идут прежней полной генерацией.

1. **Факты** (`rules/facts.py`): название разбирается словарями `rules/vocab.py` — тип товара, пол, описательные слова («Bisiklet Yaka» → «с круглым вырезом»), цвет, объём; латинские токены до первого словарного слова и коды — бренд/модель. Из атрибутов парсера: цвет, пол, состав («%100 Pamuk» → «100% хлопок»), материалы обуви (`TEKSTIL/PU`), материал аксессуара, тип мебели IKEA (`furniture_type`) и отделка («beyaz-meşe görünümlü» → «белый/под дуб»). Заглушка бренда «Другое» и «Markalar» не используются; бренд ищется в описании («U.S. Polo Assn. Erkek Tişört»).
2. **Название** (`rules/text.py`): RU «Мужские кроссовки BUCKY 6FX, белые» (прилагательные согласуются по роду), EN «BUCKY 6FX Men's Sneakers, White»; у мебели «Комод с 6 ящиками IKEA MALM, белый/под дуб». Цвет пишется только у товара без вариантов (у вариантов цвет к названию дописывает `sync_variant_titles_from_parent`). Неизвестное турецкое слово после типа, название-подпись Instagram (исламская одежда) или парфюм без бренда/модели → название запрашивается у LLM. Шаблонное название, которое `SemanticValidator` отклонил бы (`title_untranslated`, `title_category_mismatch`), тоже уходит в LLM. Русское название источника (Zara RU, прошлый AI) сохраняется, EN собирается из фактов: тип по категории + бренд и латиница названия + пол + материал («Кожаный ремень LC Waikiki» → «LC Waikiki Men's Faux Leather Belt», «Кресло HAVBERG» → «IKEA HAVBERG Armchair»); LLM — только если тип неизвестен.
3. **Описание:** источник, где сверх названия и атрибутов меньше 6 значимых слов (`THIN_SOURCE_MAX_WORDS`), получает описание из фактов без LLM («Мужская футболка Routine. Состав: 100% хлопок. …»); причина `short_description` для него не ставится. Иначе описание берётся из **памяти переводов** (namespace `product_description:<id категории>`; переиспользуются только записи, чей лог `completed`/`approved`, либо правленные вручную), а при промахе — один узкий запрос к LLM только за RU/EN-описанием (и названием, если правила его не собрали): статический промпт ≈ 400 токенов + текст источника до 3000 символов, `max_tokens=1200`. Если модель вернула описание только на одном языке, недостающий язык получает описание из фактов (`rule_content["description_fallback"]`), такой неполный перевод в память не кладётся. Обязательны лишь RU-название и RU-описание: без EN лог не падает, пустые EN-поля при применении пропускаются. Порог `short_description` для узкого запроса — 10 слов (пересказ короткого источника без «воды»), для полной генерации — прежние 20.
4. **SEO** по шаблонам сайта: `meta_title` «{название} — купить с доставкой из Турции» (≤ 70, обрезка по слову), `meta_description` «Заказать {название} из Турции. {первое предложение описания}» (≤ 160), keywords — тип, пол+тип, тип+бренд/модель, «… из Турции», бренд.
5. **Атрибуты:** `extract_dynamic_attribute_candidates` (канон `attribute_specs.py`) + перевод словарём там, где канона нет (подошва, тип мебели); значения на турецком отбрасываются, а не шлются в модерацию.

**Память переводов** (`AITranslationMemory`, сервис `apps/ai/services/translation_memory.py`) — общая для всех доменов: `namespace` + sha256 нормализованного источника (схлопнутые пробелы, регистр сохраняется), `source_text`, `ru_text`/`en_text`, `hits`, `source_log`. API: `lookup(namespace, texts, log_statuses=None)`, `remember(namespace, {text: {"ru", "en"}}, log=None)` (существующие строки не перезаписывает), `get_or_translate(namespace, texts, translator)` — готовые из памяти, недостающие одним вызовом `translator(list[str]) -> ({text: {"ru", "en"}}, usage)`, сохраняется только то, что он вернул. Админка «AI → Память переводов AI»: поиск по исходнику/переводу, правка RU/EN обычным `save()`; ручная правка отвязывает запись от лога, и исправленный перевод используется везде.

Ответ имеет ту же форму, что ответ полной генерации: сохранение, проверки, модерация и применение не меняются. В `raw_llm_response["rule_content"]` — источник описания (`template`/`memory`/`llm`), источник названий (`rules`/`llm`), был ли вызов LLM и разобранные факты; `cost_usd` = 0, если LLM не вызывался. Новые слова добавляются в словари `rules/vocab.py` без правки кода правил.

R2 опционален для основного хранилища проекта. AI-процессор также умеет читать внешние URL изображений. Наличие доступного изображения не гарантирует анализ: это зависит от режима товара и параметров запуска.

### Модерация

Без авто-применения ручная проверка включается, например, при confidence категории ниже `0.75`, подозрительной цене/лексике, слишком коротком описании или семантическом несоответствии. Сотрудник использует единое действие «Проверено — применить к товару», отклоняет или принудительно перезапускает результат. Отдельного ручного изменения статуса «Одобрено» нет.

### Что AI не перезаписывает

- **Категория.** Предложенная категория записывается, только если у товара категории нет (и confidence ≥ `0.75`). Категория определяет наценку и цену, поэтому заданную категорию AI не меняет: другое предложение даёт причину модерации `category_change_suggested`, сменить категорию модератор может вручную.
- **Slug.** AI-название меняет только `name`; slug существующего товара остаётся прежним, старые URL продолжают открываться.
- **Ручные правки.** При старте обработки в `input_data["content_snapshot"]` сохраняются хэши описания, SEO и полей переводов. При применении эти поля перезаписываются, только если текущее значение пустое или не менялось с момента генерации. Логи без снимка (созданные до этого изменения) применяются по-старому.
- **Динамические атрибуты.** `value_ru`/`value_en` существующего атрибута не обнуляются, если AI их не вернул.
- **Размеры товаров с вариантами.** Размеры из `attributes.sizes` берутся структурно, а JSON вариантов и URL картинок в поиск размеров не попадают (раньше «99» из адреса картинки считался размером). Если все найденные размеры уже есть у вариантов, причины `ambiguous_variant_sizes` нет; размеры на уровень товара с вариантами не пишутся никогда.
- **Аудитория и материал — не тип товара.** Категории «Мужские», «Men's», «Leather» не считаются конфликтом с названием («Мужские джинсы» в «Джинсах» — не `title_category_mismatch`).

### Повторный парсинг и тексты AI

Правило владения (`apps/ai/services/ownership.py`): если к товару применён AI-результат (`application_status` = applied/partial или лог утверждён), его тексты — название, описание, переводы, SEO, динамические атрибуты — принадлежат AI/менеджеру. Повторный парсинг:

- обновляет только «сырые» поля: цену, наличие, URL, `external_data` (атрибуты, источники), доменные поля, если они пусты;
- описание не трогает; свежий исходный текст кладёт в `external_data["source_description"]` (полный текст — только если он отличается от описания карточки, иначе хранится лишь хэш `source_description_sha256`);
- если исходник изменился после AI-обработки, ставит `external_data["ai_source_changed_at"]` — сигнал к переобработке: `ai_enqueue --source-changed --force`. Флаг снимается при применении нового AI-результата.
- ilacfiyati при каждом скрейпе (новый и существующий товар) пишет название со страницы в `external_data["source_name"]`; `name` существующего товара по-прежнему не трогает. Применение AI перед первым AI-названием лекарства кладёт туда прежнее `name`, если оно похоже на турецкий оригинал (без кириллицы и не обрезано). Так шаблон названия строится и при повторной обработке, когда `name` уже RU.

Без AI-результата описание заменяется только «сырым» текстом источника (маркеры ilacfiyati, непереведённый турецкий или текст, совпадающий с прошлым исходником): текст менеджера более длинным исходником не перебивается. IKEA-импорт следует тому же правилу и больше не стирает служебные ключи `ai_*`/`source_description*` при замене `external_data`.

При переобработке AI получает сохранённый исходник как `raw_description`, а не собственный прошлый текст из `description`.

### Проверки результата генерации

- Ответ, обрезанный по лимиту токенов (`finish_reason=length`) или с невалидным JSON, — ошибка: лог переходит в `failed` с записанной стоимостью вызова, дальнейшие платные шаги (перевод разделов лекарства) не запускаются и автоповтора нет. Обрезанный перевод раздела лекарства не используется — раздел уходит в модерацию.
- Лекарства: всё, что можно, делает код (раздел «Лекарства: код вместо LLM» ниже). Клинические разделы сверяются с турецким исходником без LLM (`apps/ai/services/medicine_fact_check.py`): дозировки с единицами (мг/мкг/г/мл/МЕ/ммоль/%) в каждом абзаце и в разделе целиком. Каждый новый перевод абзаца дополнительно проверяется на чужой перевод (`apps/ai/services/medicine_paragraph_check.py`, раздел «Сдвинутые переводы абзацев» ниже). Раздел с расхождением блокируется с причиной `medicine_fact_mismatch`; правка модератора снимает блок. Справочные поля, объём и МНН заполняет код, поэтому сверка на них не срабатывает.
- Название: дозировки и размеры с десятичной запятой («2,5 мг») сохраняются, вырезается только цена; подзаголовок после запятой отрезается только у книг. У лекарств «артикулы» из названия не вырезаются: бренд с дефисом («DEVIT-3», «CALIRA-MET») и «film-coated»/«gastro-resistant» в EN похожи на код (до 20.10.2026 так терялись бренд и форма). RU/EN-название с турецкими словами или их кириллической транслитерацией («Эркек…», «TAKVIYE EDICI GIDA», «SUSPANSIYON», «ГИДЕРИЧИ ДАМЛА») не применяется (`title_untranslated`). Дозировочные формы («Tablets», «Suspension») не считаются конфликтом категорий у лекарств и БАДов; категории услуг (`uslugi`) в проверке конфликтов названий не участвуют. Предложение родительской категории вместо текущей не отправляет лог в модерацию. Для БАДов в названии обязаны сохраниться бренд (первое слово источника), дозировки и фасовка, а турецкие описательные слова переводятся. Это же правило с пятью примерами «источник → ru / en» (`SUPPLEMENT_TITLE_RULES` в `content_generator.py`) стоит в статической части промпта БАДов: бренд латиницей как в источнике + вещество или тип по-русски (иначе «пищевая добавка») + дозировка + фасовка с переводом единиц (tablet → таблеток, kapsül → капсул, saşe → саше, ml → мл, sprey → спрей, şişe не пишется). В RU-названии БАДа латинское «ml» и турецкое «sprey»/«spreyi» (в любом языке) считаются непереведёнными. Если название БАДа отклонено как `title_identity_lost` или `title_untranslated`, один раз перегенерируется только пара RU/EN-названий коротким запросом с причиной отказа (≈1k токенов на вход, ≈$0.0002); новое название принимается, только если проходит проверки, иначе остаётся исходное и лог уходит в модерацию. Стоимость и итог повтора — в `raw_llm_response["title_retry"]`, `cost_usd` включает повтор. Динамические атрибуты без спецификации для типа товара (например, «путь введения» у БАДа) отбрасываются: при генерации — фильтром, при проверке — остаются только в `rejected_fields` отчёта и не отправляют лог в модерацию. Лекарственные поля источника (`administration_route`, `sgk_status` и т.п.) подаются во вход модели только для лекарств.
- EN-перевод заполняется только из EN-ответа модели; русский текст в EN не подставляется, значения на кириллице в EN отбрасываются.
- Входные данные товара собираются один раз за обработку.
- `enqueue_product_ai_task(index_vectors=False)` отключает переиндексацию рекомендаций после обработки (для массовых прогонов).

`auto_apply=True` пропускает предварительное решение `quality_checker` и сразу применяет поля, не отклонённые `SemanticValidator`. Семантические проблемы всё ещё могут оставить лог в `moderation`, но часть данных к этому моменту уже будет записана в товар. Поэтому режим подходит только для контролируемых запусков.

### Лекарства: код вместо LLM

Цель — платить модели только за то, что без неё не сделать. Для лекарства (`product_type = medicines`):

| Что | Кто делает | Где |
|---|---|---|
| Лекарственная форма, путь введения, тип рецепта, условия хранения, SGK, происхождение, срок годности («24 Ay» → «24 месяца / 24 months») | код, словарь RU/EN. Тип рецепта — без цвета турецкого бланка: «Beyaz Reçete» → «Рецептурный препарат / Prescription medicine», красный/зелёный/оранжевый/фиолетовый → «Рецептурный препарат строгого учёта», «Reçetesiz» → «Безрецептурный препарат» | `services/medicine_reference.py` |
| Объём: число из источника + единица по названию или форме («20» + tablet → «20 таблеток / 20 tablets») | код | `translate_volume` |
| Лекарственная форма в переводе (`varchar(20)`) | код: только подпись справочника («Таблетки»); иной текст applier не пишет | `dosage_form_labels` |
| МНН (`active_ingredient`) | память переводов `medicine_inn`; новое вещество — один короткий запрос, в память только проверенный перевод (полностью кириллицей, то же вещество) | `services/medicine_memory.py` |
| Название: бренд + дозировка + форма + фасовка («MAJEZIK 100 мг, таблетки, покрытые плёночной оболочкой, 15 шт.») | код по шаблону (несколько форм через запятую, «(80 TABLET)» — фасовка, CR/SR/XR — как в источнике, SETLI/PEDIATRIK — переводом); модель — только если в названии есть незнакомое слово. RU-название модели с транслитерацией турецкой формы («ДИЛАЛТИ», «ФИЛЬМ-…», «80 ТАБЛЕТ», «УЗАТИЛМИШ САЛИМЛИ», «Топикальный», «СЕРТ», «ОРОЛЬ», «(50 ТБ)», «ФИЛЬМ-КАПЛИ ТАБЛЕТКИ») или латиницей вне бренда источника («50 MG», «TU/ML») отклоняется (`title_untranslated`) — остаётся исходное название. Шаблон, промпт модели (`product_name`) и бренд абзацев строятся из турецкого оригинала (`medicine_title.medicine_source_name`): `external_data["source_name"]` → `name`, если он похож на оригинал, → строка вкладки аналогов с тем же штрихкодом → `name` как есть; проверки названия сверяются с тем же источником. Название, обрезанное прежней обработкой (число без единицы в конце: «MOUNJARO 7», «DIFFERIN 0», «Аугментин 200 мг/28»), — `title_truncated`; копия названия, которое в БД уже переведено прежней обработкой (кириллица), когда турецкого оригинала нет нигде, — `title_source_translated`. Обе причины проверяют результат, поэтому название, исправленное модератором, проходит. Лекарство без категории (на проде 140) проверяется так же — пропускается только сверка с категориями; текст лекарственной формы («gastro-resistant tablets») в сверке с чужими категориями («gastro») не участвует | `services/medicine_title.py`, `_medicine_ru_title_untranslated` |
| Реквизиты в конце инструкции («Ruhsat sahibi: … A.Ş.», адрес, «Tel: …») | код: подписи переводятся словарём, фирма и адрес — как в источнике; модели не отправляются, проверка «RU не на турецком» их не учитывает (`is_proper_name_line`) | `translate_requisites` |
| Клинические разделы (показания, противопоказания, применение, побочные, хранение) | по абзацам: готовые — из памяти `medicine_paragraph`, новые — модель короткими запросами (до 10 абзацев и 5000 символов, RU и EN каждого абзаца — одним объектом под его номером); абзац с другой дозировкой, непереведённый или с чужим переводом — один повтор, при сдвиге ответа повторяется весь запрос, иначе раздел уходит в модерацию и в память не попадает. Слова источника заглавными, перенесённые в перевод латиницей (бренд), в проверке «RU не на турецком» не считаются: «5. DERMOVATE'IN SAKLANMASI» → «5. Хранение DERMOVATE» — перевод (до 20.10.2026 такой заголовок давал `ru_not_russian`) | `translate_sections_by_paragraph`, `paragraph_problems` |
| Короткое описание, SEO RU/EN, особые сведения | модель (карточка); справочные поля в ответе больше не запрашиваются, она получает их готовыми переводами (`facts_ru`/`facts_en`). Цвет рецепта в описании и SEO код убирает («по белому рецепту» → «по рецепту», `neutral_prescription_text`). Особые сведения — бейджи «ÖZEL BİLGİLER» ilacfiyati; бейджи без предмета («Birlikte kullanılmamalıdır», «Dikkatli olunmalıdır», «Hastalar duyarlılıkları belli oluncaya kadar kullanmamalıdır») модели не передаются, а если других нет — `special_notes` из ответа отбрасывается (`meaningful_special_notes`) | `_construct_medicine_user_prompt`, `_apply_medicine_code_fields` |
| Атрибуты лога (коды, штрих-код, SGK-коды) | код, копия источника | `MEDICINE_SOURCE_ATTRIBUTE_KEYS` |

Неизвестное значение справочника не переводится (на сайте остаётся исходник) и попадает в `extracted_attributes["medicine_reference_unknown"]` и в отчёт `medicine_reference_coverage`; словарь дополняется в коде.

Шаблон названия (с 20.10.2026 строится для 9 420 из 13 033 лекарств вместо 6 977): сокращения и английские слова источника разворачиваются («TB», «TAB», «TABLETS», «CAP», «VIAL», «AMP.», «FLK.», «ENJ.», «INF.», «COZ.», «SOL.», «I.V.», «ENT.», «YUM.», «GRAM», «POWDER»); связка «ICEREN» пропускается, а флакон/ампула как форма не повторяется, если указана фасовкой («ICEREN FLAKON (1 FLAKON)» → «1 флакон»); формы «… HAZIRLAMAK ICIN TOZ / LIYOFILIZE TOZ / KONSANTRE», «ENJEKSIYONLUK/INFUZYONLUK COZELTI», «TOZ VE COZUCU» («с растворителем»), «REKTAL MERHEM», «SISE» и др.; форма после фасовки («UZATILMIS SALIMLI 30 TABLET»); разделитель между дозировками как в источнике — «+» и «VE» → « + », «/» сохраняется, «400/57 MG» → «400/57 мг» (раньше «1 MG/ML + 50 MG/ML» становилось «1 мг/мл (50 мг/мл)»); два разных числа фасовки («KLACID MR 500 … (20 TABLET)») — шаблон не строится. Турецкое название вещества в начале названия («MAGNEZYUM SULFAT», «DEKSTROZ») остаётся как бренд — так было и раньше.

Испорченные названия в БД. У старых лекарств `Product.name` уже переведён прежней обработкой или обрезан на десятичном разделителе: на проде 20.10.2026 — 119 из 13 033 (103 с кириллицей, 16 обрезанных; 25 ещё не обработаны AI). Турецкое название для них берётся из уже сохранённой вкладки аналогов (`external_data.attributes.source_tabs.equivalents`, строка перед `BARKOD` с тем же штрихкодом) — по данным 20.10.2026 у 70 из 119, шаблон из него строится у 39. Остальным нужен перескрейп по URL: парсер запишет `source_name` (сам `name` он не меняет). Если турецкого названия нет нигде, шаблон не строится, а копия названия уходит в модерацию (`title_source_translated`, `title_truncated`).

До 20.10.2026 применение AI писало RU-название в `name`, а турецкий оригинал нигде не хранился, поэтому повторная обработка уже применённого лекарства тоже не строила шаблон. Теперь оригинал сохраняется в `external_data["source_name"]` (см. «Повторный парсинг и тексты AI»). `medicine_paragraph_batch` и `medicine_reference_coverage --paragraphs` берут бренд для ключей абзацев из того же источника, что и обработка. «Название по шаблону» и объём в `medicine_reference_coverage` тоже считаются по `medicine_source_name`, поэтому после массового AI-прогона (в `name` — RU-название) доля не падает; из `external_data` отчёт читает только `source_name`, `attributes.barcode` и `attributes.source_tabs.equivalents.text`.

Бренд в абзацах инструкций заменяется меткой `{BRAND}`: абзац «MAJEZIK'i … kullanmayınız» и тот же абзац у PAROL («PAROL'ü …») — одна запись памяти и один перевод модели. Бренд — первые слова названия до дозировки (как в шаблоне названия, `paragraph_brand`); метка ставится на бренд с заглавной буквы в любом написании (MAJEZIK, MAJEZİK, Majezik), знак ® после бренда в ключ не попадает, турецкий суффикс после апострофа приводится к одной форме (`'ı/'ü/'yu` → `'i`, `'nın/'un` → `'in`, `'ya` → `'e`, `'ta` → `'de`; «EPORON®'u» → `{BRAND}'i`). Бренд короче 3 букв или совпадающий с МНН («IBUPROFEN 400 MG») не заменяется. Модель обязана вернуть метку в RU и EN, иначе абзац — брак (`brand_token_missing`); в карточку метка подставляется обратно брендом из названия. В админке памяти такие абзацы видны с `{BRAND}` — при ручной правке метку не трогать. `medicine_paragraph_batch` и `medicine_reference_coverage --paragraphs` строят ключи так же.

Абзац — строка текста раздела, но строка, которую от предложения отрезал строчный тег страницы ilacfiyati (так парсер собирал текст до 21.10.2026 — через `get_text("\n")`, и `<b>`, `<sup>`, `<sub>`, `<a>` внутри предложения становились отдельными строками; теперь `_block_text` переводит строку только между блочными элементами — `<p>`, `<li>`, `<td>`, `<br>`…, и склейка нужна для `source_tabs`, снятых раньше), приклеивается к предыдущей (`split_paragraphs`): «Somatropine veya NORDITROPIN» / «®» / «'un içerisindeki … varsa.» — один абзац «Somatropine veya {BRAND}'in içerisindeki … varsa.». Клеится строка из знака ®/™, строка с турецкого суффикса после апострофа («'un», «'in») или с закрывающего знака («,», «.», «)»), строка после ® и после индекса («B» / «12» / «vitamini», «mg/m» / «2», «25» / «o» / «C altında»), ссылка «www.…» внутри фразы и строка со строчной буквы после неё или после слова заглавными («DERHAL» / «doktorunuza başvurunuz», буквица «A» / «şağıdakilerden»). Строка со строчной буквы после обычной строки остаётся отдельным абзацем — так выглядят пункты списка побочных эффектов («baş ağrısı» / «bulantı»); не клеятся и нумерация «1.», заголовки, ячейки таблицы доз («miktarı» / «8» / «Günde iki kez 3 ml»), реквизиты и строки через пустую строку. Проверено разметкой 349 публичных страниц ilacfiyati: склейка совпадает с HTML в 99,5 % случаев и находит 78 % разрывов; цифры и оценка повторного перевода — [docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md](docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md), «Обрывки абзацев» и «Блочный сбор раздела в парсере».

Перед применением лога лекарства (кнопка «Проверено — применить к товару», одобрение через API, авто-применение, «Закрыть решённые записи модерации») клинические разделы перевода сверяются с исходником лога (`input_data.attributes.source_tabs`) по абзацам теми же правилами, что и абзацы в памяти, плюс сдвиг по соседним абзацам (`medicine_paragraph_findings` в `semantic_validator.py`, `section_paragraph_problems`). Раздел с подозрительными абзацами не применяется ни в одном языке, лог уходит в модерацию с причиной `medicine_paragraph_mismatch`; в логе видно, какие абзацы и почему (номер, исходник и RU в подсказке поля, строка «Не будет применено» в сравнении), а в `application_report["paragraph_problems"]` — номера и причины. Модератор может исправить абзацы в форме лога (исправленный текст повторно не проверяется — за него отвечает модератор), выбрать «Не менять этот раздел товара» или перезапустить AI. Раздел без исходника в логе (перевод сделан не по абзацам) не сверяется. На проде 22.10.2026 проверка задерживает 112 из 125 ожидающих логов (это логи до PR #121, в них ≈ 4,6 тыс. подозрительных абзацев), а на переводах из очищенной памяти — 2 раздела из 315.

Память переводов — модель `AITranslationMemory` (раздел AI → «Память переводов AI»): исходный текст, RU, EN, счётчик использований. Правка МНН менеджером сразу разносится по переводам всех лекарств с этим веществом (сигнал в `apps/ai/signals.py`); правка абзаца применяется при следующей обработке товара. В `raw_llm_response.section_translation` видно, сколько абзацев взято из памяти (`paragraphs_cached`) и сколько перевела модель (`paragraphs_translated`).

Команды:

```bash
# Отчёт (только чтение): неизвестные значения справочников, доля названий по шаблону (из турецкого оригинала),
# сколько МНН и абзацев ещё не в памяти и сколько стоит их перевод
docker compose exec backend poetry run python manage.py medicine_reference_coverage --paragraphs

# Испорченные name (кириллица, обрезка): откуда берётся турецкое название и строится ли шаблон,
# остальным — URL для перескрейпа. Без --dry-run название из вкладки аналогов пишется в source_name
docker compose exec backend poetry run python manage.py medicine_source_names --dry-run

# Одноразовый перевод всех МНН в память (пачки по 100), затем разнос по товарам
docker compose exec backend poetry run python manage.py translate_medicine_inn --dry-run
docker compose exec backend poetry run python manage.py translate_medicine_inn

# Опционально перед массовым прогоном: абзацы инструкций через OpenAI Batch API (−50 %, до 24 ч) частями
docker compose exec backend poetry run python manage.py medicine_paragraph_batch submit --dry-run   # что войдёт в часть и цена
docker compose exec backend poetry run python manage.py medicine_paragraph_batch submit             # часть по 5000 абзацев
docker compose exec backend poetry run python manage.py medicine_paragraph_batch status             # все части и их состояние
docker compose exec backend poetry run python manage.py medicine_paragraph_batch collect <batch_id> # забрать часть + отчёт
docker compose exec backend poetry run python manage.py medicine_paragraph_batch submit --retry <batch_id>  # только отклонённые

# Аудит памяти абзацев: отчёт, затем бэкап и перенос подозрительных в medicine_paragraph_suspect
docker compose exec backend poetry run python manage.py medicine_paragraph_audit --dry-run --report /tmp/paragraph_audit.jsonl
docker compose exec backend poetry run python manage.py medicine_paragraph_audit --backup /tmp/paragraph_audit_backup.json
```

Пакет идёт частями по `--part-size` абзацев (по умолчанию 5000, ≈ 500 запросов): при ошибке теряются деньги одной части. Часть — абзацы, которых нет в памяти, по лекарствам в порядке `pk` с лекарства после последней части (номер части и последнее лекарство записаны в метаданных пакета OpenAI; `--from-start` — с начала каталога) и заканчивается на границе лекарства. `submit` не отправит часть, пока предыдущая в работе (иначе те же абзацы оплатятся дважды) или пока у последней части нет в памяти больше `--max-defect` абзацев (по умолчанию 15 %): она не забрана или брак выше порога. `submit --retry <batch_id>` отправляет только абзацы этой части, которых нет в памяти; следующая часть их не повторяет. Для частей, отправленных до склейки строк (часть №1 от 21.10.2026), `--retry` не нужен — он отправил бы обрывки, которые больше не используются; их абзацы в новом виде заберёт часть с `--from-start`.

То же без консоли — в админке: AI → AI-прогоны → «Перевести абзацы инструкций (Batch API)» (устройство — в «Массовые прогоны из админки», пошагово — [docs/AI_RUNS_ADMIN_GUIDE.md](docs/AI_RUNS_ADMIN_GUIDE.md), раздел 5). Команда и админка вызывают один код — `apps/ai/services/medicine_paragraph_batch.py` (выбор части `iter_parts`, `submit_part`, `collect_part`, итог `part_summary`) — и пишут одинаковые метаданные пакета; у частей из админки есть ещё `run` (номер прогона), `status` их показывает, а `submit` учитывает их как предыдущие части. Каталог при выборе части читается потоком (`iter_missing_paragraphs`: хэши уже встреченных абзацев и сверка с памятью порциями по 2000), поэтому часть выбирается без загрузки всего каталога в память. Брак части в отчёте — отправленные абзацы, не попавшие в память: отклонённые проверкой и абзацы запросов, на которые OpenAI не ответил («без ответа»).

`collect` проверяет каждый абзац теми же правилами, что обычный перевод, включая сдвиг ответа (`shifted` — отклоняется весь запрос); отклонённые переводятся повтором части или уже при обработке товара. В конце — отчёт части: абзацев и запросов, принято, брак с долей и причинами, в скольких запросах сдвиг, цена всего и за 1000 абзацев (по `usage` ответов, цены Batch API), и вывод «можно следующую часть» или «СТОП». Обычная обработка (`ai_enqueue`) работает и без Batch API — память заполняется по ходу прогона. `collect` читает пакет потоково (пиковая память — десятки МБ; входной файл пакета временно кладётся в `--work-dir`, нужно его размер + 1 ГБ свободного места) и пишет в память порциями по 500 строк, каждая в своей транзакции (`translation_memory.REMEMBER_BATCH_SIZE`): одна вставка на ~300 тыс. абзацев 20.10.2026 уронила Postgres по OOM. Прогресс печатается каждые `--progress-every` запросов; прерванный collect повторяется той же командой — записанное не дублируется. Запускать в отдельном контейнере, не в воркере с CLIP.

#### Сдвинутые переводы абзацев

В длинном JSON-ответе модель иногда пропускает элемент, и дальше каждому ключу достаётся перевод следующего абзаца («5. VISCOTEARS'IN SAKLANMASI» → «Храните при комнатной температуре ниже 25°C»); бывает, что сдвинут только EN. 20.10.2026 так было испорчено ≈ 21 % памяти `medicine_paragraph` — отчёт, цифры по правилам и порядок исправления на проде: [docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md](docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md). Проверки без LLM (`medicine_paragraph_check.py`):

- в `paragraph_problems` (`item_problems`): `heading_mismatch` — номер «N.» заголовка исходника стоит в начале RU и EN («1. günde» — не заголовок); `number_mismatch` — все числа, а не только дозировки (разделители тысяч, «2,50» = «2.5», «½», «tip II» = «2 типа»; 1 и 0 не сравниваются; числа словами — «üç», «трёх», «twice» — только оправдывают цифру); `length_mismatch` — перевод длиннее или короче исходника больше чем вдвое; `ru_en_mismatch` — числа или длина RU и EN расходятся; `concept_mismatch` — ни одного из ≥ 2 медицинских понятий исходника (почки, врач, хранение, таблетка…; словарь TR/RU/EN `_CONCEPTS`) нет в переводе; `frequency_mismatch` — «Yaygın olmayan:» переведено не как «Нечасто:»/«Uncommon:»;
- в `check_paragraph_payload` (`request_shift`): если перевод абзаца ближе к соседнему исходнику ответа, чем к своему (по числам, понятиям, длине — модель Гейла–Чёрча, номеру заголовка, метке `{BRAND}`), отклоняется весь запрос (`shifted`): он короткий (до 10 абзацев), и повтор дешевле риска принять чужой перевод на границе сдвига. Это работает и в обычной обработке, и в `medicine_paragraph_batch collect`.

Причина сдвига — длина ответа: в пакете 20.10 (20 000 символов, ≈ 154 абзаца на запрос) сдвиг был в 59 % запросов; среди первых 10 абзацев запроса сдвинуто 1,6 %, к концу — до 54 %. Ответ, где у части абзацев нет перевода, тоже считается сдвигом (так выглядели 86 % сдвигов). Поэтому запрос — до 10 абзацев (`PARAGRAPH_BATCH_ITEMS`) и 5000 символов (`PARAGRAPH_BATCH_CHARS`), а RU и EN абзаца модель возвращает одним объектом `{"1": {"ru": …, "en": …}}`; прежний формат `{"ru": {…}, "en": {…}}` `collect` тоже читает. Оценка и план пилота — в [docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md](docs/MEDICINE_PARAGRAPH_SHIFT_2026-10-20.md), раздел «Маленькие запросы».

Уже записанную память проверяет `medicine_paragraph_audit`: те же правила плюс сдвиг относительно соседних записей (записи одного запроса стоят в памяти подряд по `pk`). `--dry-run` — только отчёт (`--report` — JSONL со всеми подозрительными записями); без него команда сначала пишет бэкап затронутых строк в `--backup` (формат `loaddata`), затем переносит их в namespace `medicine_paragraph_suspect`: память их не находит, и абзац переведётся заново при следующей обработке или `medicine_paragraph_batch submit`. Строки остаются в БД и видны в админке; ручные правки (`updated_at` позже `created_at`) не трогаются; откат — `manage.py loaddata <backup>`.

## 4. API

Все `/api/ai/...` endpoints имеют permission `IsAdminUser`: пользователь должен быть аутентифицирован и иметь `is_staff=True`. Обычный пользователь с корректным JWT получает `403`; анонимный запрос — `401`.

### Обработка товара по ID

```http
POST /api/ai/process/<product_id>/
```

```json
{
  "generate_description": true,
  "categorize": true,
  "analyze_images": true,
  "use_images": true,
  "auto_apply": false
}
```

Все пять полей необязательны и имеют показанные значения по умолчанию.

- `generate_description` — включить текстовую генерацию;
- `categorize` — включить предложение категории;
- `analyze_images` — участвует в выборе режима обработки;
- `use_images` — разрешает фактическую загрузку изображений;
- `auto_apply` — сразу применить результат к товару.

Vision и загрузка изображений выполняются только когда оба флага истинны.
Поэтому любой из `"analyze_images": false` или `"use_images": false` полностью
отключает image pipeline; для явности в примерах без Vision допустимо передать
оба значения `false`.

Пример для staff-пользователя:

```bash
curl -X POST http://localhost:8000/api/auth/jwt/create/ \
  -H 'Content-Type: application/json' \
  -d '{"username":"<staff-user>","password":"<password>"}'

curl -X POST http://localhost:8000/api/ai/process/<product-id>/ \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <access-token>' \
  -d '{"generate_description":true,"categorize":true,"analyze_images":true,"use_images":true,"auto_apply":false}'
```

Успешная постановка возвращает `202`, `task_id`, `log_id` и `submitted`. Значение `submitted=false` означает, что подходящий лог уже существовал и новая задача не создавалась.

### Альтернативный endpoint

```http
POST /api/ai/generate/
```

Он принимает те же флаги, а также обязательный `product_id` и необязательный `processing_type`: `full`, `description_only`, `categorization_only` или `image_analysis`.

### Просмотр и модерация

- `GET /api/ai/logs/` — список логов;
- `POST /api/ai/logs/<id>/approve/` — применить завершённый результат;
- `POST /api/ai/logs/<id>/reject/` — отклонить;
- `POST /api/ai/logs/<id>/reprocess/` — принудительный повтор без авто-применения;
- `/api/ai/moderation/` — очередь модерации;
- `/api/ai/templates/` — шаблоны;
- `GET /api/ai/stats/?days=30` — статистика, диапазон `1..365` дней.

## 5. Django Admin

Для товаров доступны действия:

- «[AI] Полная AI обработка (без авто-применения)»;
- «[AI] Полная AI обработка + авто-применение»: новые товары ставятся в обработку, а уже готовый (`completed`) лог применяется без повторной генерации; логи в очереди, на модерации или уже применённые пропускаются (в сообщении — счётчики по каждому случаю);
- просмотр последнего AI-статуса.

Оба действия принимают не больше 100 товаров (`AI_ADMIN_MAX_PRODUCTS`). Массовая обработка — разделом «AI-прогоны» (ниже) или командой `ai_enqueue`, но не в HTTP-запросе админки.

В админке скрапера кнопка сессии/задачи выбирает товары из `ScrapedProductLog` с action `created` или `updated` и ставит их в очередь с `auto_apply=False`. Это отдельное действие и не является продолжением парсинга.

Раздел AI показывает сравнение текущих полей товара с предложением AI, причины блокировки и фактический статус применения. Единое действие сохраняет правки модератора, применяет разрешённые поля и закрывает очередь только при полном успехе. Страница `/admin/ai/manual-tasks/` запускает категоризацию товаров без категории, генерацию отсутствующих описаний, повтор недавних ошибок и очистку логов. Первые три действия могут расходовать токены и не включены в Celery Beat.

### Массовые прогоны из админки

Пошаговая инструкция для администратора — [docs/AI_RUNS_ADMIN_GUIDE.md](docs/AI_RUNS_ADMIN_GUIDE.md). Устройство:

- Модель `AIRun` (`apps/ai/models.py`): вид операции, кто запустил, условия (тип товара, категория, лимит, «только без описания», авто-применение), состояние (`draft` / `running` / `stopped` / `finished` / `failed`), счётчики, оценка и фактическая стоимость (сумма `cost_usd` логов прогона), пояснение и отчёт. Логи прогона — M2M `AIRun.logs` (фильтр «AI-прогон» в «Логах AI обработки»).
- Логика — `apps/ai/services/ai_runs.py`, страницы — `apps/ai/admin_runs.py`, шаблоны — `templates/admin/ai/airun/`. Выборка, оценка и обслуживающие операции общие с командами (`apps/ai/services/bulk_ops.py`).
- Кнопка «Запустить» только создаёт `AIRun` с зафиксированным списком товаров и ставит задачу `advance_ai_run` (очередь `ai`, `priority=0`, раньше обычных AI-задач). Каждый шаг (раз в 15 с) проверяет текущую партию, при необходимости останавливает прогон и ставит следующие 20 товаров через `enqueue_or_apply_product_ai` (как `ai_enqueue --wait`, без переиндексации рекомендаций; после прогона с авто-применением один раз ставится `index_product_vectors`). `tick_token` не даёт двум цепочкам шагов работать параллельно.
- Автоостановка: в завершившейся партии ошибок больше 30 % или партия не завершилась за 30 минут. Нет шагов дольше 5 минут — прогон показывается как зависший с кнопкой «Продолжить».
- «Остановить»: ожидающие (`pending`) логи текущей партии получают `failed` с текстом «Отменено: …» — воркер такие задачи пропускает, товары возвращаются в начало очереди прогона и, так как `failed` не считается обработкой, попадают в выборку следующих прогонов. Отменённые не считаются ошибками партии. Обрабатываемые (`processing`) дорабатывают.
- Защиты: условный `UniqueConstraint` — не больше одного `running`-прогона на тип товара (и на вид обслуживающей операции); лимит 1000 товаров за запуск; при оценке больше $5 нужна галочка подтверждения. Константы — в начале `services/ai_runs.py`.
- Обслуживающие операции («Перегенерировать отклонённые названия» = `retry_ai_titles`, «Закрыть решённые записи модерации» = `close_resolved_ai_moderation`): черновик → задача `run_ai_maintenance` считает dry-run и показывает список → после «Да, выполнить» та же задача выполняет операцию (лимит до 500 записей).
- Перевод абзацев инструкций (`AIRun.Kind.MEDICINE_PARAGRAPHS`, = `medicine_paragraph_batch`): форма (абзацев в части 10–20 000, порог брака, «ждать кнопки после каждой части») → «Посчитать» создаёт черновик, задача `preview_medicine_paragraph_run` проходит каталог по частям и пишет оценку (абзацы, части, запросы, цена Batch API и обычная) → «Запустить» ставит задачу `advance_medicine_paragraph_run` (раз в 5 минут, `PARAGRAPH_TICK_SECONDS`). Шаг: часть в OpenAI ещё в работе — ждать; готова — `collect_part` пишет принятое в память, итог части сохраняется; дальше остановка (брак выше порога, запрошен «Стоп», включено «ждать», OpenAI выполнил часть не целиком) или следующая часть с лекарства после последней забранной (`iter_parts`); абзацев не осталось — прогон завершён. Пакет без файла ответов (OpenAI отклонил часть) — часть `failed`, курсор не двигается: «Следующая часть» отправит те же абзацы. Перед отправкой проверяется, что в OpenAI нет другой части в работе (например, из консоли), иначе остановка — абзацы не оплатятся дважды.
- Состояние прогона абзацев — в `AIRun.report`: `settings`, `preview` и `parts` (по каждой части: номер, `batch_id`, `retry_of`, абзацев, последнее лекарство, состояние, запросы, принято/брак/без ответа, сдвиг, причины, цена, цена за 1000, время отправки и сбора); счётчики прогона: `queued_count` — отправлено абзацев, `done_count` — принято, `failed_count` — брак без принятых повтором, `cost_usd` — сумма по частям. Кнопки: «Стоп» (часть, уже отправленная в OpenAI, оплачена — её заберём, прогон остановится после неё), «Следующая часть» (у остановленного, даже при браке выше порога), «Повторить отклонённые» (абзацы последней забранной части, которых нет в памяти — `rejected_paragraphs`), «Продолжить» (после сбоя шага или зависания: нет шагов 20 минут). Строка прогона блокируется на весь шаг, сбор части пишет память одной транзакцией; кнопки во время шага отвечают «повторите через минуту». Прогон с частью в OpenAI нельзя удалить. Один такой прогон за раз (тот же `UniqueConstraint`). Код — раздел «перевод абзацев инструкций» в `services/ai_runs.py`, шаблон части страницы — `templates/admin/ai/airun/_paragraphs.html`.

## 6. Команды

### Массовая постановка: `ai_enqueue`

Ставит товары в очередь `ai` батчами. Обязателен `--limit`; по умолчанию пропускает товары с готовым или активным логом и не применяет результат.

```bash
# Сначала всегда dry-run: выборка, первые id и оценка стоимости (по средним cost_usd логов)
docker compose exec backend poetry run python manage.py ai_enqueue --product-type medicines --limit 20 --dry-run

# Батчи по 10, ждать каждый батч, остановиться при >2 ошибках, без переиндексации рекомендаций
docker compose exec backend poetry run python manage.py ai_enqueue --product-type medicines --limit 20 \
    --batch-size 10 --wait --max-failures 2 --no-index-vectors
```

Фильтры: `--product-type` (можно несколько), `--category <slug>` (с подкатегориями), `--ids 1,2,3`, `--missing-description`, `--include-processed`. Режимы: `--processing-type full|description_only`, `--auto-apply`, `--force`, `--batch-delay`, `--wait-timeout`.

### Регламент массового прогона

Шаги ниже можно выполнять кнопками в «AI → AI-прогоны»: «Посчитать» = dry-run, прогон всегда идёт партиями по 20 с ожиданием и автоостановкой, «Сразу применять результат» = `--auto-apply`.

Ориентиры по партиям на проде 2026-10-18 (gpt-4o-mini): лекарство ≈ $0.006 и 60–80 с, остальные ≈ $0.001 и 6–9 с (до детерминированной обработки; теперь узкий запрос ≈ $0.0003–0.0005, описание из фактов и из памяти — $0); общий префикс промпта кэшируется (3072 токена). Полный каталог (~13 тыс. лекарств, ~8 тыс. БАДов, ~5 тыс. прочих) ≈ $95. После перевода лекарств на код и память переводов (см. «Лекарства: код вместо LLM») оценка для лекарств — ≈ $28 на каталог (≈ $17 с `medicine_paragraph_batch`), уточняется пилотом.

1. **Перед запуском:** свободно ≥ 3 ГБ на диске (`df -h /`), Redis без ошибок записи (`redis-cli info persistence`: `rdb_last_bgsave_status:ok`), нет активных AI-логов. Бэкап: `pg_dump` (или снимок затрагиваемых товаров: id, категория, slug, имя, цена, тексты).
2. **Dry-run:** `ai_enqueue --product-type <тип> --limit <N> --dry-run` — проверить число товаров и оценку стоимости.
3. **Сначала без авто-применения**, небольшая партия по каждому типу (10–20): `ai_enqueue --product-type <тип> --limit 20 --batch-size 10 --wait --max-failures 2 --no-index-vectors`. Просмотреть результаты в AI → Логи: названия, описания RU/EN, причины модерации.
4. **Затем с авто-применением** растущими партиями (50 → 200 → 1000): добавить `--auto-apply`; один тип за раз; `--batch-size 20 --wait --max-failures 3`.
5. **Что смотреть по ходу:** доля `failed` (сообщение в `error_message`), доля `moderation` и её причины (одна причина у большинства — системная проблема, а не товары), стоимость `cost_usd` против оценки dry-run, свободное место на диске.
6. **Когда останавливать:** команда сама останавливается при ошибках в батче больше `--max-failures`. Остановить вручную, если: модерация > 30 % с одной повторяющейся причиной; стоимость заметно выше оценки; ошибки 429/квота (`insufficient_quota`); диск < 2 ГБ. Остановка: прервать команду (Ctrl+C), ожидающие логи партии перевести в `failed` — задачи по неактивным логам воркер пропускает.
7. **После:** `close_resolved_ai_moderation --dry-run`, затем без `--dry-run`, если после исправлений остались лишние записи; если запускали с `--no-index-vectors`, переиндексировать рекомендации: `index_product_vectors.delay()` без аргументов сам выберет товары, изменённые после последней индексации.

### Закрытие лишней модерации: `close_resolved_ai_moderation`

В админке — кнопка «Закрыть решённые записи модерации» в «AI-прогонах».

После исправлений валидатора закрывает открытые записи модерации, у которых `get_moderation_reasons(log)` стал пустым (например, лог ушёл в модерацию только из-за запрещённого для домена атрибута). Закрытие идёт тем же путём, что ручное «Проверено — применить к товару»: разрешённые поля применяются, лог становится `approved`, запись очереди получает `resolved_at`.

```bash
docker compose exec backend poetry run python manage.py close_resolved_ai_moderation --dry-run
docker compose exec backend poetry run python manage.py close_resolved_ai_moderation --product-type supplements --limit 50
```

### Повтор отклонённых названий БАДов: `retry_ai_titles`

В админке — кнопка «Перегенерировать отклонённые названия» в «AI-прогонах».

Для логов, обработанных до появления автоповтора названия (или если повтор не помог): берёт открытые записи модерации БАДов с причиной `title_identity_lost` / `title_untranslated` и для каждого лога делает один короткий запрос только за RU/EN-названием (≈$0.0002). Новое название пишется в лог, только если проходит проверки; товар команда не меняет. Применить названия и закрыть модерацию — `close_resolved_ai_moderation`.

```bash
docker compose exec backend poetry run python manage.py retry_ai_titles --limit 50 --dry-run
docker compose exec backend poetry run python manage.py retry_ai_titles --limit 50
docker compose exec backend poetry run python manage.py close_resolved_ai_moderation --product-type supplements --dry-run
docker compose exec backend poetry run python manage.py close_resolved_ai_moderation --product-type supplements
```

### Диагностика

Подготовка RAG создаёт коллекции Qdrant, синхронизирует категории и импортирует шаблоны:

```bash
docker compose exec backend poetry run python manage.py setup_ai_rag
```

Синхронный benchmark не использует очередь Celery:

```bash
# Только показать выбранные товары; OpenAI не вызывается
docker compose exec backend poetry run python manage.py benchmark_ai 3 --dry-run

# Реальная обработка без применения результата
docker compose exec backend poetry run python manage.py benchmark_ai 3

# Реальная обработка с немедленным применением
docker compose exec backend poetry run python manage.py benchmark_ai 3 --auto-apply
```

Команда выбирает первые `N` товаров из `Product`; это smoke/стоимостной benchmark, а не изолированный unit-тест. Реальные запуски требуют доступных PostgreSQL, OpenAI и, для RAG, Qdrant. Асинхронный API дополнительно требует Redis и worker очереди `ai`.

`cost_usd` считается по `AI_CONFIG["PRICING"]` с учётом кэшированной части промпта (`tokens.cached`). Для модели без цены в таблице стоимость записывается как 0 с предупреждением в логе — при смене `AI_MODEL` добавьте её тариф.

Промпты построены так, чтобы работал кэш OpenAI: статические правила и схема ответа идут первыми и одинаковы для всех товаров типа, а данные товара, RAG-контекст и инструкция категории — в конце. В схеме ответа нет конкретных примеров значений (категория, материал, размер), которые модель могла бы скопировать. Температура: лекарства 0.2, остальные 0.3.

При смене embedding-модели нужно учитывать, что `QdrantManager` сейчас создаёт векторы размерности `1536`. При изменении размерности коллекции необходимо пересоздать согласованно с моделью и повторно выполнить `setup_ai_rag`.

## 8. Ограничения

- AI зависит от внешнего OpenAI API и может расходовать заметный бюджет; расчёт `cost_usd` основан на таблице цен `AI_CONFIG["PRICING"]` и может отличаться от фактического счёта, если тарифы не обновлены.
- Qdrant улучшает контекст, но его недоступность не всегда делает задачу ошибочной: генерация может продолжиться без RAG.
- Модель может ошибаться или придумать неподтверждённый атрибут; рекомендуемый режим — `auto_apply=False` и модерация.
- Шаблоны и категории в Qdrant не обновляются автоматически после каждого изменения БД; RAG нужно синхронизировать явно.
- Отдельная AI-обработка содержательных вариантов запускается вручную; обычные цветовые варианты не должны автоматически умножать число LLM-вызовов.
